# 缓存设计与问题处理

## 缓存场景概览

| 场景 | 接口 | 缓存层 | TTL |
|---|---|---|---|
| 图片单条查询 | `GET /picture/get/vo` | Redis | 5min |
| 图片分页查询 | `POST /picture/list/page/vo/cache` | Caffeine + Redis | 300~600s |
| 空间单条查询 | `GET /space/get/vo` | Redis | 10min |

---

## 场景一：图片单条查询

```
key: teacuppicture:picture:{id}
```

### 缓存穿透 ✅ 空值缓存

不存在的 id 查询结果写入 Redis，TTL=2min，拦截后续相同请求。

```java
if (picture == null) {
    stringRedisTemplate.opsForValue().set(cacheKey, "null", 2, TimeUnit.MINUTES);
    throw new BusinessException(ErrorCode.NOT_FOUND_ERROR);
}
if ("null".equals(cached)) throw new BusinessException(ErrorCode.NOT_FOUND_ERROR);
```

**为什么不用布隆过滤器？**

- 布隆过滤器有误判率（~0.1%），会误拒合法 id
- 不支持删除（图片删除后过滤器无法同步），需要 Counting Bloom Filter，实现复杂
- 项目图片量不是亿级，空值缓存实现简单且零误判

### 缓存击穿 ⚠️ 低风险，未加锁

单图以 ID 定位，TTL 5min，过期后的并发冲击通常是个位数。真正的热点图片在 5min 内大概率一直在缓存中不会频繁过期。如遇百万并发热图，可补加与场景二相同的互斥锁。

### 缓存雪崩 ✅ 主动清理分散风险

图片增删改后由观察者模式立即清除对应 key，缓存的自然过期时机分散到各图片的最后写入时间点，而非同一批次到期。

## 场景二：图片分页查询（核心场景）

```
key: teacuppicture:listPictureVOByPage:{MD5(queryParams)}
```

### 缓存穿透 ✅ 天然不存在

"无数据"的查询结果是空列表 `[]`，会被正常缓存，不会穿透到 DB。

### 缓存击穿 ✅ Redis 互斥锁

热点 key 过期时，只允许一个线程查 DB，其余线程等待后读缓存。

```java
String lockKey = cacheKey + ":lock";
Boolean locked = stringRedisTemplate.opsForValue().setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);
try {
    if (!Boolean.TRUE.equals(locked)) {
        try { Thread.sleep(100); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        cachedValue = valueOps.get(cacheKey);
        if (cachedValue != null) return ResultUtils.success(JSONUtil.toBean(cachedValue, Page.class));
    }
    // 持锁线程查DB → 写缓存
} finally {
    if (Boolean.TRUE.equals(locked)) stringRedisTemplate.delete(lockKey);
}
```

**互斥锁 vs 逻辑过期**

| | 互斥锁 | 逻辑过期 |
|---|---|---|
| 一致性 | 强一致（等待新数据） | 弱一致（有短暂旧数据窗口） |
| 可用性 | 等待期间有轻微阻塞 | 始终快速返回 |
| 实现复杂度 | 低 | 高（需要异步线程池） |
| 适用场景 | 数据准确性要求高 | 超高并发、可容忍短暂旧数据 |

图片列表对实时性有要求（新上传图片应尽快出现），且项目并发量不是微博热搜级别，互斥锁的轻微等待代价可接受。

### 缓存雪崩 ✅ 随机 TTL + 双层缓存

**随机 TTL** 把同类 key 的过期时间打散在 5min 窗口内：

```java
int cacheExpireTime = 300 + RandomUtil.randomInt(0, 300); // 300~600s
```

**双层缓存（Caffeine 兜底）** 即使 Redis 宕机或大面积过期，本地缓存还有 30min 保护：

```
Caffeine (TTL=30min, max=1000条) → Redis (TTL=300~600s) → DB
```

**为什么不用 Redis 集群作为雪崩防护？**  
集群解决的是 Redis 高可用，无法解决大量 key 同时过期的问题。随机 TTL + 双层缓存成本更低，对单机 Redis 同样有效。

## 场景三：空间单条查询

```
key: teacuppicture:space:{id}  TTL=10min
```

### 缓存穿透 ❌ 待修复

当前代码在 `spaceService.getById(id)` 返回 null 时直接抛异常，未缓存空值。修复方式与场景一完全一致。

### 缓存击穿 ⚠️ 低风险

空间数量远少于图片，写操作后立即删除缓存 key，自然过期概率低，击穿风险可接受。

### 缓存雪崩 ✅ 主动清理

增删改操作后立即删除对应 key，主动失效比自然过期更可控：

```java
stringRedisTemplate.delete(SPACE_CACHE_PREFIX + id);
```

## 总结

| | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
|---|---|---|---|
| 图片单条查询 | ✅ 空值缓存 | ⚠️ 低风险未加锁 | ✅ 主动清理分散 |
| 图片分页查询 | ✅ 天然不存在 | ✅ Redis 互斥锁 | ✅ 随机 TTL + 双层缓存 |
| 空间单条查询 | ❌ 待修复 | ⚠️ 低风险未加锁 | ✅ 主动清理分散 |

> 待办：空间单条查询缺少空值缓存，存在穿透风险，修复方式与图片单条查询一致。
