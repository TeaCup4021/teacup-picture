## 评估「改库后发消息修改各实例缓存」（回到双写 + 广播）

陈同学提出第四种替代方案。未改动任何代码，纯讲解与对账。

### 结论框架（可复用，后续同类提问直接套）

- **推送式 vs 拉取式**：推送式把正确性押在「消息一定送到」上，任一步失败（进程崩／队列抖／实例漏收／消息乱序）都留下**永久脏值且无自愈路径**；拉取式把正确性押在「读时校验」上，通知丢失只是少清一次内存，**不可能读到错值**。
- **金句（可直接作为面试答案）：广播是优化，不是正确性。** 广播挂掉只让内存占用与回源次数上升，不会让任何请求读到错值。

### 三个失败点（按严重程度）

1. **写库与发消息无法原子，且两种顺序都救不了**
   - 先写库后发消息 → 发失败则该数据脏到 TTL 过期（详情 180 秒／列表 60 秒）；而项目文档给失效事件定的目标是 **p99 < 5 秒**，属违约。
   - 先发消息后写库 → 实例先清缓存，有请求回源读到**未提交的旧值**并填回，随后事务才提交 → 脏且**不自愈**。
   - 唯一出路：把「要发消息」与业务数据放进同一事务（即发件箱）。
2. **「修改」弱于「删除」，差异在数学性质**：**删除幂等且可交换**（删两次＝删一次，与顺序无关，之后回源必得当前值，各实例收敛到同一真相）；**写入某个值不是**——乱序后停在旧值且无人纠正；且写的是「消息产生那一刻的值」，消息延迟即等于写入历史值。呼应 cache aside 经典建议「写后删除而非更新」。
3. **广播天然会漏且漏了无人知道**（实例重启、网络分区、消费位点丢失）。本地窗口短（10 秒）可自愈，共享缓存那份脏 180 秒。

### 关键论证（本轮最有价值的一条）

思想实验：**即便消息队列不丢不重、永不故障，乱序仍会留下永久脏值。** 要解决乱序必须在消息里带递增序号、消费端只接受更新的那个——**那就是版本号**。

→ 结论：为了让该方案正确，最终必然把版本号重新发明一遍；不如一开始就把它放在读取路径上（读时校验不需要维护任何送达保证）。

## 图片分片上传与断点续传（讲解 + 方案对比）

未改动任何代码。两轮：先按项目实现讲解链路，再对账外部设计方案。

### 项目实现事实（回代码核对过的）

- 前端按 8 MiB 阈值分流：以下走单请求表单上传，以上走分片（`m1-api.ts:143-149`）。
- **片大小被服务端硬校验为 5 MiB**，理由不是调优而是对象存储**服务端合并**的规范下限（除最后一片外每片不得小于 5 MiB）。单图上限 20 MB ⇒ **最多 4 片**，分片收益仅为弱网重传。
- 分片是**独立普通对象**（前缀 + 片序号），不是原生分片协议；完成时用服务端合并拼成中间对象，再**当成普通输入流重走一遍标准校验与缩略图流程**（`MinioPictureStorage.java:257-282`）。
- 断点续传 = **客户端会话缓存（记住会话标识，键为 文件名+大小+修改时间）+ 服务端两张表（权威进度）**；恢复时先查服务端进度再跳过已传片。取消 = 删会话，属"放弃"而非"暂停"。
- 三层防线：分片级幂等（前置查询 + 会话序号唯一键）、分片内容摘要比对（边写边算）、完成前校验片数齐全且序号连续。
- 过期清理走定时任务（每小时），清理时删分片对象并置会话为已过期。

### 项目实现的真实缺陷（面试会被挑，已当面说明）

1. **会话行锁方法定义了却零调用**（`PictureUploadSessionMapper.java:11-12`）→ 两个完成请求并发时会双写图片记录、空间用量加两次。
2. 同一片并发上传：先查后插之间有空档，撞唯一键会返回服务端错误而非"分片已存在"的冲突错误。
3. 合并只按序号定位对象，**分片表里的摘要与大小未参与校验** → 对象被外部清理时要到合并才暴露。
4. 会话表预留的整文件摘要字段**全链路未落地**（前端不传、服务端不校验）。
5. **文档滞后**：`product-prd.md:227` 与 `ui-design/pages/upload.md:25` 仍写"不提供断点续传"，与实现矛盾。引用 PRD 会自相矛盾。

### 方案对比结论（外部方案 vs 当前实现）

外部方案要点：控制面走后端、数据面走存储（前端凭预签名直传）、原生分片协议、Redis 存进度与限流、支持秒传。

- **第一道坎是架构规约而非技术**：`picture-storage.md:9-11` 与 `AGENTS.md` 明令禁止前端拼接存储地址、接收凭据或预签名地址、浏览器直连对象存储。理由链是**私有桶 + 读取需过权限 + 公开需审核**；预签名地址签发后有效期内谁拿到谁能写，**写入那一刻服务端无法校验内容**，等于未审核内容先落存储。该方案在本项目**不成立**。
- **量化判据**：当前实现下后端参与搬运约 **80 MB 每张 20 MB 图**（上行 20 + 分片写入 20 + 读回 20 + 正式原图 20）；外部方案约 **40 MB**（缩略图必须后端生成，读回与写出两段谁也省不掉）。即**约 2 倍差距**。按 1 Gbps 有效 100 MB/s 计：日万张多搬 400 GB ≈ 1.1 小时满载，**不构成瓶颈**；若单图上限提到 500 MB，日万张需多搬约 10 TB ≈ 27 小时，**物理不可行**。→ 结论：**方案优劣由单文件上限决定**，20 MB 量级留当前实现，百 MB 量级必须换方案（且要先推翻架构规约）。
- 当前实现真正更优的三点：完成时**先合并到临时区、校验通过才写正式对象**（校验失败正式目录零污染）；分片是普通对象因而**中断残留可见、可审计**（原生未完成分片是存储内不可见占位数据，只能靠定时任务回收）；抽象层只有 4 个方法，**换存储实现不泄漏原生分片能力**。
- 外部方案值得抄的三样：**分片并发**（当前串行；前置条件是先修并发写同一片的唯一键冲突）、**完成前用已落库摘要与大小交叉校验**、**上传侧限流**（当前完全没有，AI 任务链路已有并发许可与速率令牌的现成模式可迁移）。
- 外部方案自身的四处问题（已当面指出）：数据库口径不统一（架构图写"PostgreSQL/MySQL"，建表语句是 MySQL 语法）；**分片凭据存放有真空**（既说 Redis 不能作唯一事实来源，又写"Redis / DB 记录进度 + ETag"，若凭据只在 Redis，重启淘汰后完成请求凑不齐列表、任务作废）；**秒传未谈引用计数**（按"用户 + 内容摘要"查重后秒传会让两条图片记录指向同一对象，删其一若直接删对象则另一条立刻变坏）；**5 MiB 只给数字不给约束**（文中还混用 5 MB 与 5242880）。

## 追加：抛开规约做「数据面路径」通用对比

他明确要求舍弃项目约束，只谈前端直传 vs 后端代理的通用优劣。本轮无代码改动。

### 核心提炼（可复用的立论）

**两条路径的全部优劣来自同一个取舍：内容校验发生在「字节落存储之前」还是「之后」。**

- 直传侧的全部代价（凭证有效期即权限、内容不可控、后置校验与回删、产生「已落存储但未校验」的中间状态、依赖存储原生能力）**都源自"先落存储后校验"**。
- 代理侧的全部代价（后端字节量翻倍、线程被传输时长占住、临时磁盘多一次写、扩容要扩带宽）**都源自"字节先过后端"**。

→ 所以选型的真正问法不是"哪个性能好"，而是：**能否接受未经校验的内容先落进自己的存储？** 由三个下游问题裁决：①存储里允许存在未校验内容吗；②有没有能力做异步后置校验并保证垃圾被回收；③读路径是否也直连（若读仍走后端，则写作两套路径、权限模型翻倍，收益只兑现一半）。

### 三个可算判据（本轮最有价值）

1. **后端字节放大倍数 = (2 + P) / P**，P 为「后置处理必须搬运的字节倍数」。P=2（读回 + 写正式对象）→ 2 倍；**P=0（上传即成品，不做派生）→ 直传对后端是零字节，优势无穷大**。即 P 越大直传优势越小。
2. **并发容量的决定因素变了**：代理下容量 = 线程数 ÷ 单文件传输时长（200 线程、单文件 16 s → 约 12.5 个/秒，CPU 全程空闲）；直传下容量 = 线程数 ÷ 控制请求时长（毫秒级），差 2~3 个数量级。
3. **带宽临界式：2·S·N ≤ 0.5 × 86400 × B**（S 单文件 MB、N 张/日、B 后端有效带宽 MB/s，留 50% 余量）。取 B=100 → S·N ≤ 2.16 TB/日：单文件 20 MB 可撑约 10.8 万张/日；200 MB 约 1.08 万张/日；500 MB 只剩约 4300 张/日。

### 三个易被忽略的点

- **直传只省数据面，控制面往返反而变多**：4 片场景下直传 = 4 次取凭证 + 4 次传 + 1 次完成 = 9 次往返，代理 = 5 次。故高并发分片应设计成「一次取全部凭证」。
- **代理能在写入的同一遍里算出内容摘要，直传算不到**（要么信任客户端上报，要么从存储读回再算一遍，等于又一遍全量 IO）。这是能力差异而非性能差异。
- **凭证过期是直传方案的专属故障**：重试逻辑必须能识别「凭证失效 → 重新取凭证」，否则长上传会在最后阶段失败。

## 追加：空间额度校验的审计与改造方案（未改动代码）

他提出「只要上传的图片加上已用空间不超过规定空间就可以，可以怎么改」。先审计出三个事实：

### 审计事实

1. **该语义项目里已经这么判**：`M1Service.java:130`（建会话）与 `:472`（保存图片）均为 `totalSize + 本次 > maxSize → 拒绝`。
2. **判断与扣减分离，中间是敞口**：判断读旧值，扣减在 `:484` 才执行，两处之间无锁、无预留、无条件。
3. **递增点 4 处，带校验仅 1 处**：`M1Service:484`（有校验，覆盖分片完成与 AI 生成）、`M3Service:319`（另存图片，**无校验**，且 `M3Service:404` 已有现成的容量校验方法却只被"应用版本/上传新版本"调用）、`PictureServiceImpl:208`（旧接口 `/api/picture` 上传，**无校验**）。

### 关键区分（易误判）

`setSql("totalSize = totalSize + N")` 是**数据库端原子自增，不会丢更新**——10 个并发会话结果是 200 而非 20。**错的不是数值，是"超额被允许"**：每一行数据都正确，被破坏的只是规则本身。这一点决定了该缺陷很难被数据核对发现。

### 四档改造方案

- **档 1（修竞态）**：把判断合并进更新语句，WHERE 带上限条件，看影响行数是否为 0。
  `UPDATE space SET totalSize = totalSize + N, totalCount = totalCount + 1 WHERE id = ? AND totalSize + N <= maxSize AND totalCount + 1 <= maxCount`
  靠行锁天然串行化，无需改表、无需显式加锁。需用 `spaceMapper.update(...)` 取 `int` 影响行数（`ServiceImpl.update` 只返回 boolean，判断不了 0 行）。
- **档 2（加预留）**：`ALTER TABLE space ADD COLUMN reservedSize BIGINT NOT NULL DEFAULT 0`（MySQL 8 走 INSTANT ADD COLUMN，秒级不锁表），语义变为 `totalSize + reservedSize + 本次 <= maxSize`。建会话预留、完成扣减、取消/过期释放。**一个重要性质：当前"声明总大小"是强约束的（每片大小精确匹配、总片数由声明算出），所以预留与实际用量恒等，不需要处理差额**——改造时必须保住这条，否则预留会泄漏。
- **档 3（收口）**：4 个递增点 + 3 个递减点收敛到单一额度入口（预留/释放/扣减/结算四个方法），消灭"新增上传路径忘校验"这一错误类型。
- **档 0（只去掉数量维度）**：需提醒——数量不是冗余维度。20 MB 上限下 10 GB 空间可存 500 张 20 MB 大图，或 10 万张 100 KB 小图，后者的元数据量、列表页性能、缩略图对象数相差 200 倍。

## AI 生图链路走读：状态机 / 重试 / 租约 / 异步化设计（未改代码）

### 源码核对出的事实

- `ai_task.status` 是自由字符串，合法值靠服务层白名单约束：**queued / running / succeeded / failed / cancelled，共 5 个**（无 pending）。终态判定分散**两处**，加状态必须同时改。
- 可重试失败只有三类码：上游 429 限流、408/504 超时、5xx。退避 5s / 30s / 120s 由**三档 TTL 队列 + 死信交换机**实现延迟投递，单任务最多 4 次提交、退避累计 155s。
- **客户端读超时（120000 ms）抛出的网络异常不可重试**，落 failed 时失败码被改写成「结果未知」——因为请求可能已到达上游并计费，重试有重复计费风险。这是刻意的保守取舍。
- 租约：租期 300s、续租周期 90s，构造器强制校验 `续租×3 ≤ 租期`（不满足启动即失败）。续租器是**独立调度线程**——这是机制成立的前提，不是实现细节。恢复扫描每 30s、每轮 LIMIT 50，回收动作**不碰额度**。
- **栅栏令牌能防「重复落库」，防不了「重复调用上游」**——这两件事必须在设计时分开谈。
- 并发限流：全局并发许可 12、速率 60 次/分钟、突发 4。按响应 120s 算吞吐上限 6 次/分钟，**当前并发先到顶，速率令牌是松的**。

### 关键发现：异步轮询的地基是孤桩

- `V24__add_ai_task_poll_count.sql` 已给 `ai_task` 加 `pollCount` 列，注释明确「提交次数与轮询次数必须分开计数」，但 `AiTask` 实体**没有该字段**、Java 代码**零引用**。
- `AiProvider` 接口只有同步 `execute()`；`AiProviderResult.providerTaskId` 实际填的是同步响应体 id，**不是异步任务句柄**。

### 本轮我说错了一处（已当面认账，勿再犯）

为了论证「若按 120s 回收会误杀」，我编了「上游第 125 秒才吐回图片」的场景。**该场景在当前配置下不可能发生**——120s 的客户端读超时会先掐断连接，老执行者等不到第 125 秒。

- 错误性质：**用「当前配置下不可能发生」的场景，去论证「另一个假设方案」的问题**，双重假设叠加，数字就编飞了。
- 教训：**举反例前必须先确认该反例在当前实现下成立**；若必须用假设链条，要显式标注是假设，且只能叠一层。
- 修正后的正确结论：超时那一刻「成功还是失败」已永久不可知，只能二选一——不重试（丢图，损失 1 次调用）或重试（可能付 2 次钱）。**这个损失是超时本身的代价，与「多少秒回收任务」无关。**

### 用户质疑「300s + 续租是扯淡」，论证过程

他的主张：任务 120s 内没返回就 failed，续后面的约没用；不如直接设「最大 300s 未完成即判失败」。

回应与结论：

- **承认**：在该项目当前参数下，他要的「一次性死线」与「租约 + 续租」**结果等价**，因为单次执行被 120s 客户端超时锁死，永远碰不到 300s。
- **核心差异**：租约的倒计时是**滚动的**（从最后一次续租起算），一次性死线是**绝对的**（从抢占起算）。差别在「从哪一刻算起」，不在「300 秒长不长」。
- **他方案里的三处错误**：①「检查连接是否存活」查的是**上游**，租约管的是**我方实例**，两者在协议栈两头，中间无推导关系；②租约过期后应**重投**而非判死（滚动重启这类故障不该让用户买单，且重投受次数上限约束不会失控）；③续租**绝不能**挂在业务线程上。
- **反例（有效）**：若上游超时从 120s 调到 600s，一次性死线会让**每个正常任务都被误杀**，而租约方案一行不用改。→ 他的方案错在把「执行能跑多久」和「什么时候判死」压进同一个数字，是**隐性耦合**，参数一改就断且不报错。
- 成本量化：续租 = 每 90s 一条批量 UPDATE，影响行数 ≤ 12，折算 60 次/小时；一个 120s 就结束的任务，续租器平均只触发 0~1 次。**开销近乎为零，收益是参数解耦。**

### 提出的设计方案（仅讨论，未实施）

用户诉求：给生图链路加机制，解决「生图慢但线程提前结束导致费用超支」。

**病因诊断（本轮最有价值的立论）**：根因不是缺租约，是**任务句柄寄存在了 TCP 连接上**。同步模式下句柄 = 那条连接，线程一超时/被 kill，句柄随之湮灭，我方对仍在烧钱的上游任务**失去一切控制手段**。**同步模式下没有句柄，任何租约都救不了。**

→ 解法：**提交与等待分离，把句柄持久化进数据库**。

| | 同步（当前） | 异步（建议） |
| --- | --- | --- |
| 句柄存在哪 | TCP 连接 | 数据库字段 |
| 线程/实例死了 | 句柄消失 | 换个实例接手轮询 |
| 能否叫停上游 | 不能 | 能（调取消接口） |
| 用户取消的后果 | 认损 | 止损 |

设计要点：

- `AiProvider` 拆三接口：`submit`（秒级返回，只拿上游任务 ID）/ `poll`（幂等查询）/ `cancel`（止损）。
- 状态机 **5 → 6**，新增 `submitted`（已提交待查询）。终态判定两处要同步改。
- **关键语义**：租约过期后必须回 `submitted` 而非 `queued`——回 queued 意味着**重新提交给上游**，会重复计费；回 submitted 只是换个实例继续轮询。
- 计数分离：`attemptCount` 只管提交（上限 4 不动），`pollCount` 管轮询、独立上限。**必改点：`AiTask` 实体补 `pollCount` 字段**，否则 V24 那列永远是死的。
- 租约的正确位置是「**轮询权**」（轮询幂等，重叠无损失），不是「提交权」（提交重叠 = 重复计费）。
- 轮询由**现有三档延迟队列**驱动，退避语义天然吻合，基础设施零新增。
- **取消顺序：必须先调上游取消，再落终态。** 反过来等于「状态已终了而钱还在烧」。
- 用户上一轮说的「最大 300s 判失败」在此**才是对的**——它管的是「上游任务还值不值得等」，与「执行者存活」无关，两个判据各干一件事。
- 额外收益：线程不再被等待时长占住，瓶颈从「线程与许可」移到「上游配额」，吞吐从约 6 次/分钟的量级解放。
- **未验证的前置条件**：上游是否支持异步提交 + 查询 + 取消。若不支持，整盘不成立，只能退回「调大超时 + 记录损失」。**第一步要确认的是这个，不是写代码。**
- 落地顺序建议：①补 `pollCount` 到实体（零风险）→ ②抽象三接口但保留同步适配器（行为不变，可回滚）→ ③确认上游后实现异步 provider 与 `submitted` 状态 → ④接通取消。

## 追加：上游是否支持异步（查证结果）

### 已确认的事实

- 项目端点是 `POST {base}/v1/images/generations`（`OpenAiImagesProvider.generationsUrl`），**OpenAI Images API 的同步端点**；模型为 **gpt-image-2**（见 `docker/README.md:58`，要求 key 所属分组暴露该模型）。
- **OpenAI 官方 Images API 本身没有异步／查询／取消。** 开发者社区有原话抱怨：「the lack of result tracking……a huge number of money write-offs without the ability to get the result」——**用户担心的「费用超支」在官方 API 层面就是无解**，是全球开发者的共同投诉。
- 官方唯一的异步途径是 **Responses API + `background=true` + `store=true`**，返回 `response.id` 可 `retrieve` 查询；但这是另一套 API，不是 Images API。
- 聚合/中转商确有异步实现，形态各异：Atlas Cloud 走独立预测端点（`POST /model/generateImage` → prediction_id → `GET /model/prediction/{id}` 轮询，状态 created/processing/completed/failed，有 `enable_sync_mode` 开关且默认异步）；Ace Data Cloud 靠 **`callback_url` 触发**才产生可查询任务，再查 Tasks API，**且明确「Tasks API 轮询免费，只有生成请求收费」**。

### 无法确认的部分

`claudenb.com` **在本机完全不可达**：直连 DNS 解析失败（curl exit 6），经本地代理返回 502，搜索引擎无任何收录。→ 无法判断是域名失效、被墙，还是仅此网络环境不通。**不能替用户假设。**

从配置能推出的**弱判断**：`docker/README.md` 要求「key 所属**分组**暴露 gpt-image-2」——「分组」是 new-api / one-api 类中转系统的典型用语，这类系统绝大多数是**同步透传**，不提供任务查询端点。→ **大概率不支持异步，但需用户确认。**

1. 服务商控制台／文档里搜「异步 / 任务 / 回调 / prediction」字样。

## 追加：用户确认上游不支持异步；查 stream 支持情况

用户回复「不支持」。随后问「能否在快到 120s 时检测连接是否存活，存活就延长时间」——**该方案不成立，已当面否掉**：

- 等待响应期间 TCP **没有任何周期性信号**，唯一的状态变化是「收到数据」或「连接断开」。静默期里「连接存活」永远返回真，**判据不携带信息，等于没检测**。
- 更糟：连接持续「存活」→ 无限延长 → **超时机制被取消** → 12 个并发许可被永久卡死任务吃光 → **服务彻底停摆**。
- 金句：**超时的价值恰恰在于「无法判断时强制做决定」**；给「无法判断」补一个不含信息的判断，等于取消超时。
- 正确方向：不是「我方探测连接」，而是「**让上游持续发数据，读超时自动被重置**」。

**关键机制事实**：读超时的语义是「**两次数据到达之间的间隔**」，不是「整个请求的总时长」。所以只要上游持续发一段段数据，总时长 300 秒也不会超时——**超时延长在流式模式下是免费的**。

## 实测结果（用他的 key 直连 wawapii 完成，key 已外泄需轮换）

本机网络起初全部 000，重试后走代理/绕代理均可连通（站点在 Cloudflare 后）。key 所属分组只暴露 3 个模型：`gpt-image-2`、`gpt-image-2.5-flare`、`gpt-image-2.5-sunburst`。

### 结论一：异步任务端点不存在

- **对照组校准很重要**：该平台对「存在的端点但方法不对」返回 **404**（`/v1/models` GET=200 / POST=404），对「不存在的路径」也返回 404。所以**不能只看状态码，要用 POST 带空 body 判断**：`/v1/chat/completions` POST=400（存在，缺参数）vs 不存在路径 POST=404。
- `/v1/tasks/submit`、`/v1/tasks/status`、`/v1/tasks`、`/v1/task`、`/v1/images/tasks`、`/v1/images/generations/probe` —— **全部 POST=404**。
- **踩坑记录**：`/mj/task/probe`、`/mj/submit/imagine` 返回 **200，但内容是前端 SPA 的 HTML**（`<!doctype html>`），属**假阳性**——平台前端为 `/mj/*` 配了页面路由。凡是返回 HTML 的 200 都是页面，不是 API。
- `/v1/responses` POST=400（存在，与大模型对话用）。

### 结论二：`stream: true` 有格式、无流式语义

| 项 | 实测 |
| --- | --- |
| 稳定性 | 带 stream 共 5 次：**4 次 `text/event-stream`，1 次 `application/json`**（会退化，不可依赖） |
| 事件结构 | 仅 **2 个 data 行**：`image_generation.completed`（含完整 b64_json）+ `[DONE]` |
| partial | **传了 `partial_images:2` 但没有任何 partial 事件**，参数未生效 |
| **首字节 vs 总耗时** | **39.2s vs 42.4s** —— 几乎同时 |

→ **判定：图片先在服务端完整生成，再用 SSE 格式一次性吐出。** 是格式包装，**不是渐进推送**。

**对超时问题无效**：读超时算的是「两次数据之间的间隔」，而这里**只有一次数据**（全在最后 3 秒内到达）。上游若要 200 秒，首字节就是 200 秒，读超时照样在 120 秒触发。

### 结论三：附带的高价值数据

- **响应时间分布**（5 次采样）：21.6 / 25.5 / 34.0 / 35.7 / 42.4 秒。p50≈34s，max=42.4s，**离 120 秒上限余量很大**。
- 空 body 请求返回的错误原文：`{"error":{"message":"Image request could not be completed. Do not automatically regenerate; check usage or contact support.","type":"image_request_error"}}` —— **平台自己明确警告「不要自动重生成」**，反向印证了本项目「网络异常不重试」的设计方向正确。

### 方法论（可复用）

- **空 body POST 探端点存在性**比状态码可靠：存在→400/401/405，不存在→404。
- **判断真假流式看 `time_starttransfer` vs `time_total`**：真流式首字节远早于总耗时；两者接近=服务端缓冲后一次性返回。
- **Git Bash 下 `-o /dev/null` 会让 curl 报错 23 并导致字节数与首字节时间测量失真**，必须落盘到真实文件再测量。
- 测量流内容时剔除 b64 字段再统计事件类型，否则日志会被几 MB 的 base64 撑爆。

### 最终方案判据

- 异步化方案**作废**（无端点）；stream 路线**作废**（无流式语义）。
- 只剩 Plan B：**当前不做任何改动**——120 秒超时相对 42 秒实测最大值余量充足。**首选动作是补响应时间埋点，持续观测 p99 与 `provider_outcome_unknown` 的数量**，用数据决定是否调超时，而不是拍脑袋改。
- 若要异步/取消能力，唯一出路是**换上游**。

## 「预占是在 queued 时还是 running 时？」——核对结论：**queued**

**答案**：`AiTaskService.create()` 里 `reserveQuota(...)`（L112）在 `task.setStatus("queued")` + `insert`（L119–121）**之前**执行。worker 抢到任务转 running 的整条链路（`AiTaskRunner.markRunning` → `claimForExecution`）**一次额度读写都没有**。

**预占的原子过程**（`reserveQuota` L338–343）：`ensureRow`（INSERT IGNORE 建行）→ `selectForUpdate`（`ai_quota_usage` 行级排他锁）→ 判 `usedCount + reservedCount + cost > limit` 则 409 → `reservedCount += cost`。与 `quotaView` 的 `remaining = limit - used - reserved` 同口径。

**为什么必须占在 queued**：排队是有长度的。若等 running 才占，用户在 queued 期间可无限提交、每笔都过校验；worker 抢到时才发现超限，要么批量拒绝（白等）要么放行（超限）。预占把「校验 + 受理」绑在同一事务，队列长度天然被额度上限截断。

**两把尺子（本轮最值得记的区分）**：
- **占不占**看「是否已被受理」= 创建成功。
- **退不退**看「上游是否已开始调用」= `invocationStarted`，**不看状态**。
- 重试路径 `retry()` 把任务退回 queued，但 `invocationStarted` 保持 1 → 此时取消走 `cancelled_after_invocation`，**不退**（上游成本已产生）。所以 L146 的 `"queued".equals(status) && !invocationStarted` 两个条件都必要；只看状态会把重试中的任务错退。

**settle 不在抢占那一刻**：整个 running 期间额度一直挂在 `reservedCount`。只有结果落库成功时 `AiTaskRunner.complete` 才调 `settleQuota`（reserved−cost、used+cost）。语义切分：`used` = 已出图，`reserved` = 已受理未出图。

**别与上传链路混**：AI 任务走 `AiQuotaUsageMapper`（调用次数），不是 `SpaceMapper.reserve/tryConsume`（存储字节）。两套独立账本，同名不同表。

## 「什么时候会被置为 queued？」——全量核对：运行时只有三个写入点

grep `src/main` 下 `"queued"` 字面量，写状态的只有三处：

| # | 位置 | 触发判据 | `nextAttemptAt` |
| --- | --- | --- | --- |
| ① | `AiTaskService.create()` L119 | 幂等键未命中 + 模型/参数校验通过 + 额度预占成功 | 立即（now） |
| ② | `AiTaskService.retry()` L236 | `ownedBy` 三者匹配 **且** 错误码可重试 **且** `attemptCount < maxAttempts` | `now + 5/30/120 秒` |
| ③ | `AiTaskOutboxService.recoverExpiredTask()` L44 | `status=running` 且（`leaseUntil <= now`，或 legacy 无租约且 `startTime <= now−15min`），且行锁抢占成功 | 立即（now） |

可重试错误码白名单（`AiTaskRunner.retryable`）：`provider_rate_limited` / `provider_timeout` / `provider_http_5xx`。其余一律直接 `fail` 终态化。重试延迟阶梯（`retryDelay`）：1 次 → 5 秒、2 次 → 30 秒、≥3 次 → 120 秒，与 `maxAttempts=4` 配套。

**最反直觉的一条**：③ 不是「running 回退到 queued 才能被抢」。`claimForExecution` 的 WHERE 本身就是 `(status='queued' AND nextAttemptAt<=now) OR (status='running' AND leaseUntil<=now)`——**租约过期的 running 任务可以被下一个 worker 直接抢走并原地改写成 running**，不必经过 queued。所以 ③ 的真实职责是「往发件箱补一条投递消息」（`enqueue`），状态改写只是顺带把 `workerId` / `leaseUntil` 清干净。

另：`V20__add_ai_task_dispatch.sql` 里有数据回填（给存量 queued 补 `nextAttemptAt`、给存量 running 补 `leaseUntil`、给存量 queued 补发件箱记录），属一次性迁移不算运行时路径。

**三条路径的共同点**：都不重新占额度——预占在 ① 就已发生，②③ 只改状态字段（`workerId` / `leaseUntil` / `nextAttemptAt` / `failureCode`），不碰 `ai_quota_usage`。

## 「额度什么时候返还？」——全量核对 + 修正本文档上文一处过期数字

所有归还都收敛到 `finalizeQuota(task, refund=true, reason)` → `releaseReservation`（`reservedCount −= quotaCost`），共 **5 个入口**：

| 入口 | 位置 | 判据 | 时延 |
| --- | --- | --- | --- |
| 取消（未发起调用） | `cancel()` L150 | 状态 ∈ {queued, running} **且** `invocationStarted != 1` | 秒级 |
| 执行失败终态化 | `fail()` L166 | `ownedBy` 三者匹配且错误码不可重试（或重试已用尽由 Runner 转 exhaust） | 秒级 |
| 重试耗尽 | `exhaust()` L187 | 抢占失败时 `status=queued` 且 `attemptCount >= maxAttempts(4)` | 秒级 |
| 死信回收 | `AiTaskDlqService` → `exhaust(dead_letter)` | 消息被 `basicReject(requeue=false)` 或队列 rejectPublish 溢出进 DLQ | 秒级（DLQ 单并发，积压时排队） |
| 对账兜底 | `reconcile()` L207 / L225 | 见下 | ≤ 21 分钟 |

**不返还（结算 `settleQuota`：reserved → used）的 3 个入口**：成功出图 `complete()` L199；取消但 `invocationStarted == 1`（L152）；对账补结算 L205。

**对账的两条分支**：
- L203–210 `terminal(status)` 分支（`release_missing` / `settled_missing`）**实践中近乎不可达**——终态写入与额度流转在同一事务内，不存在「已终态但额度未流转」的状态。
- L219–227 僵尸分支才是真正在干活的：非终态 + （running 无租约或租约已过期）+ `createTime < now − zombieAgeMinutes`。

**⚠️ 修正上文数字**：本文档前面写的「周期对账 6 小时 10 分内」是旧门槛（360 分钟）时期的值。现配置为 `reconcile-zombie-age-minutes: 11` + `reconcile-millis: 600000`（10 分钟），故对账口径的最坏时延 = **11 + 10 = 21 分钟**；`reconcile-initial-delay-millis: 60000` 只在启动后生效一次。

**时区口径的连带结论**：`releaseReservation` 走 `lockedUsage(task)` → `usageDate(task)`，而 `usageDate` 把 `createTime` 按 UTC 解释再转上海时区。所以跨日回收的预占会还到**任务创建那一天**的账行上，不是回收执行日。对 AI 配额（按日分行、每日满额）无实质影响（今天那行压根没被占），但做总量型额度时这个口径会真影响用户——不能照搬。

**与空间额度的对比**：`SpaceMapper.releaseReservation` 是另一套（管字节、不日切），恢复只靠上传会话过期清理（24 小时 + 每小时一轮 ≈ 25 小时），没有对账兜底这类快速通道。
