## 10:30 归纳同步提交段「防什么」（面试口径）

用户追问这一段的存在理由。归纳为**两类承诺**，这个两分法是可复用的面试答法：

- **第一类「能不能做」**（可拒绝的判定，失败可干净回滚）——额度是否够、模型是否支持该类型/比例/清晰度、参考图是否符合模型能力、原图/参考图归属是否本人。**必须在同步段**，否则用户白等一轮才被告知做不了。
- **第二类「答应了就一定做」**（过了提交点就不可撤回）——任务行与事件行同事务落库。**这是 outbox 模式真正防的东西**：库写入与消息投递拆开的两个失败方向是「任务永挂」（先插库、消息发失败）和「消息白发」（先发消息、事务未提交，消费者查不到任务）。同事务消除竞态。

**具体防的五件事**（面试可直接点名）：① 无效等待 ② 额度超卖（并发预占必须加锁，异步预占会让 200 个任务全部提交成功后才在执行时发现额度不够）③ 任务黑洞 ④ 消息空转 ⑤ 幂等失效（重复提交变两条）。

**主动交代的代价**：单用户提交被 `user` 行锁串行化，事务内 6 条语句 + 2 把行锁（先用户行、后额度行）。单用户提交上限 = 1 ÷ 事务耗时，按 5ms 估约 200 次/秒，实际用户达不到——**这是主动选择的代价，不是缺陷**。

**边界（同步段不保证什么，避免过度承诺）**：不保证 AI 调用成功（靠退避重试）、不保证不重复执行（靠状态机 + 租约 + 栅栏令牌）、不保证额度不漏（靠对账任务）。

## 10:35 用户质疑「user 行锁没意义」——核对后的精确结论

用户直接质疑 `userMapper.lockById`（`UserMapper:15`，`SELECT id FROM user WHERE id=? FOR UPDATE`）存在的意义。**结论：用户质疑基本成立，但需补一个判据。**

**核对到的关键事实（与上一轮的表述有三处要收紧）**：
1. `ai_quota_usage` 的行键是 `(userId, usageDate, taskType)`（`AiQuotaUsageMapper:12/16`）→ **生成与扩图是两把互不相干的锁**。
2. `reserveQuota`（`:338-343`）**自己就已经在锁额度行**（`ensureRow` + `selectForUpdate` + 判断 + 更新），额度超卖与 user 锁无关。
3. 唯一索引是 `uk_ai_task_user_idempotency(userId, idempotencyKey)`（`V6:7`）—— **不含 taskType**。

**去掉 user 锁的完整推演**（已画对照图）：
- A、B 并发同键同内容提交 → 都查幂等键未命中 → A 锁额度行、预占、插任务 → A 提交 → **B 拿到额度行锁**（不是 user 锁）→ B 预占、插任务 → **撞唯一索引** → 整个事务回滚（含那次多余预占）→ **用户看到 500**。
- **数据完全正确**：任务只有一条、额度只扣一次（事务原子性保证）。所以 **user 锁在数据正确性维度上零贡献**，这是用户说对的部分。
- 它的真实作用：把并发重复提交的第二个请求从「唯一键冲突 500」变成「查到已有任务 → 200」。**是语义层，不是正确性层。**

**一个必须讲对的机制细节**：B 的幂等查询是**快照读**（普通 SELECT，RR 隔离级），不会被 A 的额度行锁阻塞、也不会看到 A 未提交的任务，所以 B 必然查不到——这正是为什么要靠唯一索引兜底。

**替代方案及其坑**：捕获 `DuplicateKeyException` 后重查幂等键。坑是 **Spring 事务里捕获唯一键冲突后事务已被标记 rollback-only**，同一事务内继续查库抛 `UnexpectedRollbackException`；要正确实现必须把 `create` 拆成「外层非事务捕获重查 + 内层保留 @Transactional」。**当前选择行锁 = 用一次锁换业务代码简洁，是合理权衡，不是必需也不是没意义。**

**升格为必需的条件（这轮最值钱的判据）**：**锁的粒度必须覆盖不变量（invariant）的作用域。**
- 现在：额度不变量作用域 = `(用户, 日期, 类型)`，恰好等于额度锁粒度 → user 锁只落在语义层。
- 若产品把额度改成「生成 + 扩图共享一个总上限」：两个请求锁**不同的额度行**、互不阻塞，各自读到相同总量、各自判断未超限 → **超卖**，额度行锁失效，**必须靠 user 级锁串行化 → user 锁从"语义工具"升格为"正确性基石"**。

**面试口径**：被问「为什么锁用户表」不要答"防并发重复提交"（必被追问"唯一索引不是已经防了"）。答：它不防数据重复（唯一索引兜底，无锁时数据也不会坏、预占随事务回滚），防的是**语义退化**——并发重复提交的第二个请求不应该拿到唯一键冲突的错误，而应该按幂等语义返回原任务。代价是单用户提交串行化。

## 10:50 唯一索引设计与冲突表现（**含一处上一轮的更正**）

**⚠️ 更正**：上一节我写"无 user 锁时第二个请求拿到 500"——**错**。`V1ExceptionHandler:23-27` 专门有 `@ExceptionHandler(DuplicateKeyException.class)` → **409 / code 40901 / "资源状态冲突"**（该类 `@Order(0)` + `@RestControllerAdvice(basePackages = "...api.v1")`，`M2Controller` 正在此包内）。所以有无 user 锁的真实差异是 **200 返回原任务 vs 409 资源状态冲突**，方向没变（语义退化）但程度比我说的轻。另注意它**不在事务内**（异常已冒泡出 `create`，事务已回滚），所以不存在 rollback-only 问题。

**索引定义（`V6:4-7`）**：
```sql
ALTER TABLE `ai_task`
    ADD COLUMN `idempotencyKey` VARCHAR(128) NULL AFTER `userId`,
    ADD UNIQUE KEY `uk_ai_task_user_idempotency` (`userId`, `idempotencyKey`);
```

**设计意图**：`userId` + `idempotencyKey` 两列，作用域=「这个用户的这一次意图」，用 userId 隔离不同用户的相同键。**故意不含 `taskType`**——加了就等于允许同一用户用同一个键分别提交生成与扩图，违背「一键一意图」；不含它才能让「同键异类型」也落入冲突、逼客户端换键。

**🔴 关键坑：`idempotencyKey` 允许 NULL，而 NULL 不参与唯一约束** → `(5, NULL)` 可插**无限条**；而 `(5, '')` 空串参与约束、只能一条。NULL 的来源是 `V6` 用 `ALTER TABLE` 给已有表加列（NOT NULL 需 DEFAULT，允许 NULL 最省事）——**迁移的副产品，不是刻意设计**。
- **现状无害**：`create:91-92` 的正则 `^[A-Za-z0-9._:-]{8,128}$` 会拦掉 null/空串并 `badRequest`，走 Service 路径插不进 NULL。
- **隐患**：DB 层无强制，任何绕过 `create` 的写入（修复脚本、测试数据、将来的系统自动建任务路径）只要不设 key 就是 NULL，**唯一索引对它完全失效**。属「约束强度依赖应用层」。
- **修法**：`MODIFY COLUMN idempotencyKey VARCHAR(128) NOT NULL DEFAULT ''`，但需先处理历史 NULL 行（否则改完后多条空串互撞）。
- 长度：utf8mb4 下 128×4=512 字节 < COMPACT 行格式的 767 字节上限，无需前缀索引；128 与 Java 正则 `{8,128}` 对齐。

**冲突的四层表现**（已画图）：
1. MySQL：`ERROR 1062 (23000) ER_DUP_ENTRY: Duplicate entry '5-K1' for key 'ai_task.uk_ai_task_user_idempotency'`
2. Java：Spring 异常翻译为 `org.springframework.dao.DuplicateKeyException`
3. HTTP：409 / 40901 / "资源状态冲突"
4. 副作用：失败 INSERT 会消耗自增值，**ID 跳号**

**InnoDB 唯一性检查机制**（保证并发下不可能双写）：插入时先查唯一索引，冲突行**已提交**→立即报 1062；冲突行来自**未提交事务**→当前事务**阻塞**并在该记录上加共享锁等待，对方提交则报 1062、对方回滚则自己插入成功。这是"唯一索引是幂等兜底"的底层保证（非应用层判断）。

**409 有两个来源需区分**：① Service 层 `V1Exception.conflict("Idempotency-Key 已用于其他请求")`（同键**异内容**，`:108`）；② DB 层 `DuplicateKeyException` → 40901（同键同内容的并发）。客户端拿到 409 时**无法区分**——因为异常处理器是通用兜底（对比：`M4Service:114` 邀请冲突、`PersonalSpaceServiceImpl:53` 都在 Service 里 catch 后更精确地处理）。

**`sameRequest` 的归一化细节（`:401-410`，共 10 字段）**：`defaultOption(task.getBackground(),"auto")` 使"显式传 auto"与"未传"等价、`blank(input.sourcePictureId())` 把空串归一成 null、`id(...)` 把 Long 转字符串比——说明考虑过"语义相同但字面不同"的归一化，是加分点。

## 11:00 `idempotencyKey` 是什么 / 怎么产生（**发现前端实现违背自己的契约**）

**两个标识的可信度是相反的**：`userId` 由服务端在登录时签发、经 HttpOnly Cookie 传输、由 `auth.requireUser()` 解出（客户端无法伪造）；`idempotencyKey` **完全由客户端生成并自供**，服务端只校验格式，不校验来源与新鲜度。

**生成与传输链路（全部核实）**：
- 生成点：`frontend/src/widgets/ai-create/ai-create.tsx:57-61` 的 `newIdempotencyKey()` = `globalThis.crypto?.randomUUID?.() ?? \`ai-${Date.now()}-${Math.random().toString(16).slice(2)}\``。降级方案里用到的 `-` 恰好落在服务端正则白名单内。
- 传输位置：**HTTP Header `Idempotency-Key`，不在请求体里**。前端 `features/ai/api/ai-api.ts:41` 显式 `const { idempotencyKey, ...body } = input;` 把它从 body 摘出来单独放 header（`types.ts:76` 里它是 `CreateAiTaskInput` 的必填字段，仅用于调用便利）。
- 服务端接收：`M2Controller:42` `@RequestHeader(value="Idempotency-Key", required=false)` → `:45-47` 空则 `badRequest`；`AiTaskService:91-92` trim 后过正则 `^[A-Za-z0-9._:-]{8,128}$`（`:44`），不匹配 `badRequest`。
- 契约：`docs/openapi/m2.yaml:38-47`（header `required: true`，含我上一轮补的语义描述）。

**🔴 新发现的真实缺陷（前端，未修）**：`newIdempotencyKey()` 是在 **`submit` 函数体内部**调用的（`ai-create.tsx:141`）→ **每次调用 submit 都生成新键**，即"一次函数调用一个键"而非契约要求的"一次用户意图一个键"。后果：POST 超时（服务端其实已建任务）→ 用户看到错误 → 再点一次 → **新键 → 服务端判定为新意图 → 建第二条任务、扣第二次额度**。唯一索引也挡不住（`(userId, 新键)` 是全新组合）。这恰好是 m2.yaml 契约里写明要防的场景。
- **`loading={create.isPending}`（`:324`）不能替代幂等**：它挡的是"请求飞行期间"的毫秒级重叠点击；幂等要挡的是失败后的秒级~分钟级重试。**保护窗口不重叠。**
- **修法**：key 的生命周期绑定到"一份表单内容"——用 `useRef` 持有，仅在提交成功或表单实质变化时重新生成。

**Header 而非 body 的理由**：语义上它是"关于这次请求的元数据"而非业务字段；工程上业务 DTO 不必知道幂等机制，网关/中间件可统一读取而不解析 body。

**`M2Controller` 写 `required=false` 与 openapi 写 `required: true` 不矛盾**：前者是框架层技巧——若写 `required=true`，Spring 抛 `MissingRequestHeaderException` 走默认错误体，破坏项目统一的 `V1Response`（code/message/requestId）结构；手动抛 `badRequest` 才能保证格式一致。openapi 的 `required: true` 才是面向客户端的契约。

**一个推演值得记**：服务端不校验 key 新鲜度 → 若客户端用**固定常量**当键，用户第二次提交会永远返回第一次那个任务（被幂等吃掉），这正是契约必须写"保留期永久、客户端不得复用历史键"的原因。

**累积待用户确认的改动（已 4 项）**：① outbox 锁释放无效 ② outbox 与 worker 双身份 ③ 实例标识可读化 ④ 前端幂等键生命周期修正。

## 11:05「同一生图请求发两次会怎样」的三态推演（内容相同前提下）

**唯一变量是幂等键**，三种落点（已画图）：

| 条件 | 结果 | 副作用 |
|---|---|---|
| 键相同 + 内容一致（串行） | `:107-109` 命中 → `CreateResult(existing,false)` → `M2Controller:49` → **HTTP 200** | 不新建、不预占、不扣额度、不发消息 |
| 键相同 + 内容有差异 | `:108` → `V1Exception.conflict` → **409** | 一次都没执行 |
| **键不同**（内容一致也不行） | 两次都查不到 → 各建任务 → **HTTP 201 × 2** | **两条任务、扣两次额度、两次 AI 调用、两张图** |
| 键相同 + 并发到达 | 用户行锁串行化 → 后到者查到已存在 → 200 + 同一个任务 id | 一条任务、一次扣费 |
| 键相同 + 并发且行锁失效 | 唯一索引兜底 → 撞键 → **409/40901**（非 500） | 数据仍正确，体验差一档 |

**🔴 关键事实①：幂等命中分支不做任何状态判断**（`:107-110` 只看 `existing != null` 与 `sameRequest`）。不论原任务是 `queued/running/succeeded/failed/cancelled`，一律返回其当前视图。含义：**原任务已失败时，重放同一请求返回的是那条 failed 任务，不会重新执行**。这是"幂等返回"而非"幂等重放执行"——幂等定义（同请求同响应）上正确，但需主动说明。

**🔴 关键事实②：内容比对只存在于「键相同」分支内**（`:105-108`）。所以"内容相同"**不能**阻止不同键的重复提交 → 用户点两次 = 两条任务。结合上一轮前端缺陷（每次提交换新键），**"用户重复点击"真实落在第三行**。

**归一化只做了一半**（`:401-410`，10 项比对中仅 5 处归一化）：`prompt` 服务端先 trim；`background`/`outputFormat` 用 `defaultOption(x, 默认值)` 使「不传」与「显式传默认值」等价；`sourcePictureId`/`referencePictureId` 用 `blank()` 把空串归一成 null 再比。其余 `ratio`/`quality`/`modelCode`/`taskType` 是**严格字符串比较** → `"1:1"` 与全角 `"1：1"` 判为不同 → 409。

**时间维度**：幂等记录即任务行、**永久保留**，三天后同键重放仍返回那条老任务，**绝不会重复扣费**；代价是客户端复用历史键将永远拿不到新任务（契约已写明）。

## 11:17 用户复述提交时序 —— 纠正两处关键理解偏差

用户复述为：「先校验参数 → 开启事务 → 锁用户行 → 创建预占额度行 → 锁住额度行更新数据后**解锁** → 写任务表和 outbox 表 → 提交事务 → **解锁用户行**」。**顺序基本正确，但有两处硬伤**（已画锁持有区间图）：

**❌ 偏差一：不存在"更新数据后解锁"这个动作。**
InnoDB 行锁的持有期是**事务边界**，不是语句边界。`SELECT ... FOR UPDATE` / `INSERT` / `UPDATE` 拿到的锁一律**持有到事务提交或回滚**，中途没有任何语句会释放它。所以正确答案是：**两把行锁从各自加锁起同时持有、直到 commit 一并释放**——图中蓝色（user 行锁，`:104` 起）与琥珀色（额度行锁，`:339-342` 起）两根条是**并行延伸到事务末尾**的，不是阶梯式的"加锁—解锁—再加锁"。
- 推论：**不能靠"先解锁 A 再操作 B"来缩小锁范围**，那需要拆事务（如 `REQUIRES_NEW`），代价是原子性丧失。
- 面试意义：说出「行锁持有到事务提交，锁的持有期等于事务长度」是区分"背过"和"调过"的分水岭。这也解释了为什么事务要尽量短——事务内每一条语句都在延长两把锁的持有时间。

**❌ 偏差二：参数校验不在事务外。**
`@Transactional` 挂在 `create` 方法上（`:89`），**事务从方法入口就开启**。`:91-103` 的参数校验、`:96` 查模型、`:101-102` 查图片归属**全部在事务内执行**。正确说法是：**事务边界早于锁边界**——事务先开，锁到 `:104` 才加。所以前置校验阶段虽然占着事务，但**不持任何行锁**（都是快照读）；即使抛 `badRequest` 也只是回滚一个没有任何写入的空事务，代价可忽略。

**正确时序（7 步，`:89-124`）**：
① 校验参数（事务内、无锁）→ ② 锁用户行 `:104` → ③ 查幂等键 `:105`（快照读，命中则提前 return，走不到后面）→ ④ 预占额度 `:112`→`:338-343`（`INSERT IGNORE` 懒创建 + `SELECT FOR UPDATE` + 判断 + `UPDATE`）→ ⑤ 插任务行 `:121` → ⑥ 写事件行 `:122` → ⑦ 提交，两锁一并释放。

**两个补充事实**：
- 步骤 ④ 的"创建额度行"是 `INSERT IGNORE`，**已存在时实际不插入**（返回 0 行），所以它可能是一次空操作；加锁动作由随后的 `SELECT ... FOR UPDATE` 明确完成。
- 锁的**释放顺序不可控也不需要控**：commit 时一次性全部释放，不是说"先解额度锁再解用户锁"。

**加锁顺序的固定性（防死锁）**：全局只有这一个提交入口，加锁顺序恒为 user → quota。如果将来出现第二个入口以相反顺序加锁（先 quota 后 user），会形成环路等待——这是"加锁顺序必须全局一致"的典型约束点。

## 11:23「前置校验为什么放在事务里」——**答案是它不是必需的**

**核心结论：没有技术必然性，是 Spring 声明式事务粒度的副作用。** `@Transactional` 挂在 `create`（`:89`）方法上，而声明式事务的**最小粒度是方法**——要么整个方法在事务里，要么都不在，没有"方法前半段在事务外"这种可能。校验写在方法开头，就被一并圈进去了。

**三条边界必须分开看（已画图）**：

| 边界 | 起点 | 说明 |
|---|---|---|
| 事务边界 | 方法入口 `:89` | 由 Spring 声明式事务决定 |
| **连接占用边界** | **方法入口**（与事务同起） | `DataSourceTransactionManager.doBegin()` 会**立即 `getConnection()` + `setAutoCommit(false)`**，不是等到第一条 SQL |
| 行锁边界 | `:104`（user）、`:339-342`（quota） | 由 InnoDB 决定 |

**关键推论：事务边界 = 连接占用边界，二者都早于锁边界。** 所以校验段"不持锁，但已经占着连接和事务"。

**项目的连接池事实（已核实）**：`application.yml:14-18` 只配了 driver/url/username/password，**没有任何 `spring.datasource.hikari.*` 或 `maximum-pool-size` 配置** → 用 HikariCP 默认 **`maximumPoolSize = 10`**；也没有自定义 `PlatformTransactionManager` → 默认 `DataSourceTransactionManager`（会立即取连接的那种）。

**真实成本（不是"长事务"，要拆成三笔分开算）**：
1. **持锁成本 = 0** —— 校验段全是快照读（`:96` 模型查询、`:101-102` 图片归属），不加任何行锁。
2. **回滚成本 ≈ 0** —— 抛 `badRequest` 时事务内**没有任何写入**，回滚是空操作。
3. **连接占用 = 真实存在的成本** —— 校验失败（用户输错提示词、比例不支持、图片 ID 不属于本人）这类**高频且注定失败**的请求，也要走「取连接 → 空回滚 → 还连接」的完整周转。池只有 10，高并发时这些无效请求会加剧其他请求的连接等待。

**校验段实际执行几次查询（`:372-378` 核实）**：`:96` 查模型**必定执行**；`picture()`（`:372`）在 `id == null || id.isBlank()` 时**直接 return null 不查库** → 纯文生图 **0 次**，扩图/带参考图 **1-2 次**。所以校验段的数据库往返是 1-3 次，不是固定 3 次。

**为什么不能"顺手挪出去"（三种做法的可行性）**：
1. **抽成同类 private 方法** → ❌ **无效**。同类内调用不走 Spring 代理，外层 `create` 上的 `@Transactional` 依然覆盖整个调用链，校验仍在事务内。（这是 self-invocation 陷阱的**反向**应用：通常人们担心"注解失效"，这里是"注解甩不掉"。）
2. **把 `@Transactional` 下沉到内层方法、外层不加** → ❌ 同样因 self-invocation 失效（`M2Controller` 调的是 `AiTaskService` 的代理，但代理只认最外层标注的方法）。
3. **抽到另一个 Bean**（如独立 Validator Bean 由 Controller 先调）或**改用 `TransactionTemplate` 编程式控制** → ✅ 可行，但代价是：校验所需的数据（模型配置、图片归属）本来就要连库读，挪出去要么**再查一次**、要么把实体当参数传进来；且打散「读-判断-写」的可读性。

**结论：保留现状是合理权衡。** 收益（省下校验失败那一次连接周转）小于成本（拆 Bean / 编程式事务 / 多一次查询 / 可读性下降）。

**什么时候才必须挪（判据）**：① 校验里出现**外部调用**（风控、验证码、限流 HTTP）→ 必须挪，否则事务被网络等待撑长；② 校验里有**慢查询或大表扫描** → 应该挪；③ **校验失败率极高**（如 >30%）→ 值得挪。当前三项都不成立。

**面试口径**：被问"为什么校验放事务里"，**别硬答"为了原子性"**——校验不需要原子性，面试官一听就知道在背。
> 「它是声明式事务粒度的副作用：事务注解挂在方法上，方法入口就开始事务，所以方法开头的校验天然在里面。严格说校验不需要事务也不涉及写入，失败时回滚的是一个空事务。保留它是因为校验本身很快，挪出去要么拆 Bean、要么改成编程式事务，收益不够。真正需要原子性的只有后面预占、落任务、写事件这三步。」

**追问"那事务是不是开得太早"时的加分答法**：把笼统的"长事务"拆成三个可分别评估的量——
> 「事务边界确实早于锁边界，但要看三件事：这段不持有任何行锁（都是快照读）；失败时回滚的是空事务；唯一真实成本是连接池——框架在事务开始就取连接，所以校验失败的请求也占一次连接周转。所以判断标准不是'事务多长'，而是'这段时间里有没有持锁、有没有慢操作'。」

**这也顺带纠正一个常见误解**：`@Transactional` 的 `rollbackFor = Exception.class` 看起来很宽，但在这个方法里校验异常全是 `V1Exception`（业务异常），回滚的都是空事务，配置宽窄对性能没有影响。

## 15:29 事务的职责边界（用户理解补两层）

用户理解为「事务是为了保证配额表 + 任务表 + outbox 表三表数据一致性」。**方向正确，但差两层，且术语要收紧。**

**① 术语精确化：是「原子性」不是笼统的「一致性」。** ACID 里 A（Atomicity）才是事务提供的机制——三笔写入全或无；C（Consistency）是**结果**而非机制，由 A + I + 约束 + 应用逻辑共同达成，单靠事务给不了。面试时说"保证原子性"比"保证一致性"准确得多，后者会被追问"你说的一致性指什么"。

**② 事务内还有第四张表：`user` 的加锁读。** 上图里用虚线圈出——它不产生数据变更（不是"一致性"的对象），但它是事务的一部分（`FOR UPDATE` 是当前读 + 加锁），且是"查幂等 → 预占 → 插任务"这个跨表链条的串行化闸门。所以准确表述是**三笔写入 + 一次加锁读**。

**③ 🔴 事务的第二个职责（用户完全没提到的）：它是「锁生效的载体」。**
`SELECT ... FOR UPDATE` 抢到的行锁，**释放时机是事务结束**。反推：**若 `create` 不加 `@Transactional`**，MyBatis-Plus 的每条语句自动提交 → `lockById` 的行锁在语句返回瞬间就释放 → 后面"查幂等键 → 预占 → 插任务"全程无保护 → **两把行锁全部形同虚设**。
所以事务不只是让三表原子写入，它还给两把锁提供了有效的持有期。**去掉事务，不只是失去原子性，还会同时废掉锁**——这是"事务 ≠ 只是打包写入"的关键认知。

**④ 事务的真实管辖范围：仅本地数据库。** 跨系统动作（消息投递 / Provider 调用 / 对象存储写入）事务一概管不了。**outbox 模式的本质不是"多写一张表"，而是把其中唯一的跨系统动作（发消息）改造成本地记录**，从而把它拉进事务的管辖范围。
- `ai_task` = 业务意图的持久化
- `ai_task_outbox` = **投递意图**的持久化（前者是"要做什么"，后者是"要通知谁"）
- 两者同事务 = 「任务存在 ⟹ 事件必然存在」

**⑤ 三种破坏场景（说明原子性为什么必需，面试可直接引用）**：

| 部分失败 | 后果 |
|---|---|
| 额度预占了、任务没插 | **额度泄漏**——白扣一次却没有任何任务 |
| 任务插了、额度没预占 | **免费生图**——不花钱就拿到任务 |
| 任务和额度都写了、outbox 没写 | **任务永挂**——用户永远看到"排队中"，无人执行 |

三种都是真实的数据损坏，事务把它们变成"全或无"。

**⑥ 事务不保证什么（避免过度承诺）**：不保证 AI 调用成功（退避重试）、不保证消息真的发出（只保证有一条待发记录，靠轮询器补投）、不保证额度最终不漏（对账任务）、不保证任务不重复执行（状态机 + 租约 + 栅栏令牌）。

**⑦ 已核实的传播行为（这是三表原子的隐性前提）**：`AiTaskOutboxService.enqueue`（`:24-25`）标注 `@Transactional(rollbackFor = Exception.class)`，默认传播行为 **REQUIRED** → 从 `create` 跨 Bean 调用时**加入当前事务**，不新开。
- **必须保持 REQUIRED**：若改成 `REQUIRES_NEW` → outbox 独立提交 → 主事务回滚时留下**孤儿事件**（事件存在、任务不存在）→ 轮询器捞到后查不到任务、空转。改动它会静默破坏整个 outbox 的语义。

**🔴 顺带发现的脆弱点（未修）**：`AiTaskOutboxService.recoverExpiredTask`（`:35-53`）第 `:51` 行的 `enqueue(taskId)` 是**同类内 this 调用**，不走 Spring 代理 → `enqueue` 上的 `@Transactional` **不生效**。当前结果正确，纯粹因为 `recoverExpiredTask` 自己已有事务，enqueue 的 SQL **搭了它的车**。这是"巧合性的正确"：一旦有人去掉 `recoverExpiredTask` 的事务（比如误判它"只是查询"），"改状态 + 写事件"会同时失去原子性，而 `enqueue` 的注解救不了它。修法：把 enqueue 的 insert 内联到本类，或注入自身代理（`@Lazy` self-injection / `AopContext.currentProxy()`）。
- 与上一轮「同类 private 方法调用导致注解甩不掉」正好互为镜像：**同类调用的注解行为，两个方向都不可靠**——想让它生效时它失效，想让它别生效时它甩不掉。**判据永远是"有没有跨过代理边界"，而不是"注解写没写"。**

**面试口径**：被问"这个事务是干什么的"，别只说"保证一致性"——
> 「它保证的是三笔本地写入的原子性：额度预占、任务落库、投递事件落库。这三笔拆开做，任何一种部分失败都会留下损坏状态——额度占了没任务、或者任务存在但没人执行。事务还把消息投递这个跨系统动作降级成了一条本地记录，这样'要不要投递'也变成可持久化的、能被事务覆盖的状态。另外它还有个容易被忽略的作用：行锁的释放时机是事务结束，所以事务同时也是那把用户行锁能真正生效的载体——去掉事务，锁会立刻失效。」

## 15:36「任务表与 outbox 表为什么分两张 / 能不能合并」（**发现是 1:N 而非 1:1**）

**决定性证据：`enqueue` 全项目只有两个调用点**，且跨表基数是**一对多**：
1. `AiTaskService:122` —— 创建任务时投递一次（每任务 1 次）
2. `AiTaskOutboxService:51` —— **租约过期恢复任务时重新投递**（每次恢复再产生 1 条）

所以任务 #31 可对应 outbox #100 / #205 / #409 多行（**同一任务被投递多次**）。**必须新起行而非原地重置**的原因：`eventId` 上有唯一索引 `uk_ai_task_outbox_event`（`V20:30`），重投必须换新的事件标识。**结论：不是 outbox 模式要求分表，是「一次意图可能对应多次投递」这个事实要求分表。**

**两表结构事实（已核实）**：
- `ai_task`（`V3:33-68` + `V20:1-6` + `V6`/`V22`）：25+ 列，含 `status`、`attemptCount`、`workerId`、`leaseUntil`、`nextAttemptAt`、`quotaCost`、`quotaRefunded`、`providerTaskId`、`resultPictureId`。
- `ai_task_outbox`（`V20:16-34`）：11 列 = `eventId` / `taskId` / `status` / `attemptCount` / `nextAttemptAt` / `lockOwner` / `lockUntil` / `publishedAt` / `lastError` / 时间戳。外键 `fk_ai_task_outbox_task → ai_task(id)`。

**五个不可合并的判据（按硬度排序）**：
1. **基数 1:N**（最硬）——见上。合并后多条投递记录无处安放，只能压成一个状态字段，丢失"被投递几次、每次为何失败"。
2. **生命周期相反**——`ai_task` **永久保留且兼任幂等记录**（幂等键与任务同行），删不得；`ai_task_outbox` 由 `cleanupPublished`（`AiTaskOutboxPublisher:44-49`）每小时删一次：`status='published' AND publishedAt < now-retentionDays(7) LIMIT 1000`。**合并后删 7 天前事件即等于删用户的生图历史 + 删幂等记录 → 用户拿同一键再提交会被当成新意图重新扣费**（功能性破坏，非性能问题）。
3. **状态语义正交**——`ai_task.status` = 业务走到哪一步（queued/running/succeeded/failed/cancelled）；`ai_task_outbox.status` = 通知送出去没有（pending/failed/published）。二者**可同时取不同值**：任务 `running` 的同时其下一条投递事件 `pending`；或任务已 `succeeded` 但仍有 `pending` 事件。一列存不下两个正交状态；若加第二列则等于把 outbox 换个形状拉回同表；若用组合值则 5×3=15 种组合、状态机爆炸。
4. **两套退避时钟同名不同义（最易被忽略）**——两表各有 `attemptCount` / `nextAttemptAt`，但数的是不同东西：`ai_task` 数 **Provider 真实调用次数**（退避 5/30/120 秒，见 `AiTaskRunner`）；`ai_task_outbox` 数 **消息投递失败次数**（`AiTaskOutboxPublisher:66` 退避 `min(60, 1<<min(attempts,6))` = 1/2/4/8/16/32/60 秒）。**两条曲线独立**：可以"消息一次投递成功但 Provider 失败 4 次"，也可以"消息投递失败 5 次而任务从未进入执行态"。合并成一列 → 丢消息失败会推后业务退避、业务失败会推后投递，互相干扰。
5. **访问模式与锁竞争不同**——outbox 是**每秒一次**的定向轮询（`idx_ai_task_outbox_due`）+ 每行一次 `claim` 条件更新（`AiTaskOutboxMapper:11-15`，锁 30 秒）；任务表是 worker 的 `claimForExecution` 条件更新。合并后两个操作抢**同一把行锁**，发布器持有任务行锁会阻塞 worker 抢占，反之亦然。另有规模差异：`ai_task` 永久无上限增长，`ai_task_outbox` 因删已发布记录而**有界**——让每秒轮询去扫无限增长的表，索引维护成本与命中率都变差。

**硬合并的代价清单**：需给 `ai_task` 加 7 列（`dispatchStatus` / `dispatchAttemptCount` / `dispatchNextAttemptAt` / `dispatchLockOwner` / `dispatchLockUntil` / `publishedAt` / `lastDispatchError`）+ `eventId` 唯一索引 → 表涨到 32 列成 god table；重投只能原地重置 → 投递历史丢失、无法统计"任务平均被投递几次"；清理逻辑写不了（删任务行会连毁业务数据）；轮询与抢占抢同一行锁。**唯一收益是少一张表，而这两张表之间连 JOIN 都不需要**（轮询不 join、任务查询不 join）。

**「什么时候可以合并」的判据**：**投递失败之后要做的事，能不能纯用业务状态机表达？** 若"消息发失败"的后果只是"任务晚点再跑"、且**永远只有一次投递**（不需重投），可退化成一个 `nextAttemptAt` 列 + 轮询业务表（"业务表轮询式投递"）。本项目不满足：**租约恢复会重新投递**（产生第 2、3 条事件），且投递重试节奏 ≠ 业务重试节奏。

**可挑刺点**：`idx_ai_task_outbox_task (taskId, id)`（`V20:32`）全项目**无任何代码使用**，是为"查某任务的全部投递记录"预留的排障索引（目前无配套接口/脚本）。既然分表的核心价值正是保留这个 1:N 历史，索引本身合理。

**面试口径**：

## 15:51 outbox 轮询语句的执行计划（**真实 EXPLAIN 实证，含一个可修缺陷**）

**查询语句（`AiTaskOutboxPublisher:32-40`）**：`LambdaQueryWrapper` → `.in(status,"pending","failed")` + `.le(nextAttemptAt, now)` + `.and(q -> q.isNull(lockUntil).or().le(lockUntil, now))` + `.orderByAsc(id)` + `.last("LIMIT 50")`，`@Scheduled` fixedDelay=1000ms（`outbox-poll-millis`）。

**索引（`V20:31`）**：`KEY idx_ai_task_outbox_due (status, nextAttemptAt, lockUntil, id)`。**是索引范围定位，不是从第一条扫。**

**key_len=93 实证解码**：status VARCHAR(20) utf8mb4 NOT NULL = 80+2 = **82**；nextAttemptAt DATETIME NOT NULL = **5**；lockUntil DATETIME NULL = 5+1 = **6** → 82+5+6 = **93**。即**前三列全部作为访问谓词**；`id` 是 BIGINT=8，未参与（参与则为 101）。
- `status IN (...)` 被范围优化器改写成**两段范围**，EXPLAIN 原文可证：`over (status='failed' AND nextAttemptAt <= X AND lockUntil <= X) OR (status='pending' AND nextAttemptAt <= X AND lockUntil <= X)`。
- **反直觉点**：`lockUntil IS NULL OR lockUntil <= now` 看似索引杀手，但**NULL 在索引升序里排最前**，`{NULL} ∪ {≤now}` 恰好是索引序里的一段**连续前缀** → 可当范围用；`Extra` 出现 `Using index condition`（ICP，下推到引擎在索引元组上过滤，减少回表）。

**🔴 缺陷：`ORDER BY id` 与索引前导列冲突。** 任何以 `status` 为前导列的索引都产不出**全局 id 序** → 优化器只剩两条路：**A** 范围扫描 + filesort；**B** 主键扫描 + 提前停止（`ORDER BY id LIMIT 50` 的 LIMIT 优化）。实测（沙箱 `outbox_plan`，MySQL 8.0.46，200,000 行 = 100,000 published 低 id + 100,000 pending 到期高 id，**未建 FK**）：

| 场景 | 实际执行计划 | 扫描行数 | 实测耗时 |
|---|---|---|---|
| 稳态（仅 50 行到期）· 带 ORDER BY id | `type=range, key=idx_ai_task_outbox_due, key_len=93, Extra=Using index condition; Using filesort` | 51 | **0.179 ms** |
| 稳态 · 去掉 ORDER BY | 同上，无 filesort | 50 | **0.116 ms** |
| **积压（10 万行到期）· 带 ORDER BY id** | **`type=index, key=PRIMARY, key_len=8, Extra=Using where`（索引被完全绕过）** | **100,050** | **41 ms** |
| **积压 · 去掉 ORDER BY** | `type=range, key=idx_ai_task_outbox_due` | **50** | **0.228 ms** |
| 积压 · 改成 `ORDER BY nextAttemptAt` | 全表扫描 + filesort（更差） | 200,000 | **96.7 ms** |
| 积压 · 强制 `INDEX(...)` + ORDER BY id | 范围扫描 + filesort | 100,000 | **155 ms** |
| 积压 · DROP 掉 idx_ai_task_outbox_due | `type=index, key=PRIMARY` | — | （同样退化） |

**估计错误是切换的根因**：积压场景优化器估 `rows=99, filtered=20.00%`，实际扫 100,050 行、真实过滤率 **0.05%** → **低估约 1000 倍**。原因：它假设 `nextAttemptAt <= now` 与 `id` 独立，而现实中**到期的行集中在表尾**（故障期间新建的任务都在尾部，之前的老行都已发布）。

**用户直觉「从第一条记录查」在积压场景下是对的**（主键扫描就是沿主键从头走）；稳态下不成立。

**修复（一行）**：删掉 `.orderByAsc(id)`。该排序**无业务价值**（不需要 FIFO）；去掉后优化器稳定走范围扫描、扫够 50 行即停，坏场景下 41ms → 0.23ms（**约 180 倍**）。**切勿改成 `ORDER BY nextAttemptAt`**——实测更差（96.7ms，优化器转为全表扫描 + filesort）。

**量级（避免夸大）**：86,400 次/天/例。稳态 ≈ 0.18ms → 约 15 秒/天 CPU；积压 ≈ 41ms → 约 59 分钟/天 CPU、每天扫约 86 亿行。**但不会失控**：单轮 50 条 / 41ms ≈ 1,220 条/秒，而下游执行能力仅 4 并发 ÷ 30 秒 = 8 任务/分钟 ≈ 0.13 条/秒 → 派发侧仍有约三个数量级余量。属"浪费"而非"瘫痪"。

## 16:15 索引底层结构讲解（B+ 树，纠正用户"二叉树"说法 + 修正上一轮 key_len 表述）

**① 术语纠正**：InnoDB 用 **B+ 树**，不是二叉树。二叉树每节点最多 2 分叉 → 20 万行要近 18 层 = 18 次页读；B+ 树「一个节点 = 一个 16KB 页、页内放几百个键」把树高压到 3 层以内 = 3 次页读。**"页 = 节点"是理解 InnoDB 索引的第一个前提。**

**② 三层结构与叶子内容**：
- 非叶页：只存「分隔键 + 子页号」，不存数据行。
- 叶子页：存「索引列 + 主键」——本索引恰好是 `(status, nextAttemptAt, lockUntil, id)` 四列，因为 `id` 是主键会隐式附加在二级索引末尾。**所以 V20 里显式写的 `id` 在存储上与不写等价**（InnoDB 不会重复存主键），这也解释了 `key_len=93` 为何不含它（BIGINT=8，含则 101）。
- 叶子页之间是**双向链表** → 范围扫描定位起点后沿链表右行，不再回根页。

**③ 叶子节点排列规则（用户问题核心）**：按索引列顺序**逐列字典序比较**，前一层相等才比下一层：
`status`（utf8mb4_unicode_ci 字符序）→ `nextAttemptAt`（时间升序）→ `lockUntil`（**NULL 排最前**）→ `id`（升序）。
- **🔴 关键：`NULL` 是索引升序里的最小值，排在同组最前。**
- 已画图举例（7 条记录）：`failed` 组 → `pending` 组 → `published` 组；同组内 `(10:00:05, NULL, 5)` 排在 `(10:00:05, 10:00:20, 9)` **之前**；`pending` 组的 id 序是 **7, 3, 11（不递增）**——因为 id=7 与 id=3 的 `nextAttemptAt` 相同，而 7 的 `lockUntil` 是 NULL 更小。**这个「id 不递增」的可视化，正是 ORDER BY id 用不上索引的直观证据。**

**④ ⚠️ 修正上一轮 key_len 的表述**：上一轮我说「`key_len=93` 正好证明前三列都当成了访问谓词」——**不准确**。准确说法：`key_len` 反映被解析进访问路径的索引列总长（ICP 下推/覆盖的列也算），**"被用上"≠"能收窄扫描范围"**。

**⑤ 复合索引的范围规则**：某列一旦用**范围条件**（这里 `nextAttemptAt <= now`），其**后面的列就不能再用于收窄扫描区间**，只能做过滤。所以真正决定扫描边界的是 `(status, nextAttemptAt)`，`lockUntil` 只是过滤器。

**⑥ 实测证明（沙箱 `idx_probe`，MySQL 8.0.46，2000 行；FORCE INDEX + COUNT + `Handler_read_next`）**：

| 查询 | 匹配行数 | `Handler_read_next`（实际扫描） |
|---|---|---|
| `status IN(…) AND nextAttemptAt <= '10:00'` | **1000** | **1000** |
| 上述 + `AND (lockUntil IS NULL OR lockUntil <= '10:00')` | **500** | **1000** |

→ **加了第三列条件后匹配行数减半，但扫描的索引记录数一行没少** = `lockUntil` 纯粹是**过滤**，不参与范围收窄。
- 附带验证索引内真实排序：`LIMIT 3 OFFSET 499` 看到 `id=500(lockUntil=NULL)`、`501(11:00:00)`、`502(11:00:00)` —— 同组内 NULL 段（id 1-500）在前、非 NULL 段（id 501-1000）在后，与「NULL 排最前」完全一致。
- Q2 的执行计划：`type=range, key_len=93, Extra=Using where; Using index`（真实查询无 FORCE INDEX 时为 `Using index condition`，即 ICP）——两种都表明 lockUntil 是过滤。
- 沙箱 `idx_probe` 已删除，真实库 `teacup_picture` 完好未动，临时 SQL 已清理。

**⑦ 面试口径**：
> 「索引是 B+ 树不是二叉树——每个节点是一页，非叶页只存分隔键和页号，实际数据全在叶子页，叶子页之间用双向链表串起来，所以范围扫描定位起点后顺着链表走就行。叶子节点内按索引列顺序逐列比较排序，前一层相等才比下一层；空值在升序里排最前。有一条容易搞错的规则：一旦某一列用了范围条件，它后面的列就不能再缩小扫描区间，只能当过滤器——我实测过，把第三列的条件加上去，匹配行数少了一半，但扫描的索引记录数一行没减。」

**🔴 三处发现（用户已告知，均未修）**：
1. **`overflow(reject-publish)` 是空转的**。全局 grep 无任何 `max-length` / `max-length-bytes`（`AiRabbitConfigTest:21` / `CacheRabbitConfigTest:17` 只断言 `x-overflow` 参数存在）→ 队列无容量上限、永远不会有「满」这个状态，拒收策略与配套的 at-least-once 死信策略都触发不了。要么补容量上限让它生效，要么承认这里不做背压。
2. **缓存失效 DLQ 无消费者**（和当时 AI DLQ 是同一个问题模式）。但在此场景**恰好无害**：消费者失败走 `basicNack(requeue=true)` 而非 reject，消息永远不进 DLQ；队列又无上限，也不会因满而触发死信 → 该队列实际恒空。
3. **缓存失效的重试是无限立即重投**（`CacheInvalidationConsumer:29` 的 `basicNack(deliveryTag,false,true)`）。requeue 会把消息放回队列靠前位置，很可能立刻又分给同一消费者 → Redis 长时间不可用时形成高速忙循环，且无 `x-delivery-limit` 永不停。对比 AI 侧用「有限次数 + 延迟队列退避」——**策略差异的正当理由**：清缓存幂等且毫秒级（重投无代价），生图有真实上游成本（必须限次）。但防忙循环仍需一个投递次数上限。

**分发机制（用户问「broker 怎么推」的答案）**：AMQP 是 push 模型，消费者 `basic.consume` 注册后被动接收。三个层次：① 分发单位是**队列**不是交换机（交换机只在投递瞬间决定进哪个队列）② 候选集按**剩余额度**筛（prefetch 是 per-consumer 的在途上限，手上没额度的本轮跳过）③ 候选集内**轮询 round-robin**（不是"谁快给谁"）。全都没额度时消息留在队列排队。quorum 队列的分发由 **leader 节点**负责。消费者掉线时 broker 把未确认消息**重新入队**（带 redelivered 标记）——**这是重复投递的根源**，AckMode 手动 + 幂等/栅栏令牌都是在应对它。

## 20:43 四个消费者是谁 + 20:47 线程池为什么 core=max=4

**消费者 = AMQP 层实体，线程 = 执行层实体，此处恰好一对一**。`SimpleMessageListenerContainer` 起 4 个 consumer，**每个 consumer 一条独立 channel + 一个 consumer tag**，消费动作交给 `ai-worker-` 线程池执行（`AiRabbitConfig:103-117`：core=max=`concurrency`，`queueCapacity=0`，`AbortPolicy`）。**多实例部署时是 4 × 实例数**（`prefetch` 也是每个消费者各算一份 → 系统总在途上限 = 4 × 实例数）。

- `queueCapacity=0` 是**防御性**的：因 prefetch=1 保证一个 consumer 同时只提交一个任务，队列容量设 0 不会触发；但若有人把 prefetch 调大，会立刻抛拒绝异常而非悄悄堆在内存 —— **把隐蔽配置错误变成显式失败**。
- **线程名有实际用途**：`AiWorkerIdentity:21` 拼出 `实例UUID:线程名`（如 `3f2a…-uuid:ai-worker-2`）写进 `ai_task.workerId` → ① 续租可按实例前缀批量刷（`workerId LIKE 'UUID:%'`）② 执行权判定精确到线程。序号由线程池分配，重启后可变，**无影响**——该标识生命周期是「一次任务执行」，不承担跨进程持久身份。
- **定时任务在另一个池**：`SchedulerConfig` 前缀 `scheduled-`、池大小 4，与 `ai-worker-` 完全隔离。若两者共用，一个跑几十秒的任务就能把续租饿死、进而拖垮自己的租约。**本项目避开了这个坑。**
- **⚠️ 边界（可量化）**：全局 **9 个 `@Scheduled` 共用 4 个线程**（grep 核实）。正常都是毫秒级查询，够用。但续租链路容忍度有数：租期 300s / 续租 90s → **能容忍连续 3 次续租失败**（270s < 300s）。DB 整体不可用超约 450s 时续租连续失败 → 恢复服务会把仍在运行的任务判成僵尸重新入队 → 重复执行（配额与结果由令牌兜住，代价是一次白烧的上游成本）。加宽办法：续租单独拆池，或与清理类任务分优先级。

**为什么 core = max = 4（用户问题的答案）**：
- **4 不是按 CPU 核数算出来的，是从上游并发额度倒推的**。`teacup.ai.worker.concurrency` 一个变量同时驱动「消费者数」与「线程池大小」（`AiRabbitConfig` 里同一个 `@Value` 传两个 bean），保证「消息在途上限」与「线程数」永不错配。
- **任务性质判定**：单次生图总耗时约 20s，本机真正计算（Base64 解码、落盘、写库）约 100ms → 等待占比 99.5%。按教科书 IO 密集型公式 `核数 × (1 + 等待/计算)`，2 核机器要 2 × 201 = **402 个线程**——数字荒谬，说明**公式前提不成立**：该公式假设「加线程就加吞吐」，而这里加线程只会得到 429 和成倍账单。**它属于「受限资源型」（bound by external permit/quota）**，本项目专门有 `AiExecutionLimiter` 按 provider 维度限流。正确推法：`线程数 = min(外部许可数, 内存能容纳的在途缓冲数)`。
- **core = max 的理由**：并发需求**恒定**（上游流入量已被 `prefetch=1 × 4` 限死），不存在需要弹性伸缩的场景；且 `queueCapacity=0` 时 `max > core` 的扩容路径本就打不通（任务无处排队即直接拒绝），设了无用。对恒定需求做动态伸缩只有成本没有收益。

**2 核 4G 的配置建议（用户问题，方法论比数字重要）**：
- **第 0 步先算内存**：若按本地开发那套在同一台跑全套中间件 —— MySQL 8 约 800MB + RabbitMQ(Erlang VM) 约 300MB + Redis 约 100MB + MinIO 约 150MB ≈ **1.35GB**，加 OS 500MB + 应用 JVM 2GB ≈ **3.85GB**，4G 无任何余量。**结论：2 核 4G 只够跑应用本身，中间件必须外置**（托管 DB / 云 Redis / 云 MQ）。能启动，但流量一上来或堆外需求一涨就 OOM/swap。
- **JVM**：`-Xms2g -Xmx2g` 固定（避免堆伸缩抖动）+ 堆外 256MB + 元空间/线程栈/JIT 约 300MB ≈ 2.6GB，留约 900MB 余量。图片缓冲实测量级：1024×1024 PNG 约 1.5MB，Base64 膨胀 1/3 → 约 2MB/张，4 并发同时持图 ≈ 8MB 峰值，相对 2GB 堆可忽略，**但前提是 `-Xmx` 不能设成 512m 这类小值**。
- **Tomcat**：默认 `max=200` 太浪费（每线程 1MB 栈）。用 Little's Law：目标 100 QPS × 单请求 50ms = **5 个线程**；给 `threads.max: 50` 已可扛约 1000 QPS（快接口）。分片上传等慢接口单请求几百毫秒~数秒，需单独估。
- **AI 工作线程**：保持 4（瓶颈在上游，与核数无关）。上游许可更少就调小。
- **定时任务池**：保持 4（9 个任务共用，都很快）；降 2 也可，但须保证续租不被饿死。
- **HikariCP（当前无任何显式配置，走默认 10）**：经典公式 `核数×2 + 有效磁盘数 = 5`，实际按「同时执行的库操作数」估 —— AI 线程只在 `markRunning`/`complete` 等小事务持连接，**调上游时不持有** → 峰值 4；定时任务峰值 4；Tomcat 侧估 10。建议 `maximum-pool-size: 15`、`minimum-idle: 5`。**不要超 50**：MySQL 每连接占 256KB~1MB 内存，且连接数超核数后并发能力不再提升，只增加上下文切换与锁竞争。
- **RabbitMQ 消费者并发**：保持 4（与上游许可一致）。
- **CPU 侧**：总线程约 70，但绝大多数在等 IO，2 核够用。真正的风险在 GC —— G1 在 2 核上 GC 线程数约 1~2，STW 期间会暂停，建议开 GC 日志观察。

## 21:00 ⚠️ 纠正「prefetch 限死流入量」的措辞 + 定位真正的背压缺口

**上一轮我说「上游的流入量已被 `prefetch=1 × 4` 限死」——两处不严谨**：①「上游」有歧义（我指本机流程入口，读者会理解成 AI provider）；② 更重要的，**prefetch 限制的是「在途量（并发）」不是「流入量（速率）」**。

**准确表述**：broker 在 channel 上做额度记账（`basic.qos`，global=false → per-consumer 未确认 ≤ 1）→ **单实例在途上限 = 4**。但**队列深度无上限**（无 `x-max-length`，「第 5 条」只是留在队列排队，不是被拒收）。

**额度归还时机（已核实）**：`AiTaskConsumer:48` 的 `basicAck` 发生在 `:37` `runner.run(taskId)` **返回之后** → **整个约 20s 的执行期都在持有这 1 个额度**；retry 分支 `:44` 的 `basicNack(requeue=true)` 同样归还额度。

**由此得到的精确链条**（这才是「core=max=4 且 queueCapacity=0 永不触发拒绝」的依据）：`prefetch=1` → 每个消费者最多 1 条未确认 → 最多 4 次 listener 调用 → 线程池最多 4 个任务 → **池的第 5 个槽位不可达**。

**🔴 真正的缺口：限的是并发，不是准入。** 1000 个生图请求全部 201 成功，发布器几分钟内把 1000 条全推进队列；4 个 worker 以 20s/条 消化 = **0.2 条/秒 = 12 条/分** → 最后一张等 `1000 × 20 ÷ 4 = 5000s ≈ 83 分钟`，而**没有任何机制把这个延迟反馈给用户**（前端只显示「排队中」）。所以风险不是「流入被限制」，而是「流入完全不设限、消化速度固定、差额全变队列积压」。

**真正的三道闸（都不在 MQ）**：① `ai_quota_usage` 的日额度 —— 唯一的**业务准入**硬闸；② 上游 provider 限速 + `AiExecutionLimiter` —— 决定**消化速度**；③ outbox `LIMIT 50` + 每秒一轮 —— 派发上限 50 条/秒，约为消化速度的 375 倍，**不构成限制**。

**面试口径**：prefetch 是**并发上限**，不是**准入限流**。它保证任务不囤在本机内存，但不阻止积压堆在 MQ 里；背压要单独做（队列容量上限 + 向用户暴露排队深度/预计等待）。

## 21:04 ⚠️「channel 也配成 4」的前提纠正 + 消费侧/发布侧 channel 的分野

**纠正措辞**：代码里**没有任何一行配置 channel 数量**。配的是 `setConcurrentConsumers(concurrency)`（`AiRabbitConfig:130`）+ `setMaxConcurrentConsumers`（`:131`）；**channel 数是派生结果** —— Spring AMQP 的 `SimpleMessageListenerContainer` 为每个 consumer 建**一条独立 channel**（`BlockingQueueConsumer` 构造时 `createChannel`）。面试别说"我配了 4 条 channel"，要说"我把消费者并发设成 4，容器为每个消费者建一条 channel"。

**channel 必须与消费者一对一（四个约束）**：
1. **channel 非线程安全** —— AMQP 规范要求单线程使用 channel，并发写入会交织协议帧 → 协议级错误；
2. **`deliveryTag` 是 channel 局部的编号** —— `basicAck(tag)` 必须在该条 channel 上执行，4 个线程共用一条会 ack 到别人的消息；
3. **prefetch 语义（最关键）** —— 共用一条 channel 会让额度被 4 个线程共享，`prefetch=1` 的实际并发从 4 退化为 1，**吞吐直接砍 4 倍**。所以「一个消费者一条 channel」是 prefetch=1 能精确表达「每消费者 1 条」的前提；
4. **故障隔离** —— channel 级异常（如队列被删、routing key 错误）只打掉这一条 channel，不波及兄弟。

**🔴 消费侧 channel ≠ 发布侧 channel（易混淆点）**：

| | 消费侧 | 发布侧 |
|---|---|---|
| 来源 | listener container 按 `concurrentConsumers` 创建 | `CachingConnectionFactory` 的缓存池 |
| 数量 | = 消费者数（4） | **默认 `channelCacheSize = 25`**（`cacheMode=CHANNEL`） |
| 生命周期 | 长期持有，直到消费者销毁 | 用完归还缓存、复用 |
| 本项目 | `AiRabbitConfig:130` | **无任何配置** → 走 Spring Boot 自动配置的默认 25 |

已核实：全局 grep **零命中** `CachingConnectionFactory` / `channelCacheSize` / `spring.rabbitmq.cache.*`；`application.yml:31-40` 只有 host/port/username/password/vhost + `publisher-confirm-type: correlated` + `publisher-returns: true` + `template.mandatory: true`。**所以发布方向的 channel 池是 25 条，与消费侧的 4 条完全无关** —— 被追问「你到底开了多少 channel」时不能只答 4。

**面试口径**：
> 「没有单独配 channel 数量，配的是消费者并发数，容器会为每个消费者建一条独立 channel，所以是 4 条。channel 不能共用：它不是线程安全的，而且确认消息用的投递编号是 channel 局部的；更关键的是预取额度会被多个线程共享，并发数会从 4 掉到 1。发布侧是另一回事——那是连接工厂里一个默认 25 条的 channel 缓存池，和消费侧的不是一回事。」

## 21:08 🔴「消费者为什么是 4」的完整推导（**本轮最重要发现：4 = 全局额度 12 ÷ 期望实例数 3**）

**关键事实（全部核实）**：
- `teacup.ai.worker.concurrency:4`（`AiRabbitConfig:105` 与 `:125` 两处 `@Value`）**在所有 yml 里都没有配置**（`application.yml` / `application-local.yml` 均无该 key）→ 生效的就是默认值 4。
- 同一个值驱动四处：容器 `concurrentConsumers`（`:130`）、`maxConcurrentConsumers`（`:131`）、线程池 core/max（`:108`/`:109`）、以及 `prefetch=1` 下的**在途上限 = 4**。**四者恒等，一个配置项保证永不错配。**
- 🔴 **`AiExecutionLimiter:68` 的 `teacup.ai.worker.global-concurrency:12`** —— 存在 Redis 的 ZSET `teacup:ai:concurrency:{provider}` 里，**全集群共享、按 provider 维度**（score = 过期时间戳，`ZREMRANGEBYSCORE` 实现崩溃后许可自动回收）。
- **`12 ÷ 4 = 3`** → **4 是「全局并发额度 ÷ 期望实例数」的结果**。3 实例 × 4 消费者 = 12，恰好用满。

**三种实例数的后果（已画图）**：

| 实例数 | 消费者总数 | 结果 |
|---|---|---|
| 2 | 8 | 4 个额度用不到 → 浪费 1/3 许可 |
| **3** | **12** | **正好用满** |
| 4 | 16 | 4 个消费者必然抢不到 → 绕 5s 延迟队列重试 |

**速率限制的配合**：`requests-per-minute:60` = 全集群 1 次/秒。Little's Law 验算：λ=1/秒、W≈20 秒 → L=20 个并发 > 12 → **并发（12）是紧约束，速率是松约束**。稳态吞吐 = 12 ÷ 20 = **0.6 次/秒 = 36 次/分**，距 60 次/分上限约 1.67 倍余量 → **速率限制只在突发时起作用**。

**`burst-capacity:4` 不是随手填的**：令牌桶容量 4 恰好 = 单实例消费者数。若容量 < 4，同一实例一轮同时启动的 4 个任务只有部分能立刻拿到令牌，其余立即失败退回重试，形成抖动。**容量必须 ≥ 单实例并发数。**

**✅ 修正上一轮「空转」的措辞**：`AiTaskRunner:82` 的 `if (acquired.isEmpty()) return ExecutionResult.retry(5, "provider_capacity_exhausted")` 发生在 **`:85` `markRunning` 之前** → **不消耗 `attemptCount`、不递增 `executionToken`**。所以额度不足是**干净的重试**，不会把任务的重试次数耗光，也不会留下半执行状态。真实代价仅：一条消息绕 5 秒延迟队列的 MQ 开销 + 一次 `selectById`。

**为什么不是更大/更小**：
- 更大（如 16）：超出全局 12 → 必然有消费者抢不到，白做一轮 DB 查询；本机在途上限也升高（内存、DB 连接）
- 更小（如 2）：要 6 个实例才能填满 12 → 部署成本上升；单实例在途只有 2
- 4 是让「单实例并发」整除「全局额度」的值，且 3 实例是常见的中小规模部署

**⚠️ 耦合隐患（可挑刺点）**：`teacup.ai.worker.lease-seconds:300` **同时驱动两个语义不同的租约** —— ① `AiExecutionLimiter` 的**许可租期**（Redis ZSET score，进程崩溃后许可自动回收的兜底）② `AiTaskRunner` 的**任务执行租约**（判定执行者死活的依据）。改一个会同时改另一个；若将来要给上游许可配不同租期，必须先把配置项拆开。

**面试口径**：
> 「这个数是一个配置项，默认 4，同时驱动消费者数、线程池大小和预取的在途上限，保证三者不会错配。取 4 的依据是上游的并发额度：限流器按 provider 在 Redis 里维护一个全局并发额度，默认 12，全集群共享。每实例 4 个消费者乘以 3 个实例正好是 12。实例少一个额度用不满，多一个就有消费者抢不到额度、只能退回延迟队列重试。速率限制是每分钟 60 次，用 Little's Law 算一下 1 次每秒乘 20 秒执行时间等于 20 个并发，比并发额度的 12 更宽松，所以并发才是真正的紧约束。抢不到额度那一次是在抢执行权之前返回的，不消耗重试次数，是干净的重试。」

## 21:42 纠正「生图消息都放在主队列、推给 4 个消费者」

用户理解：**一半对**。

**✅ 对的部分**：主队列是消息的**落脚点**，正常消费也确实发生在主队列上。

**❌ 错的一半：消息在生命周期里会离开主队列。** 三条出口：
1. **执行成功** → `basicAck` → 消息被删除（不在主队列了）
2. **需要重试** → 消费者先 `basicAck` 原消息，再用 `publishRetry` 发**一条新消息**（`AiTaskConsumer:40`，`UUID.randomUUID()` 生成**新 eventId**）到 **延迟队列（5s/30s/120s，没有消费者）**；TTL 到期后经死信路由**回流主队列**
3. **重试耗尽 / 消息格式错误** → 进 DLQ

**🔴 关键事实：同一个任务对应多条消息。** 每次重试都是**一条全新消息**（新 eventId）+ 同一个 taskId。所以「生图消息」这个说法要么指「某一次投递」，要么指「某个任务的消息链」——不能混。这也正是 outbox 表要按 1:N 设计（前面 15:36 那节的结论）在 MQ 侧的对应现象。

**❌ 「推给 4 个消费者」也有两处不严谨**：
1. **4 是「每实例」**，3 个实例 = 12 个消费者在同一个队列上轮询竞争；
2. **推给消费者 ≠ 被消费者执行**。消费者接到消息后还要过三道挡板（终态 / 未到重试时间 / 已被别人持有），再抢上游许可、抢执行权；任何一步不通过都退回延迟队列。**消息分发与任务归属是彻底解耦的两件事**——这正是前面（20:30 节）说的「不依赖消息落在哪个实例」的设计价值。

**稳态 vs 积压**：稳态下主队列里通常**只有很少的消息**（消费者立刻领走，在途上限 = `prefetch 1 × 4` = 4）；只有积压时才堆起来（无 `x-max-length`）。**延迟队列是中转站，不是处理队列**——它没有消费者，唯一的作用是"让消息等 TTL 然后自己变成死信回去"。

**精确说法**：AI 生图任务的**每一次投递**都以主队列为落脚点，但一条投递会因重试而离开主队列、在延迟队列里换一个新身份再回来；**任务**从头到尾只有一条，**消息**可能有好几条。

## 21:55 精读消费者异步执行的完整流程（`AiTaskRunner` 全文 + `AiTaskService` 各出口）

**主干 7 段（`AiTaskRunner.run:64-133`）**：

1. **快照 + 三道挡板（`:65-75`，不加锁的读）**：① null 或终态 → ack 吞掉 ② `queued && nextAttemptAt > now` → `retry(retryBucket(remaining))` ③ `running && leaseUntil > now` → `retry(5,"task_already_claimed")`。**都是读快照判断，真正的互斥留到第 3 步用条件更新做** —— 大部分重复消息在这里被廉价挡掉。
2. **抢上游许可（`:76-82`）**：`limiter.tryAcquire(provider)`；抛 `AiLimiterUnavailableException` → `retry(5,"limiter_unavailable")`；返回 empty → `retry(5,"provider_capacity_exhausted")`。
3. **抢执行权 `markRunning:173-179`**（独立事务）：`claimForExecution` 条件更新，成功后再 `selectById` 拿带**新 `executionToken`** 的行；失败 → `handleClaimFailure:139-147`（若是 `queued && attempts >= maxAttempts` 则 `exhaust` 终态化，否则 `retry(5)`）。
4. **加载输入 + 调上游（`:89-95`）**：`executionToken = token(task)` —— **先把令牌记下来**；按需查原图/参考图（纯文生图不查库）；`providerUrl()` 走 `storage.temporaryUrl(objectKey)`（**预签名临时 URL，不是公开 URL**）；`provider.execute(...)` —— **唯一的长阻塞点（约 20 秒）**。
5. **落库前校验租约（`:97`）**：`renewLease:181-186` 条件更新（`id + workerId + executionToken` 三者匹配），不匹配抛 `AiTaskLeaseLostException` → 外层 `:109` 捕获 → log.warn + **ack（刻意不调 fail——任务归属已不属于本实例）**。**这是栅栏令牌的实际使用点。**
6. **检查取消（`:98`）**：`isCancelled` → 返回 ack —— **上游已经花过钱了，结果直接丢弃**。注意 `isCancelled:290-292` 把 `task == null` 也算作已取消。
7. **存图 + 终态化（`:99-107`）**：查用户 → 取个人空间 → `storeResult:149-165`（Base64 解码 / `importUrl`）→ `saveGeneratedPicture` 建 picture 行 → `complete:188-207`（独立事务，`FOR UPDATE` 锁行 + **三重校验** status/workerId/token）→ 不通过则 **`discardGeneratedPicture(picture)` 补偿删除**。

**`retryBucket:226-228`**：把任意剩余秒数归到 5/30/120 三档 → **复用现成的三个延迟队列，不需要第四个**。取整只可能"晚到"不会"早到"（因为 `setNextAttemptAt` 用的是同一个 `delaySeconds`，两者自洽）；时钟漂移导致早到时只会再绕一轮同档桶，收敛。

**异常三条归宿**：

| 异常 | 处理 |
|---|---|
| `AiTaskLeaseLostException` | ack，**不碰任务**（归属已转移） |
| `AiProviderException` | ① `provider_permission_denied` 且有 modelId → **`disableModel:283-288` 自适应熔断下架该模型** ② `retryable()`(rate_limited / timeout / http_5xx) 且 `attempts < maxAttempts` → `retry(...)` 改回 queued + nextAttemptAt → 返回 retry → 消费者发新消息 ③ 否则 `fail(...)` 终态 + 归还配额 |
| 其他 `RuntimeException` | `fail("result_persistence_failed")` |

**🔴 一处细致设计**：`provider_network_error` 被**改写成 `provider_outcome_unknown`**（`:125-126`）。网络错误时**无法确定上游是否已经出图**，不能当"确定失败"处理；且它**不在 `retryable()` 里** → 直接 fail，不重试。这个 code 命名直接表达了不确定性语义。

**配额终态流转**：成功 → `settleQuota`（reserved−cost，used+cost）；失败/耗尽 → `finalizeQuota(refund=true)`（reserved−cost）。都带幂等标记（`quotaSettled` / `quotaRefunded`）+ 写 `ai_task_quota_audit` 审计行。

**长耗时期间持有什么（已画图）**：调上游的约 20 秒内 —— **持有** 1 个上游并发许可 + 任务归属（workerId / token / leaseUntil）；**不持有**数据库连接、不持有任何行锁。DB 只被 4 个短事务触碰：`markRunning` / `renewLease` / 存图 / `complete`。

**可挑刺点**：
1. **`discardGeneratedPicture` 失败会留下孤儿图片**：它抛异常会被 `:129` 的 `RuntimeException` 捕获 → 调 `fail`（但此时任务多半已属别人，`ownedBy` 校验返回 false，无害）→ **对象存储里那张图没人删**。缺孤儿文件清理兜底。
2. `retryDelay(attempts)`：attempts≤1→5s、==2→30s、否则→120s；`maxAttempts=4` → **实际最多重试 3 次（总尝试 4 次）**，延迟序列 5/30/120。前端展示"重试次数"时要与这个口径对齐。

**面试口径**：
> 「整个执行流程的排布原则是：**把便宜的检查放在前面，把昂贵的动作留在最后，昂贵动作之后再校验一次才落库**。前半段是三道挡板加抢许可、抢执行权，全是毫秒级的判断和条件更新；中间是唯一的长耗时操作——调上游，大约二十秒，这期间不持有数据库连接也不持有行锁，只占一个上游并发许可和这个任务的归属；调完之后不直接落库，先按执行者标识和令牌做一次条件更新确认租约还在自己手上，通过了才存图、才把状态改成成功。之所以要这一步，是因为租约可能在这二十秒里被判过期、任务被别人接管了，这时候旧结果的令牌对不上，必须丢掉。失败按三类分：租约丢失就什么都不做，因为任务已经不是我的；上游错误里可重试且没超过次数上限的走退避重试，通过延迟队列发一条新消息；其余的终态化并归还配额。所有配额的终态流转都收敛到一个出口，靠任务上的标记做幂等。」
