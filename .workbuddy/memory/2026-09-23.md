讲清楚的几个点（文档里没写全、以后可复用）：

- **三条独立时间尺度**：消息存活时间（传输层）→ 下次可尝试时间（业务层）→ 租约到期时间（执行权层）。任一失效另两层仍挡得住，三层都盖不住才轮到旁路兜底。
- **异常三类去向的判据不是"成功/失败"，而是"上游到底收没收到请求"**：明确回话的失败可重试；连接层异常（请求可能已被接单）判「结果未知」直接终态化；终态/易主/取消/格式坏属"本来就该忽略"。
- **重试消息的事件编号会换新**，它不是幂等键，只是日志追踪用；真正确保"同一条消息只执行一次"的是数据库状态机。
- **重投不走拒收重入队**，而是发延迟队列 + 确认原消息（拒收重入队会形成热循环空转）。
- 落库顺序是「先外部存储、后数据库终态化」，所以终态化校验失败必须回头删掉已写的图，否则留孤儿对象。

## 前置三道拦截（run 方法开头的三个判断）

共用同一次任务快照读（一次主键查询、不加锁），三次纯内存比较：

1. **终态拦截**：任务行不存在或已成功/已失败/已取消 → 确认应答、就地丢弃。覆盖重复消息（发布确认后崩溃、恢复服务与重试队列各投一份）和「已取消」分支，不需要单独写取消判断。
2. **未到期拦截**：排队中且下次可尝试时间晚于现在 → 算剩余秒数就近取档（5 / 30 / 120 秒）重投。挡的是「消息到达时间早于业务允许时间」——拒收重入队、延迟队列存活时间到期与数据库时间戳的偏差。就近取档导致实际等待恒 ≥ 业务要求，宁可晚不可早。
3. **占用拦截**：执行中且租约未到期 → 固定 5 秒重投。防同任务多副本被不同实例同时消费。用固定 5 秒而非按剩余租约算，是拿「高频轻量重试」换「低延迟感知状态变化」；租约已过期则放行，这正是恢复服务的入口。

四条设计原则：顺序按代价排且共用同一次查询；全部在获取上游并发许可之前（否则废消息会挤掉真任务产能）；三道都只读不写，天然幂等；**拦截是尽力而为，正确性由后续的条件更新与执行令牌保证**，前置检查只是性能优化。

两道易混边界：三道拦截**不含限流**（限流是第四步）；抢执行权是第一个写操作，其失败分支（尝试次数耗尽则终态化归还额度，否则 5 秒重投）不属于前置拦截。

## RabbitMQ 仲裁队列（quorum queue）讲解

- 概念：基于 Raft 共识协议的复制型队列，多数派（N/2+1）落盘后才回发布确认；经典镜像队列已在 RabbitMQ 4.0 移除，要做复制队列它基本是唯一选项（另一个是流式队列，定位不同）。不适合临时队列、高频声明删除、极低延迟、五百万条以上超大堆积。
- 项目实况：`docker/compose.yml` 用 `rabbitmq:4.1.8-management-alpine`，**单节点**。组大小退化为 1，多数派即自身，**本地复制容错为零**。声明仲裁队列的价值在于：将来扩多节点不用改队列声明，以及拿到仲裁队列独有的「至少一次死信」「毒消息处理」。
- 已核实两个参数必须配套：`x-dead-letter-strategy: at-least-once` **要求**溢出策略为「拒绝新发布」（默认的「丢弃队头」会让它静默退回至多一次）。项目里两者都设了，配置自洽。代价：多一个内部死信消费者进程（与领导者同节点）、消息体驻留内存、可能重复投递——死信消费端必须幂等，现实现是先判终态，成立。
- **发现一处缺口（待确认是否要修）**：设置了溢出策略但**没有设置队列长度上限**（无 `x-max-length` / `x-max-length-bytes`），因此溢出策略目前是空转的。官方对「至少一次死信」的最佳实践明确要求配上长度上限，否则死信消息（在目标队列确认前仍算存活）可能把源队列堆满。

## 三问讲解（额度结算 / 废消息来源 / 双闸限流）

- **额度记账**：已占是过渡态、已用是终态。结算 = 已占−、已用+，**不重判上限**——预占即锁定，并发判定已前移到提交时刻，结算路径因此退化为纯记账。归还 = 只减已占。已用只增不减，跨天靠「新日期新行」自然重置，不需要定时清零任务。结算动的是**任务创建日**那一行（23:59 提交、00:02 完成，扣前一天）。
- 已确认：`finalizeQuota` 只改内存对象、**不写 `ai_task` 行**，由调用方在同一事务里落库——所以「改额度行」与「改幂等标记」是一个原子提交，否则会出现「额度已归还但标记未写」导致对账重复归还。
- **废消息八种来源**：投递器双投窗口、恢复链路与在途消息撞车、重试消息与原消息并存、拒收重入队绕过时间约束、延迟队列 TTL 早到毫秒级、同任务被两个并发消费者同时取到、取消后仍在途、已失败但重试消息在路上。
- **拦截必须在拿许可之前**的理由是三级成本差：一次主键查询 + 三次内存比较 → 一次 Redis 原子脚本 → 一次带条件更新。先拿许可再判断，一条废消息会占住许可最长 300 秒。
- **双闸是两个维度**：并发许可=同时在飞数（护上游连接数），速率令牌=平均速率（护调用配额）。只做并发：请求耗时 100 毫秒时一分钟可发 2400 个；只做速率：上游变慢时会攒出 60 个在飞连接。顺序先并发后速率，因为并发名额的释放是显式零成本的，令牌扣掉只能等惰性补充。
- **发现一处可挑刺点（已核实，全仓库 grep）**：并发许可对象上定义了「续期」方法但**没有任何调用点**。即单次调用超过许可租期（300 秒）时许可会中途失效、并发上限被短暂突破；当前靠「上游 HTTP 超时 120 秒 + 落盘数秒远小于 300 秒」兜住。属「主动说比被问出来好」的已知边界。
- 并发许可用随机标识而非「实例:线程」的原因：同实例同线程短时间可能连续申请，固定标识会互相覆盖。

## 结算点的精确定位 + 许可存储方式

- **结算发生在「终态化」那一步的事务里**，和「状态改成成功、写结果图主键」是同一次数据库提交，不是事后补的、也不是独立定时任务。在此之前额度一直挂在「已占」上，第一次真正动「已用」就是任务被标记成功的那一刻。
- 全链路只有六个动额度的地方：提交时预占 1 个；结算 2 个（成功终态化、取消但已发起调用）；归还 4 个（失败、次数用尽、取消且未发起调用、死信）；对账补正复用结算与归还。**重试不动任何计数**。
- **修正一处他的理解**：并发许可不是「同时生成图片的线程数」，而是「同时处于处理中的任务数」。许可作用域是 try-with-resources 包住的整段（抢占 → 调上游 → 续租 → 落盘 → 终态化），全程占名额，不只是调上游那几秒。
- 许可数量 12 是**全局跨实例**的；单实例上限是工作线程数 4；12 需要至少 3 个实例才能同时用满，实例再多就会有实例长期抢不到而重投。4 × 3 = 12 是配套关系。
- 许可存两处：Redis 有序集合（权威状态，成员=随机标识、分值=到期时刻、个数=占用数）+ 进程内许可对象（只是凭据：键名、标识、防重复释放的原子标志）。回收靠「按分值范围删过期成员」，所以不需要登记持有者。
- **令牌桶惰性补充的走查数字**（容量 4、每分钟 60）：refill = 0.001 个/毫秒，装满一桶 4000 毫秒，键过期时间取 8000 毫秒。前 4 次吃掉初始满桶（突发），之后每 1000 毫秒补 1 个（稳态）。
- 令牌桶最易漏的一步：**被拒绝时也要写回新的令牌数与时间戳**，否则下次会拿同一个「上次更新时间」重复补充同一段时间，速率失效。
- 已知副作用（可主动说）：空闲超过 8 秒键过期、突发额度重置；但 `min` 封顶仍在，攒再久也只能攒 4 个。

## 许可的进程内形态 + 速率令牌不是「派发」

- **他卡住的根因**：把速率令牌类比成并发许可。两者是**占用型 vs 消耗型**两种语义，四个维度都不同：Redis 结构（有序集合 vs 哈希）、存什么（谁占着+何时到期 vs 一个余量数字+时间戳）、有无实体占用（加成员 vs 数字减 1）、要不要归还（必须 vs 不需要）。
- 这张对照表还能解释一个他被绕住的点：许可对象里**只记并发键、不记速率键**——速率令牌用完即弃，没有凭据要留。
- 两道闸的失败处理**不对称**是语义差异导致的：并发没过时不碰速率键（无需撤销）；速率没过时要 `ZREM` 撤销已占的并发名额（因为并发名额是先占的且必须显式归还）。
- **进程内没有任何集合在「存」许可**。许可就是那个 `Permit` 对象本身：非静态内部类，三个字段 = Redis 键名 + 36 字符随机标识 + 防重复释放的原子布尔。它挂在执行线程调用栈上（`try (…)` 语句），生命周期 = 一个 try 块，出块自动 `close()`。判定"还能不能拿"完全在 Redis 做，进程内不需要知道全局用了几个——否则 4 实例各以为有 12 个名额，实际能跑 48 个。
- `closed` 原子标志的两个价值：close 幂等（省一次 Redis 往返）；**已释放的许可拒绝续期**。
- 真正兜底的是租期而非释放：释放失败时异常被吞掉，因为成员分值（到期时刻）早写死，300 秒后由下一个申请者顺手清掉。这就是它能容忍进程被强杀的原因。
- 他问的「怎么派发」在实现里**不存在**：申请即扣减、扣减即放行，没有中间分发环节。控制速率的本质是「收支平衡」——补充速率即允许消耗速率（每秒补 1 个 → 每分钟 60 个），桶容量即允许的短期透支。

## 「速率令牌怎么控制速率」的讲法（已定稿）

一条恒等式加两个不等式就是全部机制：

```
任意时刻真实余量 R(t) = min(容量, 上次快照余量 + (t − 上次快照时刻) × 每毫秒补充量)
放行条件 R(t) ≥ 1，放行后 R ← R − 1
```

- 不等式一「消耗只能从余量里扣、余量不为负」→ 长期消耗量 ≤ 长期补充量 → **稳态速率 = 补充速率**
- 不等式二「补充被 `min` 封顶」→ 短期消耗量 ≤ 容量 + 期间补充量 → **突发上限 = 桶容量**

三种运行状态（讲这个比讲公式有效）：需求 < 供给时池子趋于满、**限流器完全不起作用**；需求 = 供给时全部放行；需求 > 供给时池子被抽干，此后节奏被补充速率锁死。

**累计曲线讲法**（已产出图）：横轴时间、纵轴累计个数，需求线与放行线的**斜率差就是被拒绝的量**；放行线在吃掉初始积蓄后斜率陡然变缓并锁死在 1 个/秒。

惰性求值的本质：进水是恒定线性的，所以"过去 347 毫秒进了多少"= 347 × 速率，用乘法算，不需要真的去一滴一滴加。类比复利。

精度：`tokens` **必须**是浮点。若存整数且只在补满 1 个时才加 1，请求间隔 100 毫秒时时间差恒为 100 → 补 0.1 → 取整 0 → 初始 4 个用完后永远拒绝。

**主动纠正了上一轮的一处表述**：上一轮说「被拒绝时也要写回，否则会重复补充同一段时间、速率失效」——**不准确**。放行时必须写回（扣减只能通过更新快照体现），但拒绝时写不写都正确，因为快照的余量与时刻是配对的，`tokens + (t2 − updated) × refill` 在两种记法下总量守恒。写回的实际价值是让快照保持新鲜、避免时间差累积过大。下次讲这里不要说成正确性必需。

## 陈同学自己推出的「桶容量导致超标」问题（他自己算对了）

他的推导：0 毫秒来 4 个取光满桶，之后每 1000 毫秒补 1 个取走 1 个，一分钟后共放行 4 + 60 = **64 个**，**超过每分钟 60**。**算账完全正确**，他这次是主动定量，值得肯定。

**我上一轮的表述要修正**：我说「长期偏差 0.1% 可忽略」，强调的是**长期均值**（跑一小时 3604 个 → 60.07/分钟）；他的质疑指向的是**任意 60 秒窗口内的峰值**（最多 64）。**这是两个不同的判据，他的质疑成立。**

结论与要点：

- 那 4 个突发**只在桶是满的时才存在**。持续高负载时桶长期贴近 0，稳态就是 60/分钟不超；只有「空闲后转繁忙」的转折点才会多放最多 4 个。
- 上游若是**严格滑动窗口**（任意 60 秒 ≤ 60），这 4 个会被拒。所以**配置 60 等于顶格配置、零余量，是真实风险**。正解是配得比上游上限低（上游 60 → 我们配 50~55），差额用来吸收突发、时钟偏差与统计窗口差异。
- **另一处更隐蔽的突发来源：键过期重置**。键不存在时 `tokens = capacity`（满桶），而过期时间 = 装满一桶时间 × 2 = 8 秒。定量算过：每 8 秒来一批、每批能放 4 个 → 每分钟 30 个，**不会超 60**（因为重置的代价是这 8 秒本该补的 8 个被浪费）。但如果把过期时间调小到 1 秒 → 每分钟 4 × 60 = **240 个，严重超发**。这解释了过期时间为什么必须取「装满时间 × 2」而不是随便一个值。

## 系统里六个不同的「过期时间」（他问「过期时间指哪个」）

**极易混，讲的时候必须点名是哪一个：**

| 名称 | 值 | 存在哪 | 谁清理 | 清理后的效果 |
| --- | --- | --- | --- | --- |
| 速率键的 TTL | **8 秒** | Redis 哈希键 | Redis 自动删键 | 键消失，下次调用当满桶（多 4 个突发） |
| 并发许可键的 TTL | 600 秒 | Redis 有序集合键 | Redis 自动删键 | 键消失，等于所有名额一次性释放 |
| 并发许可成员的分值 | 300 秒 | Redis 集合成员 | **下一个申请者按分数范围清**，不是自动删 | 该成员移除，释放一个名额 |
| 任务租约 | 300 秒 | MySQL 任务行 | 恢复服务每 30 秒扫描 | 任务回退为排队中 |
| 消息 TTL | 5 / 30 / 120 秒 | RabbitMQ 延迟队列 | RabbitMQ 死信回投 | 消息回到主队列 |
| 幂等键 | **永不过期** | MySQL 任务行唯一键 | 无 | 永久占用，客户端不得复用 |

- 关键区分：**键的 TTL 与成员的到期分值机制不同**。前者由 Redis 自动删键；后者不会自动删，靠「按分值范围删除过期成员」在下次申请时顺手回收。两者效果相似但原理不同，容易答错。
- 速率键的 TTL 是**每次取用都刷新**的（写回在判断之外，拒绝也会刷新），所以只有「两次请求间隔 > 8 秒」才会真正过期——恰好 8 秒时 TTL 已被刷新。
- 配置值推导公式：`我们的配置 = 上游真实上限 − 桶容量(4) − 时钟与统计窗口偏差(约 5~10%) − 同 key 其他消耗`。上游 60 → 约 50~54。改法是 `application.yml` 的默认值保持保守、`docker/.env` 按实际上游覆盖，并给 429 率加告警。

## 「为什么有 TTL」的答法（他问到的关键点）

核心：**补充是「算出来的」，不是「写进去的」**。惰性求值意味着没人访问就**没有任何动作发生**，键会静止不动永远留在 Redis 里 → 所以需要一个存储层的清理机制，这就是 TTL 的作用。二者不矛盾：逻辑补充管「有多少令牌」，TTL 管「这个键还要不要留」。

推论：**TTL 只在空闲时起作用**。TTL 是「最后一次访问 + 8 秒」，且每次取用都刷新（拒绝也刷新），所以有流量时键永不过期（间隔只要 < 8 秒）。

为什么这个键可以安全丢弃（对比并发许可键）：速率键丢了只是「下次当满桶、多 4 个突发」，不会让速率失控；并发许可键丢了则等于所有持有点瞬间释放、实际并发可突破上限，所以它的 TTL 更长（600 秒 > 成员租期 300 秒），保证键不会在有持有者时消失。

## 「TTL 为什么要 × 2」——他的直觉是对的

他质疑「4 秒后桶就满了，为什么还要留到 8 秒」。**结论：功能上 TTL ≥ 装满时间就够了，× 2 是工程余量。他的直觉没错。**

但那条下界是**硬的**，不能更短。反例（容量 4、速率 60/分钟、装满需 4000ms，若 TTL 取 2000ms）：抽干桶后 2000ms 键过期，此时**桶的真实水位只有 2**，但因为键不存在会被当成满桶 4 → 放 4 个，**凭空多出 2 个额度**。所以下界是「桶从任意水位涨到满所需的最大时间」，即 `capacity / refill`。

× 2 的余量防三件事：① `capacity / refill` 是浮点除法再向上取整，参数一变就有微小偏差；② 防止后人只改容量或只改速率、把「TTL > 装满时间」这个不等式破坏掉；③ 在代码里显式表达「这里有意留了一倍余量」，避免被当成冗余优化掉。

**一个关键对比（两处 TTL 都是 ×2，但必要性不同）**：

| | 公式 | 那个 ×2 是必需的吗 |
| --- | --- | --- |
| 速率键 TTL | 装满一桶时间 × 2 | **不是**。1 倍即可，过期后结果与「桶满」等价（都是满桶），没有损失 |
| 并发许可键 TTL | 成员租期（300 秒）× 2 | **是**。若 TTL 等于租期，会出现「键先于成员租期过期」→ 键被删 → 所有名额瞬间消失 → 有持有者在跑但名额没了 → 并发失控 |

这是回答「为什么 ×2」最好的落点：不是随口乘的，而是「TTL 必须大于数据失去意义所需的时间」，只不过其中一处的不等式是硬约束、另一处只是余量。

## 「上游调用很慢，怎么保证线程活着」——先纠概念

**他的措辞是「线程一直监听」，实际不是监听、不是轮询、不是回调，而是同步阻塞调用。** 工作线程调 HTTP 接口后阻塞在 socket 读上，直到上游返回或超时。所以「保证线程活着」这个问题本身不存在，它被 HTTP 超时兜住了。

一次上游调用期间有**四条时间线**（已产出图），各管一件事：

| 设置 | 值 | 解决什么 |
| --- | --- | --- |
| 上游调用超时 | 120 秒 | 线程不会无限阻塞在 socket 上 |
| 续租节拍 | 90 秒 | 声明「我还活着」，租期不到期 + 快速感知失联 |
| 任务租期 | 300 秒 | 进程挂了能被别人接管（到期未续租则任务被收回） |
| 优雅停机等待 | 180 秒 | 关闭时给正在跑的任务收尾时间 |

**硬不等式：租期 > 上游超时 + 落盘时间。** 违反的后果是正常调用还没结束租约就过期 → 别的实例把任务抢走 → 同一任务被两个实例同时执行、上游被调用两次、成本翻倍。

**续租周期取租期的 1/3（90 = 300/3）的理由**：要容忍**连续两次**续租失败（网络抖动、数据库短暂不可用）才真正到期，第三次没续上才被回收。300 − 90×3 = 30 秒余量。与刚才 TTL 的 ×2 是同一类「不变量旁留余量」的思路。

**两种「超时」必须分开讲（呼应「上游到底收没收到请求」这条判据）**：
- 上游**明确回话**「我超时了」（HTTP 408/504）→ 错误码 `provider_timeout` → **可重试**
- 我们**自己等不住断开**（socket 读超时）→ 错误码 `provider_network_error` → 改写成「上游结果未知」→ **不可重试**（可能已被接单计费）

**消息层重投不构成问题**：RabbitMQ 没有 ack 超时（不像 SQS 有可见性超时），只要连接在就一直认为在处理中。连接断了会重投，但此时任务状态是执行中 + 租约未过期，会被「占用拦截」挡住返回 5 秒重投。**任务行上的状态机 + 租约才是真正的判据，消息层只是载体。**

## 「重置 vs 累加」的讲法（次日补讲）

续租是 `leaseUntil = now + 300`（重置），不是 `leaseUntil = leaseUntil + 300`（累加）。时间线对比（续租器每 90 秒一次）：

| 时刻 | 重置语义下的 leaseUntil | 累加语义下的 leaseUntil |
| --- | --- | --- |
| 0（抢占时初值） | 300 | 300 |
| 90 | 390 | 600 |
| 180 | 480 | 900 |
| 270 | 570 | 1200 |

看不出差别的原因：正常节奏下两者都在往后推。**差别在第 270 秒的"距当前时刻"：重置是恒定的 300 秒，累加已经涨到 930 秒。**

**反例才是关键**：如果续租触发变得频繁（定时器重入、集群里多实例都以为自己该续、手动触发），累加语义下 leaseUntil 会迅速膨胀 —— 每秒续一次，1 分钟后就推到 `now + 18000 秒`（5 小时）。**此时进程真挂了，任务要僵 5 小时才会被回收，恢复服务形同虚设。**

**结论**：`leaseUntil` 的语义是「别人可以接管我的时间点」，它是一个**兜底上界**，不是「任务的总时长」。重置语义保证「距当前时刻恒为 300 秒」，于是回收延迟**有界**（[0, 300] 秒）；累加语义让回收延迟**无界**。

**类比**：这是看门狗（watchdog）的喂狗语义 —— 每次喂狗是**重新计时**，不是在原有超时上加时间。如果在原有基础上加，狗就永远咬不到你了。所有依赖方（恢复服务扫描、其他实例的占用拦截）都假设 leaseUntil 不会太远，重置语义是这个假设成立的前提。

## 从全局限流开始的完整链路 + 每步兜底（已讲）

按「步骤 / 正常动作 / 失败时谁接管」讲，用任务 1024 做例子串。七个步骤与对应兜底：

1. 拿 Redis 许可 → 拿不到就 5 秒重投；进程崩了靠许可租约 300 秒自愈
2. 原子抢占执行权 → 抢不到：已终态就丢弃 / 排队中且次数用尽就终态化归还 / 其余 5 秒重投
3. 调上游 → 可重试回排队 + 延迟消息；不可重试或次数用尽则失败归还；连接异常判结果未知不重试
4. 落库前确认租约 → 失败只确认不置失败（归属已丢，由恢复服务重新入队）
5. 取消检查 → 已取消则丢弃结果、图片不落库
6. 结果落盘 → 抛异常走「结果落盘失败」置失败；终态化校验不过则回头删图与对象
7. 终态化 + 结算（同一事务）→ 三要素不匹配即回滚已落盘内容

横切兜底四条：进程崩溃靠租约过期 + 恢复服务（30 秒扫）；消息进死信靠死信消费者；事件链路全漏靠额度对账（10 分钟扫）；优雅停机等 180 秒。

## 四个追问的澄清（续租语义 / 抢占表 / 超时后果 / 确认租约）

**①「续租器一直续，岂不是永不到期」——对，那是意图，但暴露一个真实缺口。**

只要续租器活着，租约确实永不到期。关键在于：**续租器跟着进程一起死**，所以"永不到期"只对活着的进程成立，而活着的进程本来就不该被抢任务。

**但边界在于：租约检测的是「进程存活」，不是「任务在推进」。** 如果线程假死（死循环、卡在不可中断的等待上）而 JVM 还活着 → 续租器照常续 → 租约永不到期 → 任务永远僵住。**而且对账也救不了它**：reconcile 里对「执行中且租约未过期」是直接跳过的。`running-timeout-minutes: 15` 只在 `leaseUntil IS NULL`（历史数据）时生效，不构成活跃兜底。

**这是可以主动说出来的已知缺口。** 改进方向：让续租器只续「有活跃迹象」的任务（记录上次进展时间）；或给任务加一个不受租约影响的「总超时」。

**② 原子抢占更新的表 = `ai_task`**，写入 `status` / `invocationStarted` / `attemptCount`(自增) / `executionToken`(自增) / `workerId` / `leaseUntil` / `startTime`，条件里带 `attemptCount < maxAttempts` 与「排队中且已到期 或 执行中且租约已过期」。

抢占失败（改到 0 行）后**再读一次最新状态**分三种：
- 已终态 → 直接丢弃消息
- 仍是排队中且 `attemptCount` 已达上限 → 就地终态化为失败（错误码 `attempts_exhausted`）+ **归还额度**
- 其余（被别人抢走/还在跑）→ 5 秒重投

**第三分支必须存在**：不终态化的话，任务仍是 queued 且已到期、次数已达上限 → 抢占永远失败 → 消息每 5 秒重投一次无限循环，且额度预占永久悬挂（没有任何终态事件会触发归还）。

**③ 上游 120 秒没返回 → SocketTimeoutException → 包装成 `provider_network_error` → 在 runner 里改写成「上游结果未知」→ 置失败 + 归还额度，不重试。**

「结果未知」的准确含义不是「上游失败了」，而是「**我们不知道上游那边的结果**」。上游可能收下请求并正在处理（甚至已经生成成功），只是比 120 秒慢。不重试的理由：若上游实际成功，重试会让它再生成一次、成本翻倍；我们无法区分成功与失败，只能取保守策略。**代价是用户白等（额度已归还），且上游若真成功，那张图就丢了。** 且因为超时时没读到响应体，我们连上游任务标识都没拿到，事后也无法去查询它。

**④「落库前确认租约」里的「落库」指的是「把结果图片写进数据库」，这一步本身是更新任务行。**

表：`ai_task`。数据：只把 `leaseUntil` 刷新为「当前 + 300 秒」。条件带 `id` + `status='running'` + `workerId` + `executionToken`。

**目的是用一次有条件的写同时完成「续租」和「身份校验」两件事** —— 改到 1 行说明我还持有，改到 0 行说明已被别人接管。比「先查再判」可靠，因为它原子。
