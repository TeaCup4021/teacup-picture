# 2026-09-24

承接 2026-09-23 的 AI 生图链路讲解（「重置 vs 累加」与「从全局限流开始的完整链路 + 兜底」两节记在 09-23 日志末尾）。本日澄清的四个结论：

## ① 租约「永不到期」是对的，但暴露一个真实缺口

续租器每 90 秒续一次、每次置为「当前 + 300 秒」，所以**只要续租器活着，租约确实永不到期 —— 这正是意图**。关键在于续租器跟着进程一起死，所以「永不到期」只对活着的进程成立，而活着的进程本来就不该被抢任务。

**但边界在于：租约检测的是「进程存活」，不是「任务在推进」。** 线程假死（死循环、卡在不可中断的等待）而 JVM 还活着 → 续租照常 → 任务永远僵住。

**而且对账救不了它**：`reconcile` 对「执行中且租约未过期」直接跳过；`running-timeout-minutes: 15` 只在 `leaseUntil IS NULL`（历史数据）时生效，不构成活跃兜底。**这是可以主动说出来的已知缺口。** 改进方向：续租器只续「有活跃迹象」的任务（记录上次进展时间）；或给任务加一个不受租约影响的「总超时」。

## ② 原子抢占的表与失败分支

表 = `ai_task`。写入 `status` / `invocationStarted` / `attemptCount`(自增) / `executionToken`(自增) / `workerId` / `leaseUntil` / `startTime`，条件含 `attemptCount < maxAttempts` 与「排队中且到期 或 执行中且租约过期」。

失败后**再读一次最新状态**分三种：已终态→丢弃；仍是排队中且次数已达上限→**就地终态化 + 归还额度**（错误码 `attempts_exhausted`）；其余→5 秒重投。

第三分支必须存在，否则：任务仍是 queued 且已到期、次数已达上限 → 抢占永远失败 → 消息每 5 秒重投无限循环，且**额度预占永久悬挂**。

## ③ 上游 120 秒未返回的完整后果

SocketTimeoutException → 包装成 `provider_network_error` → 在 runner 里**改写成「上游结果未知」** → 置失败 + 归还额度，**不重试**。

「结果未知」不是「上游失败」，而是「**我们不知道上游那边的结果**」。上游可能正在处理甚至已经成功，只是慢于 120 秒。不重试的理由：若上游实际成功，重试会让它再生成一次、成本翻倍；无法区分就只能取保守策略。代价是用户白等（额度已归还），且若上游真成功那张图就丢了 —— **因为超时时没读到响应体，连上游任务标识都没拿到，事后也无法查询**。

## ④「落库前确认租约」的准确含义

「落库」指的是「把结果图片写进数据库」，这一步本身是**更新任务行**：表 `ai_task`，只把 `leaseUntil` 刷新为「当前 + 300 秒」，条件带 `id` + `status='running'` + `workerId` + `executionToken`。

**目的是用一次有条件的写同时完成「续租」与「身份校验」两件事**：改到 1 行说明我还持有，改到 0 行说明已被接管。比「先查再判」可靠，因为它原子。

## 恢复服务流程 + 四个追问的答案

**先纠正他的一处口误**：他说「进程被强杀、续租器跟着死、租约永不过期」——字面正好说反了。**续租器死掉 = 没人续租 = 租约 300 秒后到期**，恢复服务正是靠这个接管。

**恢复服务流程**（`AiTaskRecoveryService` + `AiTaskOutboxService.recoverExpiredTask`）：

1. 启动延迟 30 秒，之后 `fixedDelay` 每 30 秒跑一次（是「上一轮结束后隔 30 秒」，不是固定频率）
2. 扫 `status='running' AND (leaseUntil <= now OR (leaseUntil IS NULL AND startTime <= now-15分钟))`，按 id 升序、一轮 50 条
3. 逐条**独立事务**处理，锁行后**必须二次校验**（状态还是 running 吗、租约确实过期了吗）——扫描用的是快照，处理时可能已被续租或已被别的线程回收
4. 写入：回退为 `queued`、清 `workerId` / `leaseUntil`、`nextAttemptAt = now`、`failureCode = worker_lease_expired`
5. **不递增 `attemptCount`、不归还额度**（这不是一次失败尝试，也不是终态；额度继续挂着预占）
6. **同一事务内插入一条新的发件箱事件** → 投递器把它投回队列 → 别的实例重新抢占

**最大尝试次数 = 4**（`AI_WORKER_MAX_ATTEMPTS`，默认 4），含义是「实际调用上游的次数上限」。`attemptCount` 只在抢占时递增。

**栅栏令牌为什么不能用限流时拿到的标识**——职责与可靠性都不同：

| | 限流许可标识 | 栅栏令牌 |
| --- | --- | --- |
| 解决什么 | 多实例共享配额，怎么释放自己那一份 | 同一任务被多次抢占，谁是当前合法执行者 |
| 存在哪 | Redis（有序集合成员） | MySQL 任务行 |
| 生命周期 | 一次执行，用完即删 | 随任务存续到终态 |
| 丢了会怎样 | 多一个名额被占，租约到期自愈 | **执行权判定失效，旧执行者能覆盖新结果** |

核心：**限流令牌不在数据库里，任务行的更新语句无法在一次 SQL 里比对 Redis 的值**；而且 Redis 一抖（重启/过期）就全失效，执行权判定不能建立在这种可靠性上。自增而非随机数的实际价值是「有序」——能表达新旧，便于排查。

**「5 秒后重投」重投的是什么、投到哪**：**发一条新消息到延迟队列 + 确认原消息**（不是 requeue 原消息）。新消息体是 `{新的随机事件标识, 原任务标识}`，在延迟队列躺 5 秒 → TTL 到期 → 死信回主队列 → 重新被消费。用 `new UUID` 作事件标识是因为它是「新的事件」；事件标识只用于日志追踪，不是幂等键。**唯一的 requeue 场景**是「重试消息发不出去」时 `basicNack(requeue=true)`，那是防丢消息的兜底。

**「生图本身就需要 > 120 秒」这个矛盾他抓对了**：当前配置下这类任务**永远无法成功**，每次都是超时 → 结果未知 → 失败。必须调大 `OPENAI_IMAGE_TIMEOUT_MS`，但调大要级联复核：文档明确写「租期必须大于 Provider HTTP 超时与结果落盘时间之和」，所以超时调大 → 租期也要调大（续租周期只要满足 ×3 ≤ 租期即可保持）。**注意代码里的启动强校验只有「续租周期 × 3 ≤ 租期」这一条，没有校验「超时 < 租期」** —— 后者只是文档约定。真正的正解是上游改成「提交返回任务标识 + 轮询结果」的异步模式，当前用的同步接口注定要长时间阻塞。

**「落盘前校验身份」的价值 = 提前止损，不是正确性保证**（与「三道只读拦截是优化、条件更新才是正确性」是同一个模式）。落盘要写对象存储（几 MB IO）+ 建图片行 + 更新空间用量 + 建版本记录，若租约已丢则全部白做且还要再删一遍，中间还有「图片已存在但任务未终态化」的脏数据窗口。**终态化时的那次三要素校验才是权威的那一道**，不匹配就回滚。两道校验的分工：前一道省钱省时间，后一道保正确。

**线程假死的兜底方案**（当前确实没有）：推荐「总超时」而非「续租前检查活跃迹象」——后者要在执行路径多处埋点，前者语义清晰（「这个任务最多跑 N 分钟」是业务约束，应当显式表达）。基准取值：单次超时 × 最大尝试次数 + 各次重试延迟之和（120×4 + 5+30+120 ≈ 635 秒），再留倍余量，取 20~30 分钟。要注意从「首次开始执行」起算，不能从 `createTime` 起算，否则会把排队时间算进去而误杀。

### 四个关键设计决策（面试可直接讲）

1. **两个计数器分开**：提交次数与查询次数各自计数、各自校验上限。共用一个计数器的话，一个仍在正常等待上游出图的任务会被「调用次数用尽」误杀。
2. **待查询不是失败**：回退为排队中、清执行者与租约，但**不写失败码、不归还额度、不动终态标记**——任务既没成功也没失败。
3. **等待期间释放执行权**：顺带解决了「等待时不占工作线程与并发许可」，以及「上游耗时可能超过 HTTP 超时上限」的问题。
4. **复用延迟队列做轮询节拍**，不引入新定时器或线程池；查询间隔须落在 5/30/120 三档之一，否则会被就近取档放大。

### 必须说清的前提（不要对外宣称「已经异步化了」）

当前上游是同步 Images API，**没有查询接口**，所以 `submit` 内部仍是阻塞等待，轮询分支在当前配置下**不会被触达**。收益（等待期间释放线程与许可、摆脱 120 秒硬限）需要上游提供「提交返回标识 + 按标识查询」才能兑现——届时只改适配器两个方法，执行器、状态机、兜底链路都不用动。

### 补充：查询本身要占上游配额（最易忽略的一点）

查询和提交一样要过限流双闸（占并发许可 + 消耗速率令牌），**每次查询都是实打实的一次上游调用**。一个任务轮询 36 次就占掉 36 次配额（而提交只占 1 次）。

算一下：10 个任务同时等待、间隔 5 秒 → 每秒 2 次查询 → 吃掉 60/分钟 配额的约三分之一。**这是「下游任务多」时的真实容量约束，也是轮询间隔不能设太短的根本原因** —— 不只是"省点资源"，而是会挤掉真正需要生成的任务的产能。

改进方向：递增退避（前几次快、后面慢），或推动上游支持结果回调（webhook）彻底免掉轮询。

## 讲解「多级缓存实现」（读源码 + 与设计文档对账）

按源码实况梳理了 `backend/src/main/java/.../cache/` 下的 20 个类，产出两张内联图（读路径判定链、事务性发件箱失效链）。设计基线文档是 `docs/cache-architecture-redesign.md`（已实现），旧的 `backend/docs/缓存设计与问题处理.md` 已废弃，只留作历史参考，**不可作为事实来源**。

### 真实架构（代码口径）

- 分层：浏览器/CDN（公开资源 60 秒 + 摘要校验，私有接口禁止存储）→ 本地一级缓存（Caffeine，权重上限 8 MiB）→ 共享二级缓存（Redis，JSON 信封）→ MySQL/MinIO。
- **只有两条读路径真的接入**：公开图库游标页（本地 5s / 软 10s / 硬 60s / 负值 5s）与公开图片详情（本地 10s / 软 30s / 硬 180s / 负值 15s）。等锁上限 150 ms、租约 5 s。
- 版本化命名空间：数据 key 带代数，失效 = 代数递增而非删 key，旧 key 靠物理 TTL 回收，全流程无扫描/通配符删除。
- 双代数校验：代数同时写在 key 与信封内，读时两者都必须等于当前代数（旧持有者写回旧代数 key 也读不到）。
- 单飞：进程内合并表 + Redis 分布式锁（拿不到锁则轮询共享缓存 25 ms × 最多 6 次，仍失败抛「缓存繁忙」→ 上层 503）。分布式锁本身不可用时退化成只做本机单飞。
- 失效：业务表更新 + 发件箱插入同事务；提交后钩子立即清本机（低延迟，失败仅告警）；发件箱每秒轮询、认领（30 s 锁租约）后发布，等确认应答才标记已发布，失败退避 1/2/4/8/16/32/60 s 封顶，已发布记录留 7 天。
- 幂等：Redis 侧按事件号做「仅在不存在时创建 + 7 天过期」占位，仅首次占位才递增代数（重复投递直接丢弃，代数单调）。
- 物理 TTL 恒大于硬过期时间并叠加 0~20% 抖动，保证「返回旧值 + 后台刷新」有效。
- **降级亮点**：代数读取失败时回退到本机最后已知值而非 0，否则全库 key 代数失配会造成雪崩。

### 发现的代码问题（文档与实现不符）

1. **失效范围退化**：设计文档要求「删除当前实例 L1 精确 key」，实现是 `localCache.invalidateAll()` 全清。批量审核时本地缓存持续归零，压力全给 Redis。
2. **刷新任务被拒绝会让 key 永久卡死（真 bug）**：异步刷新先在合并表占位、再提交任务；线程池核心=最大=2、队列=100、默认拒绝策略抛异常。提交失败时占位对象既不完成也不移除（移除逻辑在任务体内），此后该 key 所有请求都走等待分支 → 150 ms 超时 → 503，直到进程重启。
3. **消费者无重试上限**：处理失败即重新入队且未设最大次数；死信队列只接「队列溢出被拒收」，接不住无限重新入队。Redis 长时不可用会堆积。
4. 接入面比文档窄：文档表格里的「公开用户摘要」「标签分类字典」未接入，**不要对外宣称「全站多级缓存」**。
5. 小：`lastKnownGenerations` 这类回退表只在失效时清理，按图片数无上限累积（十万张约几 MB）。

## 追加：概念级澄清「版本化命名空间」

陈同学对上一轮讲的"失效不靠删 key"没吃透，单独追问。已用一张地址空间切换图 + 一次具体变更时间线讲透，要点：

- 定义：缓存键是「当前代数」的函数，失效 = 改一个数字，所有请求算出的键自动换到新地址空间。
- 核心判据（值得作为面试金句）：**删除要求你知道东西在哪里；版本号只要求大家知道现在到第几代了。**
- 删键派的三条结构性缺陷：副本位置不全在自己手里（本机缓存各实例私有）、列表页键按查询参数拼而无法枚举、删除与回填存在竞态（版本化下两个请求写不同地址，物理上不可能互相覆盖）。
- 代价（已如实告知）：僵尸副本内存 = 代数递增频率 × 键物理存活时间（详情 180 秒窗口、每分钟改一次则内存约 4 倍）；代数读取多一次往返（靠 1 秒本机缓存压制成每实例每秒一次）；代数必须单调，回退会跳回留有僵尸数据的旧地址空间。
- 类比：与 git 分支指针／对象可达性模型同构，"不可达"在两边都是字面意义。
- **学习进度信号：他需要概念级澄清才能接受架构结论，说明上一轮偏机制铺陈、缺少"为什么不能那样做"的反证。下次讲设计先给反证再给方案。**

## 追加三：对比「Canal 订阅变更日志」方案

陈同学提出「用 Canal 监听 binlog 发消息到队列、各实例订阅后更新本地缓存」。已纠正用词（是 **Canal**，不是 Canva）并给出**两层结构**分析框架，这张图/框架以后可复用：

- **第一层（可替换零件）：事件如何产生并送达各实例。** 应用发件箱 / 订阅变更日志 / 业务代码直接发消息，三者产出的事件语义相同，可互换。
- **第二层（不可回避的选择）：事件该作用到哪些键上。** 枚举后删键 vs 递增代数。换第一层的实现方式**不会让第二层的选择题消失**。

### Canal 的诚实对比结论

- 强项：**覆盖范围**——发件箱只覆盖走了那段业务代码的写入，手工 SQL／DBA 改数据／其他服务写同库都捕不到；日志订阅是数据变了就有事件，零侵入且不会漏。另：不影响业务事务。
- 代价：多一个运维组件、需管理消费位点、需开行格式日志且镜像完整、DDL 需同步处理、多一跳延迟。
- 本项目选发件箱的真实理由是**成本**（复用已有队列 + 不引入新中间件 + 同类模式已跑通），不是技术优越性。若写路径持续变多或有外部系统直接改库，应换 Canal——且**只换第一层，第二层版本代数照旧**。

### 纠正他方案里的三个坑

1. **不该"更新"本地缓存，应该"失效"。** 更新需消息带完整新值 → ①一个缓存对象由多表拼成而变更日志是单表事件，合并或重新查库都不划算；②缓存对象结构与表结构被绑死；③两条事件乱序到达会让旧值覆盖新值且**不自愈**。失效则天然安全（下次读回源必得当前值）。呼应 cache aside 经典建议「写后删除而非更新」。
2. 消息不会告诉你该失效哪些键：详情键可算，列表页键按查询参数拼成，**从"某行变了"反推不出**。
3. 隐藏优势：**"递增"对乱序免疫**（各加一次结果与顺序无关），"写入某个值"不是。

- **学习进度**：他的方案嗅觉不错（Canal 是第一层的正确直觉），但把两层混成一层来评估"行不行"。这已经是连续第三轮同一类偏差——**评估方案前先判定它在哪一层、与现有方案是并列还是包含**。后续陪练应固定先问这句。

## 追加二：澄清「cache aside 与版本化命名空间的关系」

陈同学提问"为什么要版本化？直接用 cache aside 不就行了"——**层次混淆**。已纠正并在日志里固化要点：

- Cache Aside 是**读写流程**（读未命中回源并写回、写先落库再失效缓存），本项目用的就是它；版本化只是"失效步骤"这一格里的一种填法。二者不互斥、不是替代关系。
- 关键不变量：**代数推进必须晚于数据落库**，顺序不可反。反了会让请求把旧值写进活跃地址且无人再推代数，方案失效。代码里由「提交后钩子 + 异步消息」保证。
- 被忽略的收益：**版本化下本机缓存无需被通知**——本机条目自带代数，读取时与当前代数比对，失配即未命中，脏副本物理上不可读。删键派必须广播且广播会丢，这个难题在本设计里不存在（仍广播，但是为了提前释放内存与压低延迟，不是正确性）。
- 三种填法对照：删键（竞态存在、本机副本管不到、派生视图键枚举不出）、延迟双删（概率降低不关窗口）、改代数（不可达 + 全覆盖 + 僵尸内存代价）。
- 诚实边界：单实例、全为主键单实体、可接受毫秒级不可证明脏读时，**删键更划算**；本项目三条件全不成立（多实例 + 本机缓存 + 列表页派生视图），且旧实现「观察者 + 扫描」走不通有历史证据。
- 正交性提醒（他易混）：**版本化解决「怎么失效」，发件箱解决「失效会不会发生」**，缺一不可。
- **学习进度**：连续两轮都在追问"为什么不用更简单的方案"，说明他的知识是零散清单式的（知道 cache aside、知道删缓存），缺少"分层归属"意识——不知道哪些是模式、哪些是模式的实现零件。下次讲任何设计，先明确这套东西在哪一层、替代关系是并列还是包含。

## AI 生图链路 · 第 3.1 节「排队中未到下次可尝试时间」成因与三档延迟实现

陈同学就口述稿 3.1 的三道只读拦截问了两个问题。核对代码后的结论（未改代码）：

### Q1 为什么会出现「排队中但没到下次可尝试时间」

不是异常态，是重试分支的**正常中间态**：`queued` 同时编码了「可执行」与「何时可执行」，`nextAttemptAt` 是该状态的组成部分。建任务时也有这个窗口（`nextAttemptAt = now`），只是只有几毫秒。

被真正看到的前提是**消息比时间戳先到**。根因两条：① 可执行时刻由应用时钟写进 MySQL，消息到达时刻由 broker 的 TTL 计时决定——两套时钟、两次提交，无法对齐；② 同一任务可有多条在途消息。

五条触发路径（按现实概率排序）：
1. **`AiTaskConsumer` 的 `basicNack(tag, false, true)`**：`publishRetry` 抛异常 → 原消息 requeue=true 立刻被再消费，而此时 `retry()` 已把 `nextAttemptAt` 推到 5/30/120 秒后。最直接。
2. **发布确认超时**：`AiMessagePublisher` 等 confirm 最多 5 秒（`publish-confirm-timeout-seconds:5`），超时抛异常但消息实际已入队 → 发件箱事件判 failed → 指数退避重投 → 同任务两条消息。
3. **未确认就断连**：prefetch=1 + 手动 ack，broker 重投已投未确认消息。
4. **租约恢复 + 原持有者后置重试交叉**：恢复服务把 `nextAttemptAt=now` 并补投，原线程事后走 `retry()` 又把时间戳推到未来。
5. 时钟抖动本身（NTP 偏差反向即为提前到达）。

### Q2 5/30/120 的实现

不是线程睡眠，是**三个队列级 TTL 延迟队列 + 死信回主队列**构成的延迟环：

- `AiRabbitConfig.retryQueue(name, ttlMillis)`：quorum + `x-dead-letter-strategy:at-least-once` + `overflow:rejectPublish` + `ttl` + 死信交换机为目标交换机、死信路由键指向主队列 → 环的闭合点。三个队列 TTL = 5000 / 30000 / 120000 毫秒。
- `AiMessagePublisher.publishRetry`：`delaySeconds<=5 → 5s 键；<=30 → 30s 键；否则 120s 键`，三条直连绑定。
- `AiTaskRunner.retryBucket(remaining)`：`<=5→5；<=30→30；否则 120`。

为什么拆三个队列：per-message TTL 是**队头生效**的，长 TTL 消息堵在队头会卡住后面所有短 TTL 消息；按档位分队列把 TTL 变成队列级即无此问题，代价是档位写死。

**取档是向上取整，不是文档写的"就近"**：剩余 6→多等 24 秒，剩余 31→多等 89 秒（最坏）。方向刻意——宁可多等，绝不提前。

**量化结论**：写 `nextAttemptAt` 的地方只有三处（建任务=now、重试=now+5/30/120、租约恢复=now），未来间隔上界 120 秒；取档向上取整 ⇒ 到达时刻 ≥ 目标时刻，因此 **((0,120] 的剩余一跳必收敛**；且队列积压只会更晚不会更早，收敛性不受影响。这个结论依赖"最大间隔 120"与"最大档 120"两个数相等，两侧任一改动就会退化成多跳。

该分支**只读不写**：不改 `nextAttemptAt`，只重排消息，所以天然幂等；代价是放弃一次纠偏机会、最多白等 89 秒。

### 与文档的口径差异

口述稿 3.1 表格里「就近取档」措辞不准，实现是向上取整（ceil）。其余与该节描述一致。

### 追问「排队中为什么不直接执行、要一个下次可尝试时间」

核心立论：**状态与时间是正交维度**，被压成一个字段才会产生这个疑问。

- `排队中` 回答「处在生命周期哪一段」，`nextAttemptAt` 回答「现在能不能执行」。三种组合：排队中+已到时间=可执行（首次提交、租约恢复退回且时间戳设为当下）；排队中+未到时间=退避中；排队中+次数已满=抢占判出后就地终态化。抢占那条条件更新同时判三条件，状态只是其一。
- **为什么不能只靠延迟队列**：至少一次投递语义下**消息与任务不是一对一**，一条任务可有多条在途消息；延迟队列只承诺「这一条」不早于 N 秒到，管不了另一条 1 毫秒后到。判据挂在消息上 → 节奏由最快的那条消息决定，退避失效。金句：**延迟队列是单条消息的下界，时间戳是任务的全局下界。**
- 去掉的后果：限流→退回排队+5 秒延迟消息；同时重复投递的旧消息到达→立刻可执行→再打上游→又限流。环周期由消息往返（毫秒级）而非上游恢复窗口决定 → ① 上游持续被打、可能升级封禁 ② 4 次重试上限在毫秒级烧光（重试次数是稀缺资源，必须跨窗口花）③ 任务瞬间失败、额度归还但用户无所得。
- 定量：上游 70 次/分钟、本项目配 60；60 次若 10 秒内打完则余 50 秒全限流。退避后的 4 个尝试点 = 0/5/35/155 秒，横跨 3 个 60 秒窗口。
- 另外三个「必须是数据库字段而非内存标志」的理由：① 恢复服务需要「立刻可执行」入口（`recoverExpiredTask` 设 `nextAttemptAt=now`），同一字段同时表达「能不能」与「何时能」，省掉布尔标志 + 额定时长字段；② 对账/审计要能查（悬挂预占、僵尸任务判定都读它）；③ **消息会丢、时间戳不会**——节奏是任务的属性而非消息的属性，队列被清/broker 重启后兜底链路仍能凭它捞回任务。
- 已产出内联时间轴对比图（无时间戳时 4 次尝试挤在一瞬 / 有时间戳时 0-5-35-155 跨三窗口）。

### 追问「上游限流已由 Redis 两道闸控制，延迟队列是否多余」

陈同学提出反驳：既然并发许可 + 速率令牌已经控制住上游限流，就不需要重试退避。核对代码后的结论：**该论点只在「闸门拒绝」这一条路径上成立，且代码已按此实现；不能推广到「上游拒绝」路径。**

七条实证（均为本次核对所得）：

1. **两条路径在代码里本就分叉。** 闸门拒绝发生在 `markRunning` 之前，`return ExecutionResult.retry(5, ...)` —— **不消耗重试次数、不写 `nextAttemptAt`**；上游可重试错误发生在 `markRunning` 之后（`attemptCount` 已 +1）—— 写 `nextAttemptAt` + 走 5/30/120 三档。**分支不对称本身就是设计依据。** 用户的直觉在第一条路径上完全正确，代码就是这么做的。
2. **速率令牌扣了不退。** `ACQUIRE_RATE` 脚本只有 `tokens = tokens - 1` 与 HSET；`RELEASE` 只对并发许可的有序集合做 ZREM。全仓 grep 确认 `teacup:ai:rate:*` 只在 `tryAcquire` 里被触碰，**没有任何归还路径**。→ 每次尝试（含 429/超时）净消耗 1 个令牌。
3. **令牌产能 = 1 个/秒**（`refillPerMillis = requestsPerMinute/60000 = 0.001` → 1 token/s；桶容量 `burst-capacity` = 4）。→ **没有退避时，被上游拒绝的任务会持续抢走刚补出来的令牌并把令牌烧成再一次 429，闸门自己的产能被浪费干净，健康任务在令牌队列里排不上。** 这个论证与「闸门准不准」正交：即使闸门 100% 准确也成立。
4. **可重试错误四类里只有一类与限流有关**：429 → `provider_rate_limited`；408/504 → `provider_timeout`；其余 5xx → `provider_http_5xx*`。后三类是上游自身故障，两道闸门对它们没有任何表达力。这是「退避不可能被闸门替代」最干净的反例。
5. **闸门是开环的**：判据只有我方两个计数，动作发生在发请求之前，**时序上不可能知道本次会不会被拒**。60 与 70 之间那 10 次/分钟的差额（注释明写用于吸收突发、时钟偏差、统计窗口差异）就是承认开环必然有误差——承认会错，就必须有「错了怎么办」的路径，那就是退避。
6. **上游错误码有优先权**：`providerError` 用 `StrUtil.blankToDefault(error.code, errorCode(status))`，上游返回的 `error.code` 覆盖 HTTP 状态映射。若上游返回我们不认识的码，任务直接判失败、不重试——进一步说明「上游会以什么形式拒绝」无法开环预测。
7. **闸门自身有失效口**：`Permit.renew()` 写了但全仓无人调用（grep 无 `.renew(`）；并发许可租期 300 秒、上游超时 120 秒，目前靠「超时 < 租期」这个巧合安全。谁把上游超时调到 300 秒以上，许可会在调用中途过期、并发上限被短暂突破，**闸门自己就会制造上游拒绝**。此条与口述稿「已知边界」第 2 条一致。

资源不对称（本题的量化收束）：**令牌产能每秒可再生 1 个；重试次数只减不增、再生速率为 0**（上限 4 次）。所以延迟队列是拿「不可再生的重试次数」去换「可再生的时间」。

用户论点中真正有价值的部分：**上游拒绝更该由全局熔断处理，而不是让每个任务各自退避**——方向对，但属补充不是替代（熔断解决「别再打了」，任务级退避解决「各任务何时回来」并避免熔断恢复瞬间的惊群）。项目正好缺这个全局冷却，只有 60/70 余量在兜。

### 再追问「下次可尝试时间 + 三档队列到底有什么用」（要求举例子）

陈同学连问两轮仍未吃透，改用完整轨迹走读 + 反证。最终收敛出的讲法（有效，后续复用）：

**一句话分工：三档延迟队列 = 闹钟（管「这一条消息什么时候能到」）；下次可尝试时间 = 判据（管「这一条任务现在能不能跑」）。缺一个都不行。**

完整轨迹（4 次上限、退避 5/30/120，源自 `retryDelay(attemptCount)` 与 `max-attempts:4`）：
t=0 第 1 次执行 → 429 → 改回排队中、写「5 秒后」、发 5 秒队列、许可与线程当场释放 → t=5 第 2 次（尝试次数 1→2）→ 429 → 写「35 秒后」、发 30 秒队列 → t=35 第 3 次（2→3）→ 429 → 写「155 秒后」、发 120 秒队列 → t=155 第 4 次（3→4）→ 429 → 尝试次数 = 上限 4 → 置失败并归还额度。总耗时 155 秒，4 次尝试跨 3 个上游窗口。

两个反证：
- **只留队列、去掉时间戳** → 发布确认超时等场景会让同一任务出现两条在途消息（一条在 5 秒队列里躺着、一条刚到主队列），早到的那条会把等待直接作废。延迟队列只承诺「这一条」不早于 N 秒到，管不了别的消息。
- **只留时间戳、去掉队列** → 谁在 5 秒后来叫醒任务？没有人。必须有「到点叫我」的载体，那就是延迟队列（替代方案是定时扫库，代价是延迟精度与空转成本）。
- **两个都去掉** → 第 1 次 429 后立刻回主队列，消息往返毫秒级，4 次尝试在约 3 毫秒内烧完 → 用 3 毫秒花掉了本该覆盖 155 秒的容错预算。

「不原地等」的量化意义：工作线程总共 4 个、并发许可 12 个。若让线程睡 120 秒，4 个线程槽位与许可被同时占死，整个系统停摆两分钟；用延迟队列则任务放弃全部资源回队列躺着，线程立刻去处理别的消息。

### 追问「上游阻塞 120 秒 / 续租节拍 90 秒 / 任务租期 300 秒分别是什么」

三个数字度量三件不同的事，混在一起是因为都在"时间"维度上：

| 数字 | 配置项 | 度量 | 对象 |
| --- | --- | --- | --- |
| 120 秒 | `teacup.ai.openai.timeout-ms` | 单次 HTTP 请求最多等多久 | 下游给的界限 |
| 300 秒 | `teacup.ai.worker.lease-seconds` | 执行权有效期（任务行的 `leaseUntil`） | **给别人的承诺** |
| 90 秒 | `teacup.ai.worker.lease-renew-millis` | 心跳节拍 | 自己给自己续命 |

两条约束：
1. **心跳周期 × 3 ≤ 租期**（`AiTaskLeaseRenewer` 构造函数校验，不满足**启动即失败**）。90×3=270 ≤ 300 ✓。含义：允许连续掉两次心跳，第三次必须在租约到期前赶到。走一遍：t=0 续租→到 300；t=90 续租→到 390（失败则仍 300）；t=180 续租→到 480，距 300 还剩 120 秒；t=270 续租→到 570，只剩 30 秒余量，刚好赶上；再失败则 t=300 过期 → t≤330 恢复服务扫到收回（恢复服务 30 秒一轮、每轮 50 条）。所以 90 的取值逻辑 = 租期 ÷ 3 再留余量：取 150 只剩一次容错，取 100 又太频繁。
2. **单次执行实际耗时 < 租期**——**代码里没有强校验**，即口述稿「已知边界」第 3 条。上游超时 120 秒 + 落盘合计远小于 300 秒所以安全；若把上游超时调到 300 秒以上，任务会在执行中途丢租约 → 恢复服务抢走重排，而原线程还在跑 → **同一任务被两个执行者同时跑、上游被调两次**。

**为什么续租不能由执行线程自己做（关键一层）**：执行线程在调上游的 120 秒里**完全阻塞**（`HttpRequest.execute()` 同步等待），不可能边阻塞边续租。所以续租被交给**实例级定时任务**：每 90 秒一条 UPDATE 把本实例持有的全部执行中任务的 `leaseUntil` 批量推到 `now + 300`；归属靠执行者标识前缀匹配（实例标识是 36 字符 UUID，线程标识是「实例UUID:线程名」，故 `实例UUID:%` 可前缀匹配并走索引）。**角色转换：续租从"属主线程的责任"变成"进程的责任"。** 进程被强杀的最坏恢复延迟 = 300（租约）+ 30（恢复扫描）= 330 秒，且 50 条/轮的批量会让它更长。

细节：`@Scheduled` 用的是**固定延迟**（上一次跑完再等 90 秒）而非固定频率，所以真实间隔 = 90 秒 + 本次批量更新耗时；`90×3 ≤ 300` 的 30 秒余量可吸收。续租失败只打日志、不改任务状态，靠租约到期兜底。另有一个数字 **15 分钟**（`running-timeout-minutes`）是给「执行中但 `leaseUntil` 为空」的存量数据的兜底判据（按开始时间早于 15 分钟前），与新增任务无关。

**易混淆点（大概率是提问的根源）**：项目里有**两个**"续期"，不是一个——
- 任务租约续期：实例级定时任务 90 秒一次，**存在且被调用** ✓
- 并发许可续期：`AiExecutionLimiter.Permit.renew()` **写了但全仓无人调用** ✗。两者租期都是 300 秒（复用同一配置），但**只有任务租约真的有人在续**。并发许可目前靠「上游超时 120 秒 < 许可租期 300 秒」这个巧合安全；谁把上游超时调到 300 秒以上，**并发许可会在调用中途消失、闸门自己失守**。即口述稿「已知边界」第 2 条。

### 追问「120 秒超时后发生什么 / 续租 +300 有什么意义 / 300 秒是谁的租期」

**① 120 秒读超时的真实结局（与直觉相反，是本题最大纠正点）**：
上游一个字都没回、客户端读超时 → Hutool 抛运行时异常 → 适配层包成 `provider_network_error` → **`retryable()` 不认这个码**（只认 `provider_rate_limited`、`provider_timeout`、`provider_http_5*`）→ 不走重试分支 → 改码为 `provider_outcome_unknown` → `fail()` 终态化、**归还预占额度** → **不会再有 5/30/120 的重投**。

**必须与另一条区分**：`provider_timeout` 这个可重试的码**只对应"上游自己回了 408 / 504"**，不等于"我方等超了"。两类超时两条路：
- 上游回 408/504 → 结果已知（它没接单或已放弃）→ 可重试 5/30/120
- 我方等满 120 秒、上游一字未回 → 结果未知（可能已在生成）→ 不重试、置失败、归还额度

判据是「**上游到底有没有接单**」，不是「超时了没有」。诚实代价：若上游实际成功，那张图永久丢失。
（附带精度点：`.timeout(120000)` 严格说是每次 socket 读的上限、非总耗时上限；生图接口返回前不发字节，故实际等价于总耗时上限。另：`providerError` 让上游 `error.code` 覆盖状态码映射，故 504 若带未知 code 也不会重试。）

**② 续租的意义（对象纠正）**：续租**不给上游加时间**，只改数据库里的「租约到期时间」，影响"别人会不会把任务抢走"这一件事。真正意义是**把租期的语义从「绝对执行时长约束」降级为「心跳窗口」**：
- 没有续租 → 租期必须 ≥ 最坏执行耗时，否则会误杀活人；而租期越长，进程被强杀后回收越慢。
- 有续租 → 租约在进程存活期间不断被推到「当下+300」，于是"租约过期"只表达"这个进程心跳停了"。跑 20 分钟的慢任务不被误杀，进程被杀后仍只需 300 秒判定死亡。
代码注释原话：「没有这一层，租约就退化成一次性超时判断，会主动误判存活者为死亡。」

当前 120 < 300，**这组配置确实是防御性冗余**；真正起作用的场景：① 上游超时被调大（可配置）；② **落盘阶段卡住**——拿到结果后写对象存储/建图片行/更新空间用量，**不调上游也不抛上游异常**，若对象存储卡 10 分钟任务会一直停在执行中，无续租则 300 秒后被抢走重排、下一个执行者卡在同一处 → 死循环 + 空间用量重复累加；③ 执行链路变长（加审核/后处理）。

诚实边界：**续租检测「进程存活」而非「任务在推进」**，线程假死也会被一起续上、永不回收（口述稿已知边界第 1 条）。可算的一笔：若确信执行路径 ≤ 130 秒，可把租期降到 150、节拍降到 50（50×3=150 ≤ 150 恰过校验），进程被强杀后的回收延迟从 330 秒压到 180 秒。

**③ 300 秒的归属**：是一条 AI 任务的租期，写在 `ai_task` 行上的租约到期列，准确说是「**这条任务 ⇄ 这个执行者**」这一对关系的有效期，绑定三要素（状态=执行中 + 执行者标识匹配 + 栅栏令牌匹配）。批量续租条件也只有「状态=执行中 且 执行者标识以本实例标识开头 」。它**不是**：模型调用超时、并发许可租期（Redis 里另有同样 300 秒的一份，对象是许可集合成员）、消息存活时间（5/30/120 秒）、连接租期。粒度为每个任务行各持一个值。

租约过期后的两条接管路径：① 恢复服务每 30 秒扫一轮退回排队重投；② **更快的一条**——抢占的条件更新里本就带「执行中且租约已过期」这一支，任何到达的消息可直接接管。
职责分工：**租约 = 时效性（时间维度，保证死人的活被接走）；栅栏令牌 = 排他性（版本维度，保证活人回来也改不了结果）**。接管时令牌自增，故原执行者持旧令牌终态化必被拒——即 3.5 / 3.8 两次校验的意义。

### 追问「速率令牌是因为上游 60 次/分钟，那并发许可是因为什么业务需求」

核心立论：**速率令牌护「流量」、并发许可护「存量」，是不同的数学量。** L = R × T（在飞数 = 到达速率 × 单次耗时）。速率令牌管 R（1 次/秒），并发许可管 L（≤12），**T 是上游决定的外部变量、谁都管不了**——正因 T 不受控，L 才不能由 R 推出。

**并发许可真正的业务需求 = 给「集群扩容」设天花板。** 单实例天然最多 4 个在飞（工作线程数 `concurrency:4`），12 ÷ 4 = 3 → **3 台实例刚好满载，第 4 台开始抢不到许可**。没有它，"加机器提吞吐"就等于"线性放大对上游的并发压力"；有它，扩容只能提升处理排队消息的速度，不能提高对上游的瞬时压力。**即把「扩容」与「打爆上游」解耦。** 次要作用：保护我方 HTTP 长连接与内存（每在飞一个请求占一份上游响应，base64 图片可能几 MB，上百个在飞即几百 MB 尖峰）；且它是租约式（Redis 有序集合记到期时间、每次抢许可先清过期），进程被杀不会永久占许可。

**失控场景（只有速率令牌时）**：上游变慢、单次耗时 30→120 秒。速率令牌照样每秒放 1 个，在飞数按耗时线性膨胀 30→120，**上游越慢我们打得越多**（正反馈）；单实例被 4 个线程天然封顶，但集群一扩容就按实例数放大。

**反过来只有并发许可也不行**：12 并发 × 单次 60 秒 → 吞吐 12 次/分钟，上游 60 次/分钟的配额只用掉 20%。速率令牌的作用是把消耗型配额**平滑成连续流速**（否则出现"每分开头发完、余下 50 秒全失败"的锯齿）。

**分界点可算**（这是本题新增的量化结论）：
- 并发许可允许的吞吐上限 = 720 ÷ T（次/分钟）
- T = 12 秒 → 60 次/分钟，**与速率令牌上限刚好相等，两道闸等价**
- **T < 12 秒 → 速率令牌先拦**（上限 60 次/分钟）
- **T > 12 秒 → 并发许可先拦**（上限 720/T）
- 生图实际耗时 20–60 秒，全部落在右侧 → **12 个并发才是真瓶颈，速率令牌几乎永远不会拒绝**（有效吞吐只有 12–36 次/分钟）
- 且许可在整个执行块内持有（含落盘），T 还要加落盘时间，右侧更偏。
→ **"两道闸是正交维度"的严格含义：谁先拦取决于单次耗时这个外部变量，两道都留才能在任何耗时形态下都有上界。**

**顺序细节（体现设计）**：先抢并发许可、再抢速率令牌；令牌抢不到时把并发许可**退回**。这个顺序是对的，因为**速率令牌扣了不退**——反序会让"并发满"的请求白白烧掉一个令牌；当前顺序下并发受限的请求不消耗任何令牌。

### 追问「只留速率令牌时上游变慢，会不会因阻塞导致线程堆积压爆后端」

**陈同学的推论需要当场纠正**（架构记错，但直觉里有一处是对的）。

**纠正：本项目不会出现"线程堆积"。** 四条约束共同把在飞数封成常量 4：① `aiWorkerExecutor` 核心=最大=`concurrency:4`；② `queueCapacity=0`；③ 消费者 `prefetchCount=1`；④ 手动确认。所以上游 30→120 秒变慢，唯一变化是这 4 个线程被占得更久，**不会有第 5 个线程被创建**，第 5 条消息躺在主队列里不占进程任何资源。观测指标也完全不同：无界线程架构看**线程数暴涨**；本项目看**线程数不变 + 队列深度增长**（压力在消息中间件的磁盘上，不在进程内）。

**"线程堆积压爆后端"属于每消息一线程 / 无界线程池 / 同步阻塞 Web 线程池那一类架构。**

**换成真正会失控的三样**：① 消息在队列里堆积（broker 磁盘）；② 在飞数失去全局上界——但**单机上线程数已给出上界 4，所以并发许可在单机上确实看不出差别**；③ 每个在飞请求占一条 HTTP 长连接 + 一份上游响应（base64 图片可能几 MB），在飞数 30→120 即 4 倍内存尖峰——注意这是**在飞数**的压力，不是**线程数**的压力。

**并发许可的真正作用域 = 跨实例**：单实例在飞 = 4（线程数给的），全局 = 4 × 实例数；12 ÷ 4 = 3 → **3 台刚好撞上、第 4 台开始抢不到**。没有它，"加机器提吞吐"就等于按实例数线性放大对上游的瞬时并发。

**陈同学直觉里对的那处**：「上游越慢我们打得越多」这个正反馈是真的，但被压爆的对象是**上游**（稳态在飞数 = 启动速率 × 单次耗时，耗时翻 4 倍在飞数翻 4 倍，环路里没有任何一环感知耗时），作用对象是"上游 + 跨实例总量"，不是"我这台机器的线程"。**并发许可是把「耗时」这个变量从反馈环里切出去的那一刀。**

**收束**：`固定线程数封顶 = 天然的、但作用域只有单机的并发上界`；`并发许可 = 显式的、跨实例的并发上界`。前者管"我这台机器不被自己拖垮"，后者管"集群不把上游拖垮"。

**对照实验**：真想制造"线程堆积"，不用去掉并发许可，把工作线程池改成无界（每消息一线程 / 缓存线程池）即可——上游一慢立刻就是那个画面。
附带核对（本项目做对了的地方）：`SchedulerConfig` 把 `@Scheduled` 的线程池设为 4，且全部用 `fixedDelay`（跑完再等），所以定时任务本身也**不可能堆积**。

### 追问「集群不扩容，是不是可以去掉并发许可」

**结论：能去掉，但「看不出差别」≠「可以去掉」。** 先承认对方对的边界：并发许可的持有区间是线程持有区间的**子集**（`tryAcquire` 在 `run()` 内、同一个 try 块内释放，全程由该工作线程持有），所以**单实例下确实不增加任何当下可观测的约束**。

**去掉就失去的三件事：**

1. **把约束从「巧合」变成「契约」（最硬）**：「4 就是并发上界」不是设计而是**推论**，依赖「核心=最大=4 + 队列容量=0 + 预取=1」三条同时成立，其中真正会破的只有 `concurrency` 这一个值 —— 而它恰是最常被调的（一看到消息堆积就想调大）。调到 8/20，在飞上限跟着变成 8/20，不改代码、不报错、无告警。有许可在，**线程数调到 100 也打不爆上游**（防呆 / fail-safe）。
2. **把「上游的配额」与「本地的算力」解耦**：若只靠线程数封顶，"上游能承受多少并发"这个**业务参数**就被写进了"线程池大小"这个**部署参数**里。上游限额变了只需改 Redis 一个数字，本地 CPU/内存/吞吐一概不动；合并成一个旋钮则是设计错误。
3. **自动覆盖「第二个调用上游的入口」**：现在只有消费者调上游，所以线程池刚好能代表它——这是**当前事实而非设计保证**。任何新入口（同步生图接口、管理端批量重生成、定时补图）都绕过线程池这道隐式限制；许可在 Redis 里，**不关心谁在调**，新入口自动进同一本账。

**去掉的成本（老实算）**：每次执行多 2 次 Redis 往返（抢 + 释放），同机房 0.2–1 毫秒/次 → 约 0.4–2 毫秒，对比一次 20–60 秒的生图，占比 **0.005% 以下**，可忽略；内存一个有序集合最多 12 个成员，可忽略；「多一个 Redis 依赖」这条**不成立**——速率令牌本来就在 Redis 里，Redis 无论如何是强依赖（不可用时任务一直 5 秒重投，但不丢任务、不丢额度）。→ **留着成本≈0，去掉换来的是"把上界交给团队记忆"。**

**可自验的对照实验**：把 `concurrency` 从 4 调到 20、不动许可，压 100 条任务 →
- 有许可：在飞被 12 卡住，Redis 集合基数恒定 12，多出的 8 条线程每 5 秒空转重投
- 去掉许可：直接 20 个在飞，超发 8 个

**可安全去掉的三个条件（须同时成立）**：① 永远单实例（注意开发机 + 测试环境 + 本地压测共用同一上游 key 也算多实例）；② 永远不新增第二个调上游的入口；③ 工作线程数永远 ≤ 上游允许的并发数且有人守着。第 ②③ 条本质是"承诺未来"，而限流恰恰是不该靠承诺的地方。

**收束金句**：单实例下并发许可**不增加任何约束**，但它把约束**从「我的部署配置恰好是这样」变成了「系统上客观存在的上限」——前者是巧合，后者是契约**。判据不该看实例数，该看**上游允许的并发数（12）与本地线程数（4）是否同一个数字**；两者不等，说明它们是彼此独立的两个量，不能用一个代表另一个。
