### 本轮教学产出
- **Little's Law**：L=λW。反推 200 并发下 3900 QPS→平均 RT 51.3ms；133 QPS→1503.8ms≈1.5s。关键推论：51ms 不在任何"缓存命中"延迟区间（Caffeine 0.1-1μs / Redis 0.1-1ms / MySQL 点查 0.5-5ms），说明瓶颈在应用层而非缓存层。并给出「并发固定时 QPS 与 RT 成反比」的提醒。
- 各层读路径延迟量级表 + 去重测必须记录的 6 类指标。
- **Caffeine 容量**：应 `maximumWeight + weigher` 按字节控，不能按条数（1000 条可能 300KB 也可能 200MB）。
- **`expireAfterWrite` vs `expireAfterAccess`**：前者让最热的 key 也 30min 强制回源 → 批量上传的图同时失效 → **周期性制造击穿**；而 Redis 层做了随机化、Caffeine 层没做。
- **多实例失效传播四方案**：TTL 兜底 / Pub-Sub 广播（快路径）+ TTL（慢路径）/ 版本号代际 / 三者结合。指出他的 version 方案在"读时一致性"上其实是正确的（下次读即失效，不必等 30min），代价是**旧 version 的 key 变孤儿占槽位**。定量：孤儿占比 ≈ (TTL÷清理间隔)×数据集÷槽位数，每 5min 清一次 → 有效命中率上限 ~21%。修法：广播清理 / 版本分桶丢弃 / 双缓冲轮换。
- 附带雷点：**version key 自身失效/过期会导致所有实例 version 归 0 并读到本地脏数据**。
- **击穿三兄弟区分表** + 互斥锁标准写法四要点（二次检查 / 拿不到锁必须自旋重读而不能查 DB / 随机 TTL / 参数按 P99 反推）。
- **Redisson leaseTime**：只有 `leaseTime=-1` 才启用 WatchDog 续期；固定 10s 会在业务超时后"锁提前蒸发"。取值 `leaseTime ≥ DB P99×3`、`waitTime ≥ 1~2×DB 耗时`。
- 布隆过滤器弃用的正确口径：图库 key 是自增 ID 不可枚举，穿透风险低，空值缓存已覆盖；标准布隆不支持删除（只能双布隆轮换重建），收益 < 维护成本——是**有成本的决策**，不是"不知道所以不用"。

### 第二轮已开打（AI 生图任务 · 5 题）
用户主动要求跳过预热直接拷打 AI 生图。已出题：
1. **条件更新 vs 行级锁语义辨析**：`UPDATE ... WHERE status='queued'` 已原子，那 `SELECT FOR UPDATE` 防的是什么？两者加锁顺序/死锁？`WHERE status=` 无索引会锁什么？workerId 为什么必须落库（钩子 → 引向续租与 owner 校验）。
2. **租约与续期（最致命）**：AI 生成 40 分钟 / 租约 10 分钟 → 第 11 分钟 recovery 把任务重置 queued → 另一 worker 抢到 → **同任务双执行、双扣配额、双写结果**。追问：有无 renew 逻辑、`complete` 的 FOR UPDATE 是否校验 `workerId == 自己`、续租用什么实现（定时线程池 vs 每任务 scheduled future）、多实例续租失败兜底。
3. **配额泄漏与恢复边界**：进程 kill -9 后 `reservedCount` 谁还？恢复时是保持预占还是重新预占（会双扣）？重试 4 次全失败后 `quotaRefunded=1` 写在哪个分支？`reservedCount` 是否按天重置、reset 触发器在哪？定量：100 用户各提交一次，漏 1% 任务一天泄漏多少。
4. **幂等作用域 + 用户行锁热点**：同幂等键但请求体不同（换 prompt）会怎样？`sameRequest` 比对哪些字段、成本多少？客户端重试换了新 UUID → 幂等失效。幂等键有无过期、表如何增长。为什么 `userMapper.lockById` 要锁用户行、不锁会怎样（引向行锁串行化 → 单用户提交吞吐上限）。
5. **prefetch=1 × 4 线程 × 队列容量（定量必杀）**：prefetch=1 约束什么？Consumer 同步执行 30s 的情况下 4 个线程有几个在工作？若丢线程池后立刻 ack，prefetch 还有约束力吗？定量：30s/任务 × 4 并发 = **8 任务/分钟**，200 用户同时提交 → 最后一个等 25 分钟；60s/任务 → 等 50 分钟；100 活跃用户用满 100/天 = 10000 任务 → 4 并发下需 **20.8 小时**。加分：提吞吐三件事按性价比排序（加 worker / 改 prefetch / 加消费者实例 / 任务拆分 / 提单任务效率）。

### 第二轮作答结果与讲评

**用户作答**：A1「是两件不同的事」（方向对但无判据）、A2 不会、A3 没看懂、A4「重新建立一个新的任务」（错）、A5 不会算。

**用户提出的重要反馈（须长期遵守）**：**出题时不要堆代码里的私有标识符**——面试官没看过源码，不懂 `claimForExecution`/`leaseUntil`/`prefetch` 这类私有命名。给了一份「私有标识符 → 通用技术术语」对照表。核心区分：**通用技术术语（行级锁、乐观锁、租约、预取、幂等、事务性发件箱）可以说，自己的方法名/字段名/类名不能说**。已用纯业务语言重述全部 5 题（第 2 题重述后完全不出现「租约」二字，考的是能否自己想到需要超时机制）。**以后出题一律走业务语言。**

**讲评要点**：
- **A1 判据（一句话）**：「判断条件」和「写入动作」能否写进同一条 SQL 的 WHERE？能 → 条件更新足够，额外行级锁是冗余；不能（读 A 表→判断→写 B 表的跨语句复合逻辑，如额度预占）→ 必须加行级锁。补充：要用行级锁必须用**主键定位**，用状态列做条件会锁住所有匹配行 + 间隙，把队列串行化。给了标准答题结构：先结论、再判据、最后反例。
- **A4 纠正**：幂等键上有唯一索引，同键第二次插入是**唯一键冲突**，不可能新建成功。行为取决于是否接住冲突：接住 → 返回原任务（真幂等）；没接住 → 500。同键但内容变 → 请求内容比对专门区分这种情况，内容不一致应拒绝（409）。**幂等键契约**：一次用户意图一个键，不是一次 HTTP 请求一个键；前端点提交时生成并缓存，重试复用同一键，改内容才换新键（Stripe/支付宝标准契约）。
- **A2 讲解（租约）**：起源是「无法区分持有者是慢慢执行还是已经死了」。租约 = 用超时代替心跳确认。两个必须同时满足的前提：①持有者必须主动续租，否则退化成一次性超时判断，比不加更糟（主动误判存活者为死亡）；②续租周期 ≤ 租期的 1/3。用户代码只在抢占时写了一次租约、无续租 → 超出租期的任务被判死亡并重新派发 → **同任务双执行**。**修复三层**：①续租（更新须带「任务ID + 执行者 = 我自己 + 状态 = 执行中」条件，防覆盖别人）；②**栅栏令牌**（每次抢占分配单调递增令牌，提交时校验，对不上则丢弃结果 + 退回配额）——防「过期持有者诈尸乱写」；③结果写入幂等（条件带「状态还是执行中」）。加分项：**AI 生成是不可撤销的外部副作用**，任务可标取消但已发出的调用不会停，计费须按实际调用次数而非任务最终状态。已产出时序图（抢占→执行→第10分钟租约到期→10分30秒恢复扫描重置→10分31秒B抢占成功→第40分钟双写）。
- **A3 讲解（配额泄漏）**：用两阶段记账（预占→结算）解释防超卖的必要性。泄漏点＝进程被 kill -9 / OOM / 断电，**没有任何机会执行清理代码**，预占永久无人归还。核心命题：**任何「先占后还」机制必然存在「占了没还」的残留，必须有独立兜底回收者，不能指望主流程自觉。** 严重性：最大重试 4 次若每次重新预占则一次操作扣 4 次；恢复任务是否管额度；泄漏**不自愈**（永久性缩水，重度用户越来越早撞额度上限且查不出原因）。**修复四件事**：①预占跟着任务走，重排队时保持原预占、绝不重新预占；②三个终止出口（失败/取消/超重试）统一收尾归还，用统一方法而非分散写；③定时对账兜底（扫描「预占超 N 小时且任务已终态或不存在」）——唯一能救 kill -9 的手段；④额度按天切换且切换幂等（用「日期」作主键插当日记录行，而非"把昨天清零"）。
- **A5 讲解（预取数与线程池 × 队列容量）**：预取数＝同一消费者最多允许几条「已推送未确认」的消息。**两种写法的结果完全相反**：①消费者同步执行（收到→跑30s→确认）→ 预取数1 意味着队列最多1条在途，**4 个线程只有 1 个在干活，并发度=1，另外 3 个纯摆设**（用户配置里这两个数字在打架）；②丢给线程池后立刻确认 → 预取数完全失效，队列疯狂推送全部堆在应用内存，**消息脱离队列管控，应用重启即全部丢失**。正确写法：**预取数 = 工作线程数**，同步执行、处理完再确认，扩吞吐靠加消费者实例。定量：吞吐 = 并发 ÷ 单任务耗时 → 4/30s = **8 任务/分钟**（200 个等 25 分钟）；4/60s = **4 任务/分钟**（200 个等 50 分钟）。**与配额设计对撞**：100×100 = 10000 任务/天 vs 一天最多 11520 个 → **利用率 87%，配额上限刚好塞满队列**，活跃用户超 100 或耗时超 30s 必然积压 → 结论：产品配额未做容量校验。提吞吐性价比排序：①修预取数与线程数不匹配（bug，免费 4 倍）②优化单任务耗时 ③加消费者实例 ④加线程（连接池先成瓶颈）⑤任务拆分。

**待补**：用户定量能力仍是核心短板（已连续两轮 Little's Law 相关计算不会）。待开第三轮：分片上传（5MiB 固定 × 20MB 上限 → 最多 4 片的悖论、无秒传/内容去重、图片校验靠格式名对比而非魔数、跨资源补偿无兜底）。

**补充 21:13**：用户反馈 A3/A5 的讲解在界面里没看到（上一轮超长回复疑似被截断）。已重讲一遍并换用更直白的讲法——A3 用「进程被强行杀死后预占无人归还」的故障时间线重构，A5 用「预取数 × 线程数 → 实际并发度」的推导链重构并配对比图。

### 交付：AI 任务可靠性改造规格书

**产出**：`docs/backend-ai-task-reliability.md`（供 codex 直接实施）

**核实后推翻的两处早前结论（必须记住，勿再重复错误）**：
1. **预取数配置是对的，不是"打架"。** Spring AMQP 的 `prefetchCount` 是 **per-consumer** 语义：`AiRabbitConfig.java:130-131` 的 `concurrentConsumers=4` 会创建 4 个消费者，各预取 1 条 = 4 条在途，与 `aiWorkerExecutor` 的 4 线程精确匹配。我之前把"4 线程 + 预取数 1 = 并发度 1"当作该项目的缺陷讲，**讲错了**，已在规格书 §1.1 列为"禁止改动"。
2. **续租逻辑存在，但时机错误。** `AiTaskRunner.renewLease`（:158-163）确实存在，但只在 `provider.execute()` **返回之后**调用一次（:90-94），覆盖不了阻塞调用期间。租期默认 300s，长调用必然过期 → recovery 重置 → 另一线程抢占 → **重复一次付费 AI 调用**。但 `complete`/`fail`/`retry` 的 `workerId` 校验挡住了双写结果与双扣配额，损失仅为重复付费调用——不含夸大。

**核实后确认的正确实现**：幂等（唯一索引 + 请求体比对 + 409 冲突，`AiTaskService:99-105`）、状态机 CAS 抢占（`AiTaskMapper:11-17`）、发件箱重试（无限重试 + 退避封顶 60s + 只清 published 且超 7 天）、终态归属校验（三处均查 workerId）。

**真实缺陷清单（D1-D8）**：
- D1 续租时机（高）· D2 租约丢失被泛化 catch 吞掉、错误码误写成 `result_persistence_failed`（中）· D3 无 fencing token，依赖"线程名恰好不同"的偶然（中）· **D4 抢占不校验 attemptCount 上限 → 可无限重投（高）** · **D5 消费者 reject → DLQ 后无恢复路径，queued 任务配额永久泄漏（高）** · **D6 无配额对账任务，归还全靠事件驱动（高）** · D7 取消 running 任务走 settleQuota 计费需产品确认（低）· D8 `userMapper.lockById` 串行化同用户全部提交（低）

**方案要点**：迁移 V22（新增 `executionToken`、两个索引、`ai_task_quota_audit` 审计表）；新增 `AiWorkerIdentity`（实例 ID 单一来源，供 Runner 与续租器共用，避免两处各自 randomUUID 导致前缀不匹配）、`AiTaskLeaseRenewer`（按 workerId 前缀批量续租，默认 90s = 租期/3，启动校验 renew×3 ≤ lease）、`AiTaskLeaseLostException` + 专用 catch 分支、`AiTaskService.exhaust`、`AiTaskDlqService`（死信队列首个消费者，独立容器工厂避免占用任务线程）、`AiQuotaReconciliationService`（扫描一预占悬挂 + 扫描二计数漂移修复）；抽取 `finalizeQuota` 统一收尾。阶段三可延后：条件更新 `reserveIfWithinLimit` 替代行锁 + 唯一索引承担幂等。
**规格书含 10 项验收用例（T1–T10）、4 条不变量 SQL、8 条禁止改动清单。**

**同时修正了用户对幂等的理解**：本实现的幂等记录就是 `ai_task` 行本身，键一旦使用**永久占用**（不是 24 小时窗口幂等），这一点必须写进客户端契约。

### 实施：AI 任务可靠性改造（用户要求"直接改"，不走 codex）

**范围** = 规格书阶段一（租约 D1–D4）+ 阶段二（配额兜底 D5–D6）+ 阶段三的文档部分。**阶段三 D8（移除用户行锁改条件更新）主动延后**——理由：它是并发优化不影响正确性；且捕获 `DuplicateKeyException` 会把事务标记为 rollback-only，要正确返回既有任务就得拆事务边界并改到 Controller 层，风险/收益不划算。D7（取消 running 计费语义）保持代码不变，只写进文档等产品确认。

**新增 8 个文件**：
- `db/migration/V22__harden_ai_task_lease.sql`：`executionToken BIGINT`、`idx_ai_task_worker(status,workerId)`、`idx_ai_task_quota_pending(quotaSettled,quotaRefunded,createTime,id)`、workerId 扩到 VARCHAR(160)、新建 `ai_task_quota_audit`
- `ai/AiWorkerIdentity`（实例 ID 单一来源，workerId = `实例UUID:线程名`，UUID 固定 36 字符故前缀匹配安全）
- `ai/AiTaskLeaseRenewer`（`@Scheduled` 按实例前缀批量续租；构造器校验 `renew*3 <= leaseSeconds*1000`，不满足直接拒绝启动）
- `ai/AiTaskLeaseLostException`、`ai/AiTaskDlqService`（死信队列首个消费者，独立容器工厂 `aiDlqListenerContainerFactory` 单并发、不占 aiWorkerExecutor）、`ai/AiQuotaReconciliationService`、`model/entity/AiTaskQuotaAudit`、`mapper/AiTaskQuotaAuditMapper`

**修改 9 个文件**：`AiTaskMapper`（抢占加 `attemptCount < maxAttempts` + `executionToken = executionToken + 1`；`renewLease` 带令牌；新增 `renewLeasesByInstance`）、`AiTaskService`（`fail`/`retry` 加令牌参数并纳入 `ownedBy` 校验；新增 `exhaust`/`reconcile`/`isTerminal`；抽取 `finalizeQuota` 统一收尾 + `audit` 写审计；`usageDate` 抽成单一来源）、`AiTaskRunner`（`AiWorkerIdentity` 注入、`handleClaimFailure` 识别尝试耗尽并终态化、`AiTaskLeaseLostException` 专用 catch 分支只 ACK 不 fail）、`AiRabbitConfig`、`AiTask` 实体、`application.yml`、两个测试、`docs/ai-task-execution.md`、`docs/openapi/m2.yaml`（Idempotency-Key 补全语义说明：一次用户意图一个键 / 同键同内容返 200 / 异内容 409 / 保留期永久）
