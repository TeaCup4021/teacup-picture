### 简历措辞 vs 代码事实的落差点（高危靶点）
1. **「QPS 133→3900」全仓库无任何依据**——无 .jmx、无压测报告、无机器配置、无并发/时长记录。最容易被当场拆穿。
2. 「大幅降低缓存击穿可能性」——文档自认单图查询未加锁、判定低风险，只对分页/公开列表成立。
3. AI 段「条件更新实现原子抢占」与「结合事务与行级锁」是同一件事的两种说法 → 会被追问是否有一个多余。
4. 缓存两套实现并存，旧 `/api/**` 已标 Legacy，简历只说一套。

### 本轮教学产出
- **Little's Law**：L=λW。反推 200 并发下 3900 QPS→平均 RT 51.3ms；133 QPS→1503.8ms≈1.5s。关键推论：51ms 不在任何"缓存命中"延迟区间（Caffeine 0.1-1μs / Redis 0.1-1ms / MySQL 点查 0.5-5ms），说明瓶颈在应用层而非缓存层。并给出「并发固定时 QPS 与 RT 成反比」的提醒。
- 各层读路径延迟量级表 + 去重测必须记录的 6 类指标。
- **Caffeine 容量**：应 `maximumWeight + weigher` 按字节控，不能按条数（1000 条可能 300KB 也可能 200MB）。
- **`expireAfterWrite` vs `expireAfterAccess`**：前者让最热的 key 也 30min 强制回源 → 批量上传的图同时失效 → **周期性制造击穿**；而 Redis 层做了随机化、Caffeine 层没做。
- **多实例失效传播四方案**：TTL 兜底 / Pub-Sub 广播（快路径）+ TTL（慢路径）/ 版本号代际 / 三者结合。指出他的 version 方案在"读时一致性"上其实是正确的（下次读即失效，不必等 30min），代价是**旧 version 的 key 变孤儿占槽位**。定量：孤儿占比 ≈ (TTL÷清理间隔)×数据集÷槽位数，每 5min 清一次 → 有效命中率上限 ~21%。修法：广播清理 / 版本分桶丢弃 / 双缓冲轮换。
- 附带雷点：**version key 自身失效/过期会导致所有实例 version 归 0 并读到本地脏数据**。
- **击穿三兄弟区分表** + 互斥锁标准写法四要点（二次检查 / 拿不到锁必须自旋重读而不能查 DB / 随机 TTL / 参数按 P99 反推）。
- **Redisson leaseTime**：只有 `leaseTime=-1` 才启用 WatchDog 续期；固定 10s 会在业务超时后"锁提前蒸发"。取值 `leaseTime ≥ DB P99×3`、`waitTime ≥ 1~2×DB 耗时`。
- 布隆过滤器弃用的正确口径：图库 key 是自增 ID 不可枚举，穿透风险低，空值缓存已覆盖；标准布隆不支持删除（只能双布隆轮换重建），收益 < 维护成本——是**有成本的决策**，不是"不知道所以不用"。
