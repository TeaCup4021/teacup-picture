## 简历压测数据核实：多级缓存 QPS 133 → 3900

针对简历条目「Caffeine-Redis-MySQL 多级缓存优化 C 端查询，200 并发单机，QPS 133→3900（约 28 倍），P99 从 2.25s 降到 3ms 以内」做了代码级核查。

### 核实的项目事实

- 对比的是两个不同 URL：`POST /api/picture/list/page/vo`（无缓存）vs `POST /api/picture/list/page/vo/cache`（Caffeine+Redis 三层）。v1 侧另有 `M1Service.cached()` 走 `publicPictureListLocalCache`(60s) / `publicPictureDetailLocalCache`(60s) + Redis(60~300s 随机) + Redisson 锁。
- `backend/src/main/resources/application.yml` **没有任何连接池配置** → HikariCP 默认 `maximumPoolSize=10`；也无 Tomcat 线程池调整 → 默认 200。
- 压测 Mock 数据仅 **5000 行**（`PictureMockDataTest`，注释写明"用于测试压力性能"）。
- 仓库内**没有任何 .jmx / .jtl 压测留痕**，数据不可复现。
- `docker/compose.yml` 中 MySQL 8.0 / Redis 7.4 均为**单实例**，无主从、无集群。
- `PictureServiceImpl.getPictureVOPage` 用 `listByIds` 批量查作者，**无 N+1**；`page()` 走 MyBatis-Plus 分页 = count + select 两条 SQL。
- legacy 击穿锁有缺陷（`PictureController:329-340`）：未抢到锁的线程 `sleep(100)` 重试一次，失败后**直接查库兜底**，故"只允许一个线程查 DB"实际不成立。
- legacy 本地缓存 TTL=30min 而 Redis=300~600s → 本地可能比 Redis 更旧。
- `M1Service.cached()` 每次请求都调 `publicCacheVersion()` 读一次 Redis version key，本地缓存命中路径也带一次 RTT。
- `invalidateAll()` 只清本机，单实例压测未暴露多实例一致性问题。

### 定量结论

- 利特尔法则约束：固定 200 并发下 `QPS × 平均RT = 200`。
- 基线 133 QPS → 平均 RT 1.504s，与 P99 2.25s 自洽；机理吻合 HikariCP：`10 连接 ÷ 75ms ≈ 133 QPS`。
- 优化后 3900 QPS → 平均 RT 51ms，与「P99 < 3ms」**不可能同时成立**；P99 应改为百毫秒级。
- 若坚持 P99 < 3ms，则反推 QPS ≈ 66,700，说明实测 3900 是 JMeter 侧瓶颈，此时「28 倍」显著低估真实提升。
- 倍率：3900/133 = 29.3，「提升 28 倍」属增量口径，可自洽但与「→3900」混用易被抠。
- **归因修正**：5000 行数据不存在"数据库读瓶颈"，基线真实瓶颈是连接池排队，不是 MySQL 读能力。
