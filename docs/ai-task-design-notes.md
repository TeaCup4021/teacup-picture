## 一、上游调用的形态

### 1.1 是同步阻塞，不是监听也不是轮询

调用上游那一行是阻塞式的：工作线程发完 HTTP 请求后就卡在 socket 读取上，一直等到上游返回或超时。

所以「怎么保证负责这个任务的线程一直活着」这个问题本身不成立 —— 它不是在监听，是在阻塞等待。而「一直等不到怎么办」由 HTTP 超时兜住。

### 1.2 一次调用期间的四条时间线

| 设置 | 默认值 | 解决什么 |
| --- | --- | --- |
| 上游调用超时 | 120 秒 | 线程不会无限阻塞在 socket 上 |
| 续租节拍 | 90 秒 | 声明「我还活着」，让租期不到期 |
| 任务租期 | 300 秒 | 进程挂了，任务能被别人接管 |
| 优雅停机等待 | 180 秒 | 关闭时给正在跑的任务收尾时间 |

**硬不等式：租期 > 上游超时 + 结果落盘时间。**

违反的后果很具体：正常调用还没返回时租约就过期 → 恢复服务把任务退回排队 → 另一个实例抢走并重新执行 → **同一个任务被两个实例同时执行、上游被调用两次、成本翻倍**。而先启动的那个还不知道自己已经被顶掉了。

**注意代码中的启动强校验只有「续租周期 × 3 ≤ 租期」这一条**，没有校验「超时 < 租期」——后者只是本条约定，改超时时必须自己记住一起改租期，没有任何东西会拦你。

### 1.3 两种「超时」必须分开

判据是**上游到底收没收到请求**：

| 谁超的时 | 错误码 | 可重试吗 | 为什么 |
| --- | --- | --- | --- |
| 上游**明确回话**「我超时了」（HTTP 408 / 504） | `provider_timeout` | **可以** | 上游处理了但没处理完，重试安全 |
| **我们自己等不住断开**（socket 读超时） | `provider_network_error` → 改写成**上游结果未知** | **不可以** | 请求可能已送达并计费，重试会导致上游被调用两次 |

「结果未知」的准确含义不是「上游失败了」，而是「**我们不知道上游那边的结果**」——上游可能正在处理，甚至已经生成成功，只是比超时上限慢。

**代价**：用户白等（额度会归还），若上游实际成功，那张图就永久丢失 —— 而且因为超时时没读到响应体，连上游任务标识都没拿到，事后也无法去查询它。

### 1.4 上游耗时超过超时上限时

当前配置下的这类任务**永远无法成功**：每次都是超时 → 结果未知 → 失败。

调大超时是一个**级联改动**：超时调大 → 租期要一起调大（见 1.2 的不等式）→ 续租周期只要仍满足「× 3 ≤ 租期」可保持不变。

更根本的解法是换交互模式（提交返回标识 + 轮询取结果，或结果回调），但那需要上游支持。

## 二、全局限流双闸

### 2.1 两道闸各自解决什么

这是**两个正交维度**，缺一不可：

| | 限制什么 | 护的是 |
| --- | --- | --- |
| **并发许可** | 同一时刻最多几个请求在飞 | 上游的连接数 / 同时处理数 |
| **速率令牌** | 单位时间平均发几个请求 | 上游的每分钟调用配额 |

**为什么一个不够**（这是最常被追问的一点）：

- **只做并发**：上限 12，若每个请求耗时 100 毫秒，一秒就能发 120 个 → 一分钟 7200 个，远超 60/分钟的配额。失控后上游返回 429，而 429 在我们的策略里是**可重试**的 → 重试又消耗配额 → 继续撞线 → 最终大批任务被判失败。**这就是「重试风暴」**：缺少限流保护时，我们自己的重试机制会把限流错误放大成雪崩。
- **只做速率**：配额 60/分钟，若上游突然变慢、每个请求卡满超时，一分钟内照样放行 60 个 → **同时在飞 60 个连接**，上游连接池被打爆，我们自己也会因为线程与许可被占满而失去产能。

### 2.2 并发许可：靠「到期分值」自动回收

Redis 里是一个**有序集合**：

- 成员 = 申请时生成的**随机标识**（每次申请一个新的）
- 分值 = 这次占用的**到期时刻**
- 集合成员个数 = 当前被占用的名额数

```
申请：取当前时刻（用 Redis 自己的时钟）→ 按分值范围清掉过期成员 → 数个数，达上限就拒
      → 否则把自己加入，分值 = 当前 + 租期 → 给键设过期时间
释放：把自己从集合里删掉
续期：先确认自己还在，在才更新分值
```

**三个设计点**：

1. **不需要登记「谁持有什么」**：回收就是「按分数范围删除」，不用遍历判断。
2. **用租约代替持锁**：进程被强杀时释放逻辑不执行，但成员到点会被下一个申请者顺手清掉 → **名额不会永久泄漏**。释放只是加速回收，不是正确性的必要条件。
3. **用 Redis 的时钟而不是应用时钟**：多实例时钟不同步也不会互相误判。

**为什么成员用随机标识、不用「实例 + 线程名」**：同一线程可能连续申请（上一次的还没释放就再申请），固定标识会互相覆盖，集合里会少算一个名额 → 实际并发突破上限。

**整个过程必须写成一段 Lua**：把「清理 → 计数 → 判断 → 写入」合成一次原子执行。用普通指令的话，两个实例可能同时读到「还剩 1 个名额」然后都加进去 → 超发。

### 2.3 速率令牌：惰性补充的令牌桶

Redis 里是一个**哈希**，只有两个字段：

- `tokens`：上次取用之后的令牌余量（**浮点数**）
- `updated`：上次取用的毫秒时间戳

**它不是一个装着 N 个令牌的容器** —— 「桶」只是比喻，物理上就是一个小数。

一次取用的四个动作：

1. **读**两个字段（键不存在时当成满桶 + 当前时刻）
2. **补**：`余量 = min(容量, 余量 + (现在 − 上次更新) × 每毫秒补充量)`
3. **判 + 扣**：余量 ≥ 1 就扣掉一个放行，否则拒绝
4. **写回**新的余量与时间戳（**放行和拒绝都要写回**）

**核心是「惰性补充」：没有任何定时器往桶里加令牌。** 进水是恒定线性的，所以「过去 347 毫秒进了多少」= 347 × 速率，用一次乘法算出来。不记录过程，只记录两个快照 + 一个线性假设 —— 和复利计算是同一个思路。

**为什么必须是浮点数**：速率是每毫秒 0.001 个，余量经常是 0.03 这种小数。若只存整数且「补满 1 个才加 1」，请求间隔 100 毫秒时时间差恒为 100 → 每次补 0.1 → 取整成 0 → **初始那几个用完后就永远拒绝**。

### 2.4 令牌桶如何「控制」速率

整段逻辑可以压成一个恒等式：

```
任意时刻真实余量 R(t) = min(容量, 上次快照余量 + (t − 上次快照时刻) × 每毫秒补充量)
放行条件：R(t) ≥ 1，放行后 R ← R − 1
```

**两个不等式决定一切**：

| 不等式 | 来源 | 得出什么 |
| --- | --- | --- |
| 消耗只能从余量里扣、余量不为负 | 每次取用减 1 | **长期消耗量 ≤ 长期补充量** → 稳态速率 = 补充速率 |
| 补充被 `min` 封顶 | 容量是上限 | **短期消耗量 ≤ 容量 + 期间补充量** → 突发上限 = 桶容量 |

用蓄水池来理解，只有第三种状态才是"限流"：

| 状态 | 请求间隔 | 池子表现 | 限流器的作用 |
| --- | --- | --- | --- |
| 需求 < 供给 | 大于补充周期 | 趋于满，来一个放一个 | **完全不起作用** |
| 需求 = 供给 | 等于补充周期 | 水位稳定 | 勉强跟上 |
| 需求 > 供给 | 小于补充周期 | 被抽干，随进随出 | **节奏被锁死在进水速率上** |

**用累计曲线看最直观**：横轴时间、纵轴累计次数时，需求线与放行线的**斜率差就是被拒绝的量**。放行线在吃掉初始积蓄后会陡然变缓，斜率锁死在补充速率上 —— 需求量再涨一倍，放行量一点都不会变。

**「每分钟 N 次」是怎么装进桶里的**：

```
每毫秒补充量 = 每分钟次数 ÷ 60000
```

这一步是把粗粒度配额**平滑成连续流速**。若不平滑（比如每分钟整点补 N 个），会出现「每分钟开头一口气发完、剩下时间全失败」的锯齿，而且瞬间冲击上游的窗口计数。

### 2.5 容量与速率的配置关系

以当前配置（容量 4、每分钟 60）为例：

| 来源 | 一分钟放行 |
| --- | --- |
| 稳态补充（每秒 1 个 × 60 秒） | 60 个 |
| 初始积蓄（一次性透支） | **+4 个** |
| 合计 | **64 个** |

跑一小时：`3600 × 1 + 4 = 3604 个` → 均值 `60.07/分钟`，偏差千分之一。**容量不参与长期速率，只抬高一个固定常数。**

**但它确实会让某个 60 秒窗口内达到 64 个** —— 如果上游按严格滑动窗口判（任意 60 秒 ≤ 60），这 4 个就是实打实的超标。

**所以配置值必须低于上游真实上限**：

```
我们的配置 = 上游真实上限 − 桶容量 − 时钟与统计窗口偏差（约 5%~10%）
```

上游给 70 → 配 60（余量 6，约 8.6%）；上游给 60 就该配 54 左右。**配得和上游上限一样高，等于零余量。**

**为什么容量是 4 而不是更大**：容量设 20 也能工作，但有两个约束 —— 一是它必须**小于等于并发许可**，否则攒下的突发额度兑现不出来；二是容量越大，瞬时冲击上游窗口的风险越高。

### 2.6 两道闸的顺序与失败处理是不对称的

顺序是**先并发、后速率**。速率没过要把刚占的并发名额还回去；反过来则不需要（并发没过时速率键根本没被碰过）。

这个不对称源于**两种限流语义的差异**：

| | 并发许可 | 速率令牌 |
| --- | --- | --- |
| 语义 | **占用型** | **消耗型** |
| Redis 结构 | 有序集合，每个占用一个成员 | 哈希，两个字段 |
| 占用 | 加入一个成员 | 余量减 1 |
| 释放 | **必须**（删成员） | **不需要**（减掉就没了） |
| 回收 | 按到期时刻清理 | 下次取用时按时间差补回 |
| 要不要留在进程内 | 要（记住标识才能删） | 不要（用完即弃） |

**这也解释了一个细节**：许可对象里只记着并发许可的键，**没有速率令牌的键** —— 速率令牌用完就完了，没有「归还」这个动作，也就不需要留凭据。

### 2.7 许可在进程内是怎么「存」的

**进程内没有任何集合在存许可。** 许可就是那个对象本身 —— 一个持有「Redis 键名 + 随机标识 + 防重复释放的原子标志」的普通 Java 对象，引用挂在执行线程的调用栈上，生命周期恰好等于一个 try 块。出块自动释放，之后等垃圾回收。

**为什么不需要进程内计数**：如果把「当前用了几个名额」放在进程内，4 个实例各维护一个计数器、各自以为有 12 个名额 → 实际可能同时在跑 48 个。**限流的计数必须在所有实例都能看到的地方。**

**原子标志的两个作用**：保证释放幂等（省一次 Redis 往返）；**已释放的许可拒绝再续期**。

**真正兜底的是租期而不是释放**：如果连释放都失败（Redis 挂了），异常被吞掉 —— 因为成员的到期分值早就写死了，到点会被下一个申请者顺手清掉。这就是它能容忍进程被强杀的原因。

### 2.8 已知边界：许可的续期没有被调用

许可对象上定义了「续期」方法，但**执行路径里没有任何调用点**。也就是单次调用超过许可租期（默认 300 秒）时，许可会中途失效、并发上限被短暂突破。

当前靠「上游超时 120 秒 + 落盘数秒，远小于 300 秒」保证撞不到这条线。**但如果哪天把上游超时调到 5 分钟以上，就必须把许可续期接进执行循环。**

## 三、系统里的六个「过期时间」

极易混淆，必须点名是哪一个：

| 名称 | 默认值 | 存在哪 | 谁清理 | 清理后效果 |
| --- | --- | --- | --- | --- |
| **速率令牌键的存活时间** | **8 秒** | Redis 哈希键 | Redis 自动删键 | 键消失，下次当满桶（多一批突发） |
| 并发许可键的存活时间 | 600 秒 | Redis 有序集合键 | Redis 自动删键 | 键消失，等于所有名额一次性释放 |
| **并发许可成员的到期分值** | **300 秒** | Redis 集合成员 | **下一个申请者清理**，不是自动删 | 该成员移除，释放一个名额 |
| 任务租约 | 300 秒 | MySQL 任务行 | 恢复服务每 30 秒扫 | 任务回退为排队中 |
| 消息存活时间 | 5 / 30 / 120 秒 | RabbitMQ 延迟队列 | 死信回投 | 消息回到主队列 |
| 幂等键 | **永不过期** | MySQL 任务行唯一键 | 无 | 永久占用，客户端不得复用 |

**最易答错的是第 1 行与第 3 行的关系**：两者的回收机制不同。键的存活时间由 Redis 自动删键实现；成员的到期分值**不会自动消失**，靠「按分值范围删除过期成员」在下次申请时顺手回收 —— 如果长时间没人申请，那些过期成员就一直躺在集合里。

**为什么并发许可不能整个键一起消失**：一个集合里可能同时有 12 个名额、各自到期时刻都不同，需要**逐个过期**。

## 四、那个 ×2 到底在防什么

项目里有两处「基础时长 × 2」，但**必要性完全不同**：

| | 公式 | 当前值 | 那个 ×2 是必需的吗 |
| --- | --- | --- | --- |
| 速率令牌键的存活时间 | 装满一桶所需时间 × 2 | 8 秒 | **不是**，1 倍即可 |
| 并发许可键的存活时间 | 成员租期 × 2 | 600 秒 | **是**，硬约束 |

**速率这边为什么 1 倍就够**：桶满之后键存不存在效果一样——都是满桶。所以功能上「存活时间 ≥ 装满时间」就够了，乘 2 只是留余量（吸收浮点取整误差、防止别人只改容量或速率踩破不等式）。

**但不能更短**。反例：容量 4、速率 60/分钟（装满需 4000 毫秒），若存活时间取 2000 毫秒 —— 抽干桶后 2000 毫秒键就过期，此时**桶的真实水位只有 2**，却因为键不存在被当成满桶 4 → **凭空多出 2 个额度**。

> 下界是「桶从**任意水位**涨到满所需的最大时间」，也就是桶从全空涨到满的时间。存活时间不是「桶满所需时间」，而是「**桶一定已经满了**」的保证时间。

**极端反证**：若把存活时间改成 1 秒，则「每 1 秒重置成满桶、放 4 个」→ 每分钟 240 个 → **令牌桶彻底失效，成了绕过限流的口子**。取 2 倍时安全，因为重置带来的突发（4 个）换不回这段空闲本该补充的量。

**并发许可那边为什么是硬约束**：那里存在真实竞态 —— 若键的存活时间等于成员租期，就会出现「**键先于成员租期过期**」：键被删 → 集合里所有名额瞬间消失 → **但任务还在跑**（它以为自己持有许可）→ 实际并发放宽。×2 保证键一定在最后一个成员的租期到期之后才消失。

## 五、额度：两阶段记账

### 5.1 六个动额度的地方

| 位置 | 动作 |
| --- | --- |
| 提交任务 | 预占（已占 + 成本） |
| 成功终态化 | **结算**（已占 −，已用 +） |
| 取消，但已发起过调用 | **结算**（不归还） |
| 失败终态化 | 归还（只减已占） |
| 尝试次数用尽 | 归还 |
| 取消，且未发起调用 | 归还 |
| 死信消费 | 归还 |

重试与重新排队**不动任何计数**。对账任务不新增第八种动作，只是按终态**补做**上面某一条。

### 5.2 结算发生在哪一步

**在「终态化」那一步的事务里，和「状态改成成功」是同一次数据库提交。**

终态化内部做三件事、一次提交：锁读任务行 → 三要素校验 → 写状态与结果图主键 → **结算**。

所以：**第一次真正动「已用」的时刻，就是任务被标记成功的那一刻。** 在此之前额度一直挂在「已占」上。

这保证了不会出现「任务成功了但额度没扣」或「额度扣了但任务没成功」。

### 5.3 为什么结算不再判上限

因为**预占时已经判过了**，额度是「预占即锁定」。结算只是把同一份额度从「占用中」挪到「已消耗」，总数不变。所以不变量 `已用 + 已占 ≤ 当日上限` 从头到尾成立。

**这才是预占制真正的价值：把并发判定前移到提交那一刻，结算路径因此退化成纯记账，不需要再做任何竞争判定。**

反过来设计（提交不预占、完成才扣）就麻烦了：完成时必须重新竞争，还要处理「额度被别的任务用光了、这个任务已经花了上游成本却扣不动」——这个状态没有好答案。

**注意判据是当日上限，不是「剩余额度」**：

```
正确：已用 + 已占 + 本次成本  >  当日上限   → 拒绝
错误：拿「剩余额度」当阈值 —— 而剩余额度 = 上限 − 已用 − 已占，
      代进去就是恒等式，永远成立、拦不住任何请求
```

「剩余额度」只是返回给前端看的派生值（上限减两者，下界截到 0）。

### 5.4 跨天的归属

结算动的是**任务创建日**那一行，不是「今天的行」：由创建时间按配额时区换算得到。所以 23:59 提交、次日 00:02 完成的任务，扣的是前一天的行。

这就是「任务归属日期只能有一处换算」的原因 —— 审计、对账、结算必须复用同一个值，各写一遍时区转换必然对不上账。

### 5.5 为什么「已用」只增不减

没有任何路径会减少「已用」。额度重置靠「**新日期 → 新行**」，不需要定时清零任务。

### 5.6 归还时为什么要夹一个下界

理论上下界截 0 是防御性写法 —— 配对正确时不会为负。但「事件驱动 + 对账兜底」两路可能撞车，夹下界防负数污染账本。审计行就是用来查这种异常的证据。

## 六、租约与执行权

### 6.1 栅栏令牌为什么不能用限流时拿到的标识

两者**职责与可靠性都不同**：

| | 限流许可标识 | 栅栏令牌 |
| --- | --- | --- |
| 解决什么 | 多实例共享配额，怎么释放自己那一份 | 同一任务被多次抢占，**谁是当前合法执行者** |
| 存在哪 | Redis | MySQL 任务行 |
| 生命周期 | 一次执行，用完即删 | 随任务存续到终态 |
| 丢了会怎样 | 多占一个名额，租约到期自愈 | **执行权判定失效，旧执行者能覆盖新结果** |

三个具体理由：

1. **跨存储比对做不到**：限流标识在 Redis，而任务行的更新是 MySQL 的 SQL —— 没法在一条更新的条件里比对 Redis 的值，而原子性恰恰是这个校验的全部价值。
2. **可靠性要求不同**：Redis 重启、键过期，标识就没了。**执行权的判定不能建立在易失存储上**。
3. **职责分离**：限流管「产能」，栅栏管「执行权」。混在一起，Redis 一抖就导致所有任务的执行权判定全失效。

**为什么是自增而不是随机数**：功能上等价（判断逻辑是相等性）。自增的额外价值是**有序** —— 能表达新旧，排查问题时一眼看出这是第几次执行。

### 6.2 续租是「重置」不是「累加」

```
重置：到期时刻 = 当前时刻 + 租期
累加：到期时刻 = 原到期时刻 + 租期
```

正常节奏下两者看不出差别（都在往后推）。**差别在「距当前时刻还有多久」**：重置恒为租期，累加会持续变大。

**真正的灾难在续租被触发得太频繁时**：假设续租每秒触发一次（定时器重入、多实例都以为自己该续、手动触发），累加语义下 1 分钟后到期时刻会被推到 `当前 + 18000 秒`（5 小时）。**此时进程真挂了，任务要僵 5 小时才被回收，恢复服务形同虚设** —— 而且它还在正常运行、每 30 秒扫一次，就是不干活。

**根因**：`到期时刻` 的语义不是「任务总共要跑多久」，而是「**如果我不再出声，别人什么时候可以接管我**」。它是一个**兜底上界**：

- 重置 → 回收延迟**有界**（任何时刻挂掉，最多等一个租期就被接管）
- 累加 → 回收延迟**无界**

**类比看门狗喂狗**：正确的喂狗是「重新计时」，不是「在原有倒计时上加时间」。如果在原有基础上加，狗就永远咬不到你了。

### 6.3 恢复服务的工作流程

**先纠正一处常见口误**：进程被强杀时，续租器跟着死 → **没人续租 → 租约到期 → 恢复服务接管**。不是「租约永不过期」。

1. **定时扫描**（启动延迟 30 秒，之后每轮结束后隔 30 秒再跑）：找「执行中且租约已过期」的任务（或老数据没有租约且开始时间超过 15 分钟），按主键升序、一轮 50 条。注意这是「上一轮跑完才计时」，不会因为扫描变慢而堆积。
2. **逐条独立事务处理**（一条失败不影响其他条）。
3. **锁行 + 二次校验** —— 这一步很关键：扫描用的是**扫描时刻的快照**，从扫描到处理这段时间里，任务可能已经被续租、已被别的恢复线程处理过、已经成功或失败。**不在锁内重新判断，就会误杀正在正常执行的任务。**
4. **回退状态**：改为排队中、清空执行者与租约、设为立即可投递、写失败码。
5. **两个字段刻意不动**：`调用次数`不递增（这不是一次失败的尝试，只是执行权丢失）；额度不归还（任务没有终态，预占继续挂着）。
6. **同事务插入一条新的发件箱事件** → 投递器把它投回队列 → 别的实例重新抢占。

**这里会产生重复消息**（原消息可能还在队列里），但因为任务状态是排队中、且抢占是原子的，重复消息最多让某个实例白跑一趟抢占，不会有正确性问题。

### 6.4 已知缺口：线程假死

**租约检测的是「进程存活」，不是「任务在推进」。**

如果某个工作线程卡死（死循环、卡在不可中断的等待上）而 JVM 还活着 → 续租器照常续 → 租约永不到期 → **任务永远僵住**。

**而且对账救不了它**：对账对「执行中且租约未过期」是直接跳过的。配置里那个「运行超时 15 分钟」只在租约为空（历史数据）时生效，不构成活跃兜底。

**改进方向**（两个都要动代码）：

- **续租前检查活跃迹象**：任务行记「上次进展时间」，执行路径的关键节点更新它；续租器只续进展时间在近期的任务。精确，但要在多处埋点、容易漏。
- **总超时（推荐）**：任务行记「最大总时长」，超过就强制回收，**不管租约是否有效**。语义清晰 —— 「这个任务最多跑 N 分钟」本来就是业务约束，应该显式表达。

总超时的取值基准：`单次超时 × 最大尝试次数 + 各次重试延迟之和`（约 635 秒），再留倍余量取 20~30 分钟。**注意要从「首次开始执行」起算，不能从任务创建时间起算** —— 否则队列积压时，刚拿到执行权的任务会因为「创建时间太久了」被立刻误杀。

## 七、一个贯穿全局的模式：前置检查 vs 权威判定

系统里有两组结构完全相同的设计：

| 前置检查（便宜、尽力而为） | 权威判定（原子、必须成功） |
| --- | --- |
| 消费端的三道只读拦截 | 抢占时那条带条件的更新 |
| 结果落盘前的租约确认 | 终态化时的三要素校验 |

**共同规律**：

| | 前置检查 | 权威判定 |
| --- | --- | --- |
| 读/写 | 只读 | 带条件的写 |
| 成本 | 便宜 | 相对贵 |
| 位置 | 在「重活」之前 | 在最后 |
| 性质 | 尽力而为，可被绕过 | 正确性的唯一保证 |

### 7.1 三道只读拦截为什么必须在「拿许可」之前

一次成本对比：

| 步骤 | 一次成本 |
| --- | --- |
| 三道拦截 | 一次主键查询 + 三次纯内存比较 |
| 拿并发许可 | 一次 Redis 原子脚本 |
| 抢执行权 | 一次带条件的更新 |

上游并发许可是全系统最稀缺的资源。**先拿许可再判断，一条废消息会占着许可最长一个租期，期间真任务全被挡在外面。**

三道拦截刻意**只读**：只读 → 不改状态 → 天然幂等 → 重复执行一百遍也没副作用。这也正是「拦截只是性能优化，正确性另有保障」的底气。

### 7.2 落盘前为什么也要校验一次租约

**因为结果落盘是「重活」，而校验失败后这些活全要白做一遍再撤销一遍。**

具体省掉三样东西：

- **白做的重活**：写对象存储是最贵的操作（网络 IO、几 MB 数据）
- **脏数据窗口**：没有这一步的话，图片行会先被创建、任务稍后才终态化 —— 这段窗口里用户在图片列表能看到一张「任务还没成功」的图
- **回滚的二次开销**：终态化失败要删图片行、删两个对象、回退空间用量，提前发现就能让这套动作根本不发生

**但它不是正确性保证** —— 因为它和终态化之间隔着「写对象存储 + 建图片行」这几秒，在此之间租约可能丢。**前置检查通过的时刻是过去，不能代表最终时刻的状态。**

**所以两道都要：前一道省钱省时间，后一道保正确。**

## 八、面试口径补充

### 8.1 能主动讲出来的设计点

1. **限流是两个正交维度**，不是冗余：并发护连接数、速率护调用配额，缺一个都会在特定负载形态下失控。
2. **消耗型配额必须平滑成连续流速**，否则会出现「每分钟开头发完、剩余时间全失败」的锯齿，并冲击上游的窗口计数。
3. **配置值必须低于上游真实上限**，差额用来吸收突发、时钟偏差与统计窗口差异。
4. **额度是预占制**：判定前移到提交时刻，结算退化成纯记账。
5. **租约是兜底上界，不是任务时长** —— 所以续租必须是重置语义，否则上界无界、兜底失效。
6. **前置检查与权威判定分离**：前者优化性能、后者保证正确，两者不能互相替代。

### 8.2 已知边界（主动说比被问出来好）

1. **线程假死没有兜底**（租约检测进程存活，不检测任务推进；对账也会跳过）。
2. **并发许可的续期方法没有被调用**（单次调用超过许可租期时并发上限会被短暂突破）。
3. **「超时 < 租期」只是文档约定**，代码里没有强校验，改超时时容易踩坑。
4. **桶容量会让某个 60 秒窗口内超出配置值**（最多超出容量个），上游若用严格滑动窗口会拒。
5. **上游同步调用受 HTTP 超时硬限**，耗时超过超时的任务在当前配置下无法成功。
