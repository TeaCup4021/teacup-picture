# AI 生图链路 · 面试口述稿

## 零、开场那几句里的两处口径

讲的时候注意这两个地方别说错：

1. **「客户端生成生图任务 ID」不准确** —— 客户端生成的是**幂等键**，不是任务标识。任务标识是数据库自增主键，客户端拿不到也生成不了。幂等键的语义是「**一次用户意图，一个键**」：点提交时生成并缓存，所有自动重试复用同一个，用户改了内容重新提交才换新键。而且它一旦占用**永久生效**，不是窗口幂等。
2. **额度判据不是「剩余额度」** —— 是**当日上限**。剩余额度 = 上限 − 已用 − 已占，拿它当阈值是恒等式，永远成立、拦不住任何请求。

另外**事务边界**：不是「锁用户行，开启事务」，而是事务注解打在方法上、**进入方法就开启**，那四组参数校验也在事务内（但它们全是只读、不加锁）。

## 一、提交阶段（同步，一个事务内）

用户点提交之后，后端按这个顺序做：

**先做四组只读校验**：

1. **幂等键格式** —— 去空白后匹配字符集和长度，不通过就报错
2. **任务类型和提示词** —— 类型只能是生图或扩图；提示词去空白后非空且不超过 2000 字
3. **模型解析与能力校验** —— 按模型编码查模型表，要求存在且已启用；然后查模型声明的能力里有没有这个任务类型、支持的比例里有没有这次的比例、支持的清晰度里有没有这次的清晰度
4. **输出选项归一和互斥校验** —— 先归一，也就是背景和输出格式没传的话，取模型支持列表里的第一项当默认值；然后判几条互斥：背景和格式要在全局枚举里、也要在该模型支持的范围里，压缩质量要在 0 到 100 之间，PNG 不能带有损压缩，传了压缩质量要模型支持，透明背景不能配 JPEG 输出

**然后校验源图和参考图**：图必须存在、属于当前用户、没被软删；扩图类型必须传源图；传了参考图要模型声明支持参考图。

**这几组全是只读，不加任何锁，到此为止没有任何写操作。**

**接着是五步写操作，全在同一个事务里**：

**第一步，锁用户行。** 按用户主键加行级排他锁。它的作用是让后面的「查任务 → 判断 → 插任务」对同一个用户串行化。

**第二步，幂等查重。** 按用户加幂等键去任务表里查。命中了就逐个字段比对请求内容——比对的是**归一后的值**，所以「省略背景」和「显式写上模型第一项」会被判成同一个请求。内容一致就返回原任务、给 200，不新建也不扣额度；内容不一致就报冲突。没命中就继续往下。

**第三步，额度预占。** 全在额度表上，分三小步：先补建当天该类型的行（幂等插入，日期按配额时区取当天、不是 UTC 日期）；然后锁这一行读出来；然后判——**已用 + 已占 + 本次成本 大于 当日上限就拒绝**，通过了就把已占加上本次成本。

**第四步，插入任务行。** 一次写全，状态**直接就是排队中**——不是先插再改状态。把上游标识、上游模型名、归一后的输出选项全部拷进任务行，这样执行阶段不依赖模型表的当前值，管理员改配置不影响已提交的任务。

**第五步，插入发件箱行。** 同一个事务里往发件箱表插一条待投递事件。

**第五步为什么必须在事务内**：任务入库在 MySQL、消息发在 RabbitMQ，两个系统没有共同事务。先入库再发消息，发消息失败就丢任务；先发消息再入库，消息可能指向不存在的任务。**用发件箱把「要不要发消息」降级成数据库的本地事务**，由独立投递器负责真正投递。这样就不会出现「任务写进去了但消息没发出去」的中间态——那条任务会永远停在排队中、额度永远被占、没有任何东西会来救它。

**最后提交事务**，释放用户行锁和额度行锁，接口返回任务标识和排队中状态。

## 二、投递阶段（异步）

事务提交之后，接口已经返回了，真正的执行还没开始。

**投递器每秒扫一次发件箱表**：捞「待投递或投递失败」且到时间、且没被别的实例锁住的记录，一次 50 条。抢到之后（条件更新写锁的所有者和到期时间）发一条持久化消息到交换机，然后**等发布确认**——确认收到且没被退回，才把这条事件标记成已投递；确认失败就记一次失败、重试次数加一、按指数退避下次再来。

两个细节值得讲：

- **扫描刻意不按主键排序** —— 索引以状态为前导列，加排序会让优化器放弃索引改走主键扫描，积压时实测慢约 200 倍。投递本来不要求先进先出。
- **已投递的记录保留 7 天**，每小时清一批。

**消息体里只有事件标识和任务标识**，不带提示词、不带密钥、不带图片内容。

## 三、执行阶段

### 3.1 三道只读拦截

消费者拿到消息，先做三道判断，共用同一次任务行的查询，都是纯内存比较：

| 判断 | 处理 |
| --- | --- |
| 任务不存在或已终态 | 直接确认丢弃 —— **这是重复消费的幂等屏障** |
| 排队中但没到下次可尝试时间 | 按剩余秒数就近取档（5 / 30 / 120 秒）重新投递 |
| 执行中且租约没过期 | 说明别人在干，5 秒后重投 |

**三道都在拿并发许可之前**，因为拦截最便宜（一次查询加三次比较），而并发许可是全系统最稀缺的资源。先拿许可再判断，一条废消息会占着许可最长一个租期，期间真任务全被挡在外面。

这三道**只读**，所以天然幂等、重复执行一百遍也没副作用。它们只是性能优化，**正确性由后面的条件更新和栅栏令牌保证**。

### 3.2 拿两道闸

**先抢全局并发许可，再抢速率令牌，两个都拿到才算拿到产能。**

- 并发许可限制「同一时刻几个请求在飞」，护上游的连接数
- 速率令牌限制「单位时间平均发几个」，护上游的每分钟调用配额

拿不到就 5 秒后重投——**不原地等**，避免线程被不可控的等待时间占住。

### 3.3 抢执行权

一条更新语句同时做几件事：状态改成执行中、把「已发起调用」标记打上、尝试次数加一、**栅栏令牌加一**、写上执行者标识、写上租约到期时间、首次执行时记下开始时间。

条件写在 WHERE 里：状态是排队中且已到时间、或者执行中且租约已过期，**且尝试次数没到上限**。改到一行就是抢到了，零行就是没抢到。

**抢不到还要再读一次最新状态，分三种处理**：

1. 已终态 → 确认丢弃
2. **还是排队中、但尝试次数已经用满 → 就地终态化并归还额度**
3. 其余（被别人抢走在跑、或还在等）→ 5 秒后重投

**第 2 种必须有**：不判这一下，任务永远是排队中且已到时间、次数已达上限，抢占就永远失败，消息会每 5 秒重投一次无限循环，而且没有路径会把它推向终态，**额度预占永久悬挂**。

### 3.4 调上游

组装请求：任务类型、上游模型名、提示词、比例、清晰度、背景、输出格式、压缩质量，加上源图和参考图的**临时访问地址**（优先用签名地址，拿不到才回落到持久地址）。

比例和清晰度要映射成上游的取值。当前上游实现只做生图，扩图类型会直接抛「能力不支持」。

**这一步是阻塞的**：线程卡在这里等上游返回，最多等 120 秒。

### 3.5 落库前确认租约

在把结果图片写进数据库之前，先执行一次带条件的续租——条件带上执行者标识和栅栏令牌。

改到零行说明**租约已经丢了、任务归属已经不属于这个执行者了**，那就抛异常走「**只确认消息、不置失败**」的分支：它已经没有资格改这个任务的状态，那是新持有者的事，应该由恢复服务重新入队。

**为什么要在落盘前先校验一次**：结果落盘是「重活」（写对象存储、建图片行、更新空间用量）。如果等到最后才发现失权，这些活全要白做一遍再撤销一遍，中间还有个「图片已存在但任务还没终态化」的脏数据窗口。**但这一步只是省钱省时间的优化，不是正确性保证** —— 因为它和终态化之间隔着几秒，前置检查通过的时刻不代表最终时刻的状态。

### 3.6 检查是否已被取消

读一次任务状态，用户已经取消就直接确认消息、结果不入库。

这一步放在**调上游之后、落盘之前**，正是「取消只停止入库、不退额度」的落点——上游成本已经产生了。

### 3.7 结果落盘

上游返回的可能是内联数据、也可能是图片地址，两种都落到对象存储：

1. 图片写进对象存储
2. 建一条图片记录：对象存储键、缩略图键、内容类型、校验值、尺寸、比例、格式、大小、名称、简介、标签、所属用户与空间
3. 更新空间的用量计数（大小和数量各加）
4. 建一条初始版本记录

保存服务自带补偿：**插入失败要把已经写进对象存储的原图和缩略图删掉。**

### 3.8 终态化 + 结算（同一个事务）

锁读任务行，校验三件事：**状态还是执行中吗、执行者标识还匹配吗、栅栏令牌还匹配吗**。

三样都对，才写：成功状态、上游的回执标识、结果图片的主键、完成时间，清掉执行者和租约；**同时结算额度——把「已占」减掉、「已用」加上**，标记已结算，写一条审计行。

**这两件事是一次提交**，所以不会出现「任务成功了但额度没扣」或者反过来。

**如果三要素校验不通过**，说明任务已经被别人接管了 —— 那就回头把刚写的图片**整条删掉**：图片行、对象存储里的两个对象、空间用量都要回退，避免留下孤儿对象。

**为什么结算不再判上限**：因为预占时已经判过了，额度是「预占即锁定」。结算只是把同一份额度从"占用中"挪到"已消耗"，总数不变。**这才是预占制真正的价值——把并发判定前移到提交那一刻，结算路径退化成纯记账。**

### 3.9 异常往哪走

| 情况 | 处理 |
| --- | --- |
| 上游限流 / 明确回「超时」/ 5xx | **可重试**：状态改回排队中、清执行者、设下次可尝试时间，由消费者发延迟消息（5 / 30 / 120 秒三档） |
| 上游回 403 无权限 | 顺手把模型下架，然后置失败并归还 |
| **连接层异常** | **判成「上游结果未知」、不重试** |
| 尝试次数用尽 | 置失败并归还 |
| 其他运行时异常（如落盘失败） | 置失败并归还 |

**连接层异常为什么不重试**：判据是「**上游到底收没收到请求**」。错误可能发生在上游已经接单之后，盲目重试会让它再生成一次、成本翻倍。而我们无法区分「成功但慢」和「真的失败」，只能取保守策略。代价是用户白等（额度会归还），若上游实际成功，那张图就永久丢失。

## 四、四条兜底

上面全是事件驱动。事件驱动覆盖不了三种情况：**进程被强杀、消息进死信没人处理、某个收尾分支漏调用**。所以有四条独立链路兜着：

| 兜底链路 | 周期 | 做什么 |
| --- | --- | --- |
| 租约续期 | 90 秒 | 按实例标识批量延长本实例持有的执行中任务的租约 |
| 租约过期恢复 | 30 秒 | 把租约过期的执行中任务退回排队并重新投递 |
| 死信消费 | 事件驱动 | 把进死信的任务终态化并归还额度，确认后不重投 |
| 额度对账 | 10 分钟 | 扫「未结算且未归还」的悬挂预占，按终态补结算或补归还；僵尸任务强制回收 |

**租约过期恢复里有个关键设计**：扫描用的是扫描时刻的快照，但处理时要**在锁内重新校验一次**（还是执行中吗、租约确实过期了吗）。因为从扫描到处理这段时间，任务可能已经被续租、已被别的恢复线程处理过、已经成功或失败。**不在锁内重新判断，就会误杀正在正常执行的任务。**

**另外两个字段刻意不动**：尝试次数不递增（这不是一次失败的尝试，只是执行权丢失）；额度不归还（任务没有终态，只是回到排队，预占继续挂着）。

## 五、一句话收尾

> **同步提交把任务和事件一起落库，异步投递把事件变成消息，工作线程限流抢占后调上游、落盘、终态化，四条独立链路兜住事件驱动盖不住的情况。事件驱动负责快，租约和对账负责不漏。**

## 六、讲的时候的加分点与避坑点

**可以主动讲的六个设计点**：

1. 限流是两个正交维度，不是冗余 —— 并发护连接数、速率护调用配额，缺一个都会在特定负载形态下失控
2. 消耗型配额必须**平滑成连续流速**，否则会出现「每分钟开头发完、剩余时间全失败」的锯齿
3. **配置值必须低于上游真实上限**，差额吸收突发、时钟偏差与统计窗口差异
4. 额度是**预占制**，判定前移到提交时刻
5. **租约是兜底上界、不是任务时长**，所以续租必须是「重置」而不是「累加」
6. **前置检查与权威判定分离**：前者优化性能、后者保证正确，两者不能互相替代

**主动说出来的五条已知边界**（比被问出来强）：

1. 线程假死没有兜底 —— 租约检测的是「进程存活」，不是「任务在推进」
2. 并发许可的续期方法没有被调用 —— 单次调用超过许可租期时并发上限会被短暂突破
3. 「上游超时 < 任务租期」只是文档约定，代码里没有强校验
4. 桶容量会让某个 60 秒窗口内超出配置值（最多超出容量个）
5. 上游是同步调用，受 HTTP 超时硬限 —— 耗时超过超时的任务在今天配置下无法成功
